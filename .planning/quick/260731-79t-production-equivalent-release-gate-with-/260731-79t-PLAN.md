# 生产等价发布门禁实施计划

## 目标

把真实 PostgreSQL、RabbitMQ、worker/systemd 一致性、durable queue 收敛、可逆写操作、页面 canonical Audit 和 T+0/T+60/T+300 延迟复核收敛为部署激活前的单一强制门禁。没有完整 PASS evidence 时禁止 activate，并保持上一稳定 release。

## 边界与 I/O

- 输入：候选 release、当前稳定 release、本机安全加载的 admin token、root-owned `0600` 且显式 `fixture_ownership=test_owned` 的可逆关系 scenario。
- 事实源：PostgreSQL durable queue/dirty scopes、RabbitMQ runtime、worker registry、systemd concrete units、页面 canonical Audit。
- 输出：按 release/commit 绑定、root-owned `0600` 的 checkpoint 与最终 evidence。
- 不新增第二套队列、缓存、worker registry 或页面 read model；不把真实业务关系升级成测试对象。

## Task 1：门禁合同与运行时证据

- [x] 页面与 API 使用独立 origin，页面 audit 走公开站点，内部 API/SLO 走候选 runtime。
- [x] 在写 smoke 与页面 audit 后重新采样 runtime health，阻断“采样后才产生 queue amplification”。
- [x] 强制校验 worker registry/systemd、unknown worker、required readiness、dirty scope、outbox、dead-letter、RabbitMQ 和页面 Audit。
- [x] 最终证据必须同时包含 pre、T+0、T+60、T+300，并由合同校验器证明 `queue_stable_after_300_seconds=true`。

## Task 2：可逆写操作安全边界

- [x] 每次执行动态生成 mutation idempotency key，禁止静态 key 跨 release 重用。
- [x] release gate 只接受登记 shape、完整 confirm/withdraw/recovery checkpoints 和 `fixture_ownership=test_owned`。
- [x] 标准 scenario 只允许通过受控 helper 校验后原子安装，拒绝 symlink、越权 owner、宽权限、大文件和非候选 release。
- [x] 普通生产业务关系只允许 read-only discovery；没有测试专用 fixture 时 fail closed，不执行 mutation。

## Task 3：性能热路径与回归保护

- [x] Workbench canonical search 复用同一 paired/unpaired 查询与一次 hydrate，移除同请求重复查询链。
- [x] 补充 gate、write smoke、deploy helper 与 canonical search 定向回归。
- [x] 完成本地 lint/docs/shell/diff 校验，提交并推送 main。
- [ ] 通过正式部署入口运行门禁；只有完整 PASS 才激活，并保存 T+300 生产证据。

## 验收

- `release_gate_status = PASS`
- `unknown_worker_count = 0`
- `required_worker_not_ready = 0`
- `dirty_scope_count = 0`
- `pending_outbox_count = 0`
- `dead_letter_delta = 0`
- `queue_stable_after_300_seconds = true`
- 可逆写 fixture 最终恢复 inactive；真实业务关系未被当作 fixture。
- 任一 checkpoint 失败时自动恢复上一 release，且候选不留作 active。

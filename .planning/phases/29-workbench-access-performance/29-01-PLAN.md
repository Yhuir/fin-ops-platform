# Phase 29 Plan 01: 关联台访问恢复热路径优化

## Goal

降低关联台写后恢复和打开页面时的重复读 I/O：保持现有 active-generation 原子发布、canonical
freshness proof 和 exact-scope queue 合同，只让操作后等待执行一次触发 load、轻量状态等待和一次
最终 fresh load。

## Baseline and root cause

- Phase 27 写后样本为 `6.975s`，其中 worker handler 约 `3.348s`；隔离重建曾为
  `1.330s`，generation save 为 `0.763s`。
- 当前生产最近一小时 Workbench handler 为 p50 `1401ms`、p95 `2366ms`、p99
  `2596ms`，最近 exact scopes 约 `2.2–2.7s`；`6.9s` 已不是当前稳定常态。
- 前端没有 backend operation projection 的操作会每 `150ms` 重复调用 combined initial，
  造成刷新期间重复完整页面 freshness/read I/O。
- 公开 `/api/workbench/refresh-status` 仍调用完整 diagnostic repository port；同一代码库的
  groups gate 和 SSE provider 已经使用轻量 `get_workbench_groups_freshness_status`。

## Non-goals

- 不重写 Workbench projection、generation save、relation fact 或业务配对规则。
- 不新增 cache、表、索引、migration、queue、worker、SSE、协调器或第二 freshness 系统。
- 不恢复写后跨页 fan-out，不让 stale/refreshing payload 冒充 fresh。
- 不运行无关的 183 个 Chromium tests 或全量 CI。

  <acceptance_criteria>

<task id="2" type="auto" tdd="true">
  <name>删除操作后重复 combined initial 轮询</name>
  <behavior>
    先调用一次 combined initial 触发 exact-scope recovery；若未 fresh，则只轮询公开轻量
    refresh-status；status 通过 canonical proof 返回 fresh 后，再调用一次 combined initial 并安装完整
    payload。最终 load 若遇到新的 version drift，继续轻量等待，不接受 stale payload。
  </behavior>
  <acceptance_criteria>
    <criterion>refreshing 期间不重复拉 paired/unpaired payload。</criterion>
    <criterion>操作完成前仍保持 blocking UI，最终只安装完整 fresh payload。</criterion>
    <criterion>failed/unavailable/timeout 继续显示明确可重试错误。</criterion>
  </acceptance_criteria>
</task>

# 05-16 Bounded Execution Prompt：成本 Audit 业务值证明单次集合查询

## 本轮唯一目标

把成本统计 Audit owner 中 `_key_display_field_issues(...)` 的五次串行数据库往返收敛为一次只读集合查询，同时保留五类证明各自的
SQL、独立 sample limit、issue code、subject/scope/details 和 fail-closed 语义。包含 active relation 的固定本地 query budget 必须从 30
降到 26。不得修改或复制 Workbench / Bank Detail 的证明逻辑，不得引入 proof cache/context、跨请求缓存、临时表、写操作或新抽象层。

## Grill-me 门禁答案

| 问题 | 本轮答案 |
| --- | --- |
| 唯一问题 | 当前成本 Audit 的业务字段、bank-flow 字段、scope summary、project/expense summary、bank accounts 五类证明使用相同 snapshot，却串行执行五次 `fetch_all`。本地 active-relation 证据显示总预算为 30，其中这五次是可在成本 owner 内安全合并的直接往返。 |
| 直接模块 | `cost_statistics_page_audit.py`、成本 Audit 专属测试与成本模块维护文档。 |
| 输入 I/O | caller-owned repeatable-read read-only snapshot、`tenant_id` 与 `example_limit + 1`。每个 proof branch 继续接收原有参数和独立 limit。 |
| 输出 I/O | 一次 `fetch_all` 返回统一的 `issue_code + subject_id + scope_key + details` rows，再映射为既有 `AuditIssue`；外部 report shape 不变。 |
| 事实源 | 仍是现有 app/read_model/settings 表和同一数据库 snapshot；不缓存上次 Audit，不以 hash 或 summary 代替 exact proof。 |
| 旧链路 | 删除五次 `_proof_query_issues(...)` 循环调用；不保留逐查询 fallback、兼容开关或第二 executor。该 helper 若 whole-repo 无调用则一并删除。 |
| 隔离性 | 只改成本 Audit owner。Workbench 与 Bank Detail collector 仍通过各自 owner执行，其他页面 Audit/read model/API/worker 零行为变化。 |
| 反过度设计 | 不增加 query builder class、proof context、memoization、并发连接、表、索引、migration 或 dependency；仅把五个既有、边界一致的 SELECT 作为独立 limited subquery 做 `UNION ALL`。 |
| 暂不删除 full-view | CodeGraph 证明 `get_cost_statistics_view` 仍被 month/summary/project兼容合同使用；旧 summary/project route 又要求生产 access-log或 owner确认后才能删除。本轮禁止无证据强删。 |
| 测试责任 | 固定 budget=26；五个 marker只出现在同一次 SQL；每个 branch独立 `limit`；五类 issue code/details保持；read-only、唯一 owner、registry/CLI/System Audit回归全通过。 |
| 部署 | 本轮不部署、不访问生产、不运行生产性能验证；不 branch/stage/commit/push/PR/stash/reset/clean。 |

schema/index、共享 pool、部署文件及其他页面代码。

## 必须满足的生产合同

1. 五个原证明 branch 的 SQL 语义、事实源、排序和独立 `limit %s` 保持，不先取全量到 Python 比较。
2. 统一查询只返回 `issue_code`、`subject_id`、`scope_key` 与 JSONB `details`；issue message/severity/report envelope不变。
3. 每个 branch 的 issue code由绑定参数传入，禁止拼接外部输入；参数顺序必须由测试精确锁定。
4. `business_value_proofs` 只执行一次 `fetch_all`；五个旧 marker仍可在同一 SQL中被定位，但不得各自执行。
5. active relation固定本地 budget恰为 26；这只是 anti-regression，不宣称生产 `p95 <= 5s`。
6. Audit始终只读，不创建 temp table、不执行写入、不触发 rebuild/refresh/export。
7. Workbench/Bank Detail dependency collectors、caller-owned snapshot和唯一成本 executor保持不变。
8. 不创建旧逐查询 fallback；旧 helper无调用时删除并用 whole-repo scan证明。

## 七类测试责任

1. Business core unit：适用；五类 proof 的 issue code、subject/scope/details和独立 sample limit保持。
2. Service-layer：适用；一次 I/O、26 query budget、caller snapshot与只读合同。
3. API contract：行为未改；复跑 operations/page Audit report envelope与 registry/CLI分派回归。
4. Read model/cache/background job：适用；proof仍读取当前 snapshot且不写、不缓存、不enqueue；worker未修改。
5. Frontend interaction：不适用；页面、Audit icon和遮罩未修改。
6. End-to-end integration：适用；统一 page Audit/CLI/System Audit对同一 owner的本地集成回归；真实 PostgreSQL性能留到统一部署后。
7. Existing regression：适用；Workbench/Bank Detail collector默认行为、其他页面 Audit和 shared-file zero-cost-branch保持。

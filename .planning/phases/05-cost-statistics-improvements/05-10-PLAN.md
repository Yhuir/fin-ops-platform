# 05-10 Bounded Execution Prompt：成本 Audit source-version 证明单次往返

## 本轮唯一目标

在不弱化完整性证明、不改变其他页面行为的前提下，把成本 Audit 专属
`_read_model_source_version_mismatch_issues` 内三个独立数据库往返合并为一个集合查询：

1. row `source_versions` 与 scope `source_versions` 一致性；
2. 月 scope 嵌入的 Workbench / Bank Detail source versions 与当前上游一致性；
3. parent `:all` scope 的 materialized child shard map 与实际月份 child scopes 一致性。

三个证明分支必须继续各自保留 `limit`、排序、issue code、subject/scope 和 details，不能用一个全局 limit
让前一个分支吞掉后两个分支的样本。本轮将 active-relation 查询预算从 32 降到 `<=30`；该预算只证明固定往返收敛，
不冒充最终 `Audit p95 <= 5s` 或最终四组集合 SQL。保持 `DEPLOYMENT_HOLD`。

## 必须保持的合同

1. caller-owned `REPEATABLE READ READ ONLY` snapshot、只读策略和统一 HTTP/CLI/System dispatch 不变。
2. 三个证明分支均执行；任一 mismatch 继续阻断 integrity，不能缓存绿色结论或跳过检查。
3. issue codes 精确保持：
   - `cost_statistics_row_source_versions_mismatch`
   - `cost_statistics_upstream_source_versions_mismatch`
   - `cost_statistics_parent_source_shards_mismatch`
4. 每个证明分支独立 `order by ... limit %s`；总返回可达 `3 * limit`，不得改成全局 `limit`。
5. 原有 details keys 原样保留；SQL 可返回结构化 `details`，Python 不得把 `issue_code` 混入 details。
6. active relation 非空场景总查询预算必须 `<=30`，且 source-version 证明 SQL 只调用一次。
7. 不改租户、scope、月份、active generation、Bank Detail scope 或 parent shard 的事实判定条件。

# Phase 30 Plan 01: 关联台并发恢复真实链路优化

## Goal

删除 Workbench exact-month worker 中被丢弃的 legacy full-payload OA 组装，并让关系写生产验证测量真实关联台
combined initial 首屏，而不是分页 `/groups` endpoint。

## Tasks

<task id="1" type="auto" tdd="true">
  <name>收窄 worker OA 读取 I/O 并删除旧读函数</name>
  <behavior>
    `WorkbenchQueryService` 提供只返回当前 exact/all scope OA rows 的窄方法；projection builder 直接消费，
    不再调用 grouped full-payload `get_workbench(...)`。删除 whole-repo 零调用 `_legacy_oa_rows(...)`。
  </behavior>
  <acceptance_criteria>
    <criterion>每个 OA row 在 projection 读取边界只序列化一次。</criterion>
    <criterion>附件 invoice rows 不作为 OA rows 重复进入 projection。</criterion>
    <criterion>OA row shape、父 OA 补载与 relation grouping 不变。</criterion>
  </acceptance_criteria>
</task>

<task id="2" type="auto" tdd="true">
  <name>修正可逆 relation 的关联台页面性能合同</name>
  <behavior>
    `reconciliation-workbench` consumer 使用真实 `GET /api/workbench?month=all`，断言根为
    `paired` / `unpaired`。断言按 relation shape 使用真实 zone：完整关系 confirm 位于 paired；
    冻结要求未满足的 active Turnover closure 与撤回/恢复事实位于 unpaired。
    `/groups` 保留为页面滚动分页 API，不删除、不伪装成首屏。
  </behavior>
  <acceptance_criteria>
    <criterion>scenario contract 拒绝旧 `/api/workbench/groups` 页面 consumer。</criterion>
    <criterion>consumer 仍要求 fresh、完整 payload 和 test-owned relation membership。</criterion>
    <criterion>不改变任何业务写、queue、worker、freshness 或页面 API response shape。</criterion>
  </acceptance_criteria>
</task>

<task id="3" type="auto" tdd="true">
  <name>阻止 exact/all 并发时的暂态全月份 fan-out</name>
  <behavior>
    exact refresh 已 active 且 all freshness 暂时没有新的 exact target 时，query facade 不把目标回退为
    `workbench:all`。等待现有任务完成后，由页面下一次轮询重新 proof 并精确 enqueue 剩余 mismatch 月份。
  </behavior>
  <acceptance_criteria>
    <criterion>普通 relation 写的 exact/all 并发访问不产生全月份 Workbench shard fan-out。</criterion>
    <criterion>explicit mismatch 与 failed exact scopes 仍精确 enqueue。</criterion>
    <criterion>稳定态 missing/cold-start 且无法得到 exact scope 时仍保留正式 all 恢复入口。</criterion>
  </acceptance_criteria>
</task>

<task id="4" type="auto">
  <name>集中验证和一次候选发布</name>
  <behavior>
    本地定向测试一次收集失败并集中修复；通过后只部署一个候选 release。使用同一类 test-owned 可恢复
    confirm/withdraw fixture，并发访问真实关联台首屏和相关消费者，验证写返回、zero fan-out、最终 fresh、
    relation membership、queue/worker drain、System Audit 和关联台 access-to-visible。
  </behavior>
  <acceptance_criteria>
    <criterion>正确性、完整性、隔离、恢复和审计全部通过。</criterion>
    <criterion>生产报告明确区分 worker、真实首屏和总恢复耗时，不把验证口径修正冒充 SQL 加速。</criterion>
    <criterion>不执行无关 183-browser tests 或全量 CI。</criterion>
  </acceptance_criteria>
</task>

## 计划复审

- 生产级：保留权限、审计、可逆 fixture、fail-closed freshness 和原子发布。
- 模块化/I/O：OA projection 只读窄 OA-row I/O；runner 只消费公开页面 API。
- 不过度设计：无新表、缓存、索引、migration、worker、queue、registry、协调器或新状态机。
- 性能：删除 worker 重复 CPU/serialization；生产性能口径改为真实页面首屏。
- 旧代码：删除零调用 `_legacy_oa_rows`，旧 grouped read 不再进入 worker。
- 回归隔离：不改变写链、事实源、scope、read model schema 或其它页面 endpoint。

结论：计划符合用户六项要求，可以执行。

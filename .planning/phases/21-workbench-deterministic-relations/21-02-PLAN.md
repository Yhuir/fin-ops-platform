<objective>
把 Wave 1 的 `FormalRelationPlan` 接入唯一生产写链：`workbench-matching` dirty-scope worker 批量读取事实并运行纯 matcher，只有安全 plan 才在同一 orchestration path 内调用现有 `WorkbenchRelationCommandService` 与 `WorkbenchWriteUnitOfWork`，原子提交 active relation、history、idempotency record、dirty scopes 和 outbox。所有 confirm/extend/withdraw/cancel 使用同一排序 member advisory-lock 约定并在锁后重读 canonical relation state；自动 origin 只进入审计 metadata，storage mode 继续使用通用 `manual_confirmed`。同时从 Application、worker、exception 和 write facade 热路径移除 candidate/decision 依赖，不保留双 orchestrator、best-effort persistence 或 compatibility fallback。
</objective>

<must_haves>
  <truths>
    - D-03：安全自动结果直接正式化；不存在 candidate/decision 先写、再消费、再升级的中间状态。零 plan、ambiguous、unsafe、resource-limited 和 stale input 都是零 relation/history/outbox 写入。
    - D-04：系统自动与人工确认共用 `relation_mode="manual_confirmed"`、active lifecycle、command validation、history 和 fan-out；`origin=system_deterministic`、rule/version/evidence 只存在于 immutable audit metadata，不参与 projection/API 分支。
    - D-05：已 active relation 不因历史 `case:decision:*`、creation origin 或 matching rerun 被重建/改名/撤回；migration 的 `preserve_active` 永不进入写 handler。允许的 runtime extension 只能在显式唯一 reference 已把新事实锚定到同一 active case 时追加成员，保留 case ID、原成员和 active 状态，并记录 confirm history。
    - D-08：写前重新核对 plan fingerprint、active overlap、withdrawal exact-set block 与 source versions；任何变化 fail closed 并由 dirty-scope retry 重新规划，禁止在 handler 内猜测、缩减成员或降级规则。
    - D-10：只有显式 audited user withdraw/cancel 退出 active lifecycle；exact sorted `(row_type, canonical_object_identity)` fingerprint 阻止同一集合自动重建。系统 retry、source change、exception apply 或 read-model rebuild 不自动撤回关系。
    - D-13：唯一链路为 bulk reader -> pure matcher -> `WorkbenchMatchingOrchestrator` -> `WorkbenchRelationCommandService` inside `WorkbenchWriteUnitOfWork` -> relation repository/history/idempotency/durable refresh -> existing workers。Worker 不依赖 Application/server/auth/HTTP；service 无 SQL；repository 不写 queue outside UoW。
    - D-14（Wave 2 runtime cut）：Application/worker/exception/write 热路径对 `WorkbenchCandidateMatchService`、`WorkbenchReconciliationDecisionStore`、candidate persistence、decision consume/suppress/cleanup、dual decision/legacy branch 的依赖为零；遗留定义/表的物理删除留给 Wave 4，且在此后必须是 inert inventory only。
  </truths>
  <artifacts>
    - `WorkbenchFormalRelationCommand`：承载 one plan 的 action/scopes/idempotency/source-version preconditions/audit metadata，供现有 UoW 使用，不是新业务状态。
    - `WorkbenchMatchingOrchestrator.run(...)`：只依赖 `PostgresWorkbenchFormalRelationFactRepository`, `WorkbenchFreeMatchingEngine`, `WorkbenchWriteUnitOfWork` 与 transaction-bound relation command factory；无 candidate/decision/read-model service dependency。
    - `PostgresWorkbenchRelationRepository.acquire_relation_member_locks(...)`：按 canonical member key 排序取得 transaction-scoped advisory locks，可由 row IDs 或 case IDs 解析成员。
    - `CallbackWorkbenchRelationRepository.acquire_relation_member_locks(...)` 与 repository adapter 等价 no-op/test implementation，保持同一 command contract。
    - 稳定幂等键 `workbench:formal-relation:{rule_version}:{relation_fingerprint}`，由现有 `app.workbench_idempotency_records` owner 预留/提交。
  </artifacts>
  <key_links>
    - `WorkbenchMatchingDirtyScopeWorker` -> `WorkbenchMatchingOrchestrator.run` -> `PostgresWorkbenchFormalRelationFactRepository.load_batch` / `WorkbenchFreeMatchingEngine.plan_relations`。
    - `WorkbenchMatchingOrchestrator._apply_plan` -> `WorkbenchWriteUnitOfWork.run` -> transaction-bound `WorkbenchRelationCommandService.confirm_relation` -> `PostgresWorkbenchRelationRepository.save_workbench_pair_relations(enqueue_refreshes=False)`。
    - `WorkbenchWriteUnitOfWork._refresh_targets_for` -> `RuntimeQueueReadModelRefreshWriter` -> existing transaction-bound `RuntimeQueueRepository.enqueue_read_model_refreshes_in_transaction`，保持 `job.read_model_dirty_scopes` / `job.outbox_events` 为 freshness 事实源。
    - manual confirm/replace/withdraw/cancel 和 automatic formalization -> `acquire_relation_member_locks` -> lock 后 reload -> command validation，避免不同入口用不同并发规则。
  </key_links>
</must_haves>

<threat_model>
  <assets>active relation membership/history, idempotency records, canonical source versions, exact withdrawal blocks, dirty scopes/outbox events, audit actor/evidence.</assets>
  <trust_boundaries>worker 从 durable dirty queue 取得 scope；repository batch进入 pure matcher；plan 从纯内存进入 transaction-bound command；UoW 写 relation/history/idempotency/queue；worker completion 只能确认对应 source version。</trust_boundaries>
  <threats>
    - 两个 worker 或人工操作同时确认/扩展/撤回重叠成员，造成双 active membership 或 lost update。
    - worker retry、lease expiry 或 transport redelivery 重复创建 relation/history/outbox。
    - plan 生成后 canonical fact、active relation 或 withdrawal history 变化，仍按 stale plan 写入。
    - outbox/dirty 写失败但 relation/history 已提交，形成 half-written state。
    - exception/write fallback 继续消费或恢复 legacy candidate/decision snapshot，隐式改变 relation。
    - audit evidence 携带 raw payload/敏感文本，或自动 origin 改变 relation mode/visibility。
  </threats>
  <mitigations>排序 transaction advisory locks；锁后 reload 和 exact fingerprint/source-version precondition；existing UoW reservation/commit idempotency；relation repository fan-out disabled inside UoW；同事务 relation/history/idempotency/dirty/outbox；lease/source-version completion guard；最小审计 metadata；architecture scan 禁止 runtime legacy imports/calls。</mitigations>
  <blocking_severity>锁失败、stale fingerprint/version、active overlap、withdraw block、idempotency conflict/in-progress/failed、relation/history/outbox 任一失败均阻断当前 plan；不得 best-effort、局部 commit、自动替换现有 case 或回到 candidate/decision path。</blocking_severity>
</threat_model>

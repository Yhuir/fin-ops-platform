<objective>
建立 Phase 21 的不可变批量事实合同与纯确定性 matcher，并先冻结所有后续 wave 共用的反例。Matcher 只返回可直接正式化的 `FormalRelationPlan`，不生成或持久化 candidate/decision；显式强引用可跨全部保留历史，复合证据窗口为 365 天，任意 N:M:K 不设业务成员数上限，但搜索状态、内存和期限有资源预算，任何弱证据、歧义、冲突、负数/红冲/退款不安全或资源耗尽都 fail closed。现有 active relation 和精确撤回指纹作为输入锚点，不被 matcher 修改或重建。
</objective>

<must_haves>
  <truths>
    - D-06：显式唯一 source reference 可跨全部保留历史；没有显式唯一引用时，复合证据候选只看 365 天窗口，amount-only、fuzzy-only、date-only 永不正式化。
    - D-07：matcher 支持任意 N:M:K 和超过 6 个成员的安全闭包，不保留旧 `max_size=6` 或其它业务规模上限；资源预算耗尽返回 `resource_limited` 且无写副作用。
    - D-08：同币种、方向相容、各 pane signed minor units 精确闭合、每个事实至少一条强证据边、证据图连通、唯一分区、无 active overlap、无精确 withdraw block 才能产生 plan；等价最优解或重叠解一律不产生 plan。
    - D-09：通用规则只处理正向正数事实；红字、退款、冲销、反向流水只有显式唯一 original-reference 边才允许进入闭包。
    - D-10：active relation 是稳定锚点；matcher 不因 source 变化自动撤回，按排序后的 `(row_type, canonical_object_identity)` 完整集合计算 withdrawal fingerprint 并阻止精确集合重建。
    - D-13：I/O 只有 focused PostgreSQL repository；matcher 对不可变 bulk batch 运行且不 import SQL、queue、HTTP、clock、logger 或 Application。
    - D-16：共享 fixture 固定 `oa-pay-2169`、`inv_imported_0369`、发票号 `26532000000716859331`、520.00，以及 13 张合计 1709.49 的 synthetic invoices，后续 projection/migration/E2E 不得另造不同反例。
  </truths>
  <artifacts>
    - `FormalRelationFact`：类型化 canonical identity、minor-unit amount、currency、direction、fact date、强引用/原始单据引用、source version 的 frozen value object。
    - `FormalRelationFactBatch`：一次 bulk read 的 facts、active relation anchors、withdrawal fingerprints、affected scopes、source versions 与 batch hash。
    - `FormalRelationPlan`：唯一安全闭包的排序成员、规则版本、证据摘要、relation fingerprint、scope keys 和幂等键输入；不含 candidate/decision 状态。
    - `FormalRelationMatchResult`：plans、ambiguity/resource-limit/unsafe 统计；只有 plans 可进入下一 wave 写链。
    - `FormalRelationSearchLimits`：max search states、max working bytes、deadline 的资源限制，不表达业务成员数上限。
    - `PostgresWorkbenchFormalRelationFactRepository.load_batch(...)`：批量读取 canonical facts、active anchors 和 audited withdrawal fingerprints 的唯一 SQL owner。
  </artifacts>
  <key_links>
    - `PostgresWorkbenchFormalRelationFactRepository.load_batch` -> `WorkbenchFreeMatchingEngine.plan_relations`，只传 frozen `FormalRelationFactBatch`。
    - `FormalRelationPlan.relation_fingerprint` 使用 sorted typed canonical identities，与 active overlap/withdrawal guard 使用同一 canonicalization function。
    - Repository 的 OA/bank/invoice 来源遵循 `docs/architecture/module-boundaries/canonical-facts.md`，不从 `read_model.workbench_*`、candidate 或 decision 表反推 canonical facts。
  </key_links>
</must_haves>

<threat_model>
  <assets>canonical OA/bank/invoice identities and amounts, pre-existing active relation membership, audited withdrawal history, matching evidence, source versions.</assets>
  <trust_boundaries>PostgreSQL rows进入 typed fact repository；raw payload/source links进入严格字段解析；纯 matcher 输出进入后续写链但本 wave 不写。</trust_boundaries>
  <threats>
    - 恶意或异常 raw payload 伪造字段、币种、方向、引用或超大候选图。
    - 金额浮点/四舍五入导致错误闭合，或 tie-break 依赖输入/哈希遍历顺序。
    - amount/fuzzy/date-only、重复发票号、红冲/退款被误当强证据。
    - 搜索空间爆炸造成 worker DoS，或预算中止后保留部分 plan。
    - row ID alias 绕过 active overlap 或 withdrawal exact-set block。
  </threats>
  <mitigations>参数化 SQL；Decimal 入口转 signed integer minor units；typed canonical identity；排序遍历与稳定 hash；强证据 allowlist；red/refund original-reference gate；connected-graph 与全局唯一分区证明；批量 query-count 断言；资源耗尽丢弃整个受影响 component 的 plan。</mitigations>
  <blocking_severity>任何 canonical identity/amount/direction 无法解析、同集合多解、active overlap、withdraw block、资源限制、source-version 不一致均为 blocking，不允许降级为 amount-only 或旧 candidate fallback。</blocking_severity>
</threat_model>

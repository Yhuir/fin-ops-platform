# Phase 31 Plan 01：外部往来款与关联台闭环一致性

## 目标

修复“确认闭环被无关页面 stale 误拒绝”的共享根因，同时保持现有 canonical relation ownership、访问时 freshness、零写后 fan-out 和双向确认/撤回合同。不得创建第二事实源、第二 read model、第二 queue 或兼容 fallback。

## 任务

1. 删除确认前整页 reload 和 whole-page freshness 写前门禁；在既有 UoW 内复用所选 Bank Detail 投影行，并锁定 canonical bank/category facts，比较 bank update、分类/确认版本和当前规则版本。
2. 在 grouped flow row 输出 opaque selection version；旧 numeric category version 暂保留为兼容 OCC，服务端不信任前端业务字段。
3. 继续通过现有 Workbench relation command 写入/撤回 `turnover_manual_closure`，验证 Turnover → Workbench 和 Workbench → Turnover 的访问时可见性，不增加写后刷新 I/O。
4. 确认按钮提交期间 disabled + `aria-busy` + “确认中…”，流水行之间增加 1px 细分割线。
5. 集中运行定向 unit/service/API/read-model/frontend/build/关键 E2E；全部通过后一次 commit/push/deploy，再用 test-owned reversible fixture 做一次生产全链与性能采样。禁止 183 项 Browser suite 和无意义 full CI。

## 验收

- 无关 Bank Detail scope stale、所选事实未变：确认成功。
- 任一所选 bank/category/rule 事实变化：409；精确证明边界不可用：503；均不产生半写。
- Confirm/withdraw 后 canonical active relation 与两个页面重新访问结果一致。
- mutation 返回无跨页 freshness/barrier target；无不相关 read-model I/O。
- 本地 lint、定向后端/前端测试、build、关键 Chromium E2E 通过。
- 生产使用正式 API 完成 confirm → 两页验证 → withdraw → 两页恢复；记录写耗时、页面访问到 fresh 耗时、queue/worker/Audit，并恢复 fixture。
- 首个候选生产发现 fresh Bank Detail v11 payload 及共享 tag read facade DTO 丢失逐行 `bank_transaction_updated_at` / `category_rule_version`，因此 grouped token 为空且 confirm 仍 409；最终候选必须以 Bank Detail schema v12 持久化并透传既有证明字段，并把 Turnover schema 升至 v11 失效已发布的 v9/v10 投影，在重新执行同一完整链路后才能通过。

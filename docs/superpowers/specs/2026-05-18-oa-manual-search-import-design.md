# OA 全量搜索与手动导入设计

## 背景

现有 `OA导入设置` 通过起始日期、表单类型和状态控制 app 侧自动导入范围。这个机制适合常规增量导入，但无法处理已经早于起始日期、却需要临时纳入 app 工作台的历史 OA。

本次需求是在设置页的 `OA导入设置` 下方新增一个独立的 OA 全量搜索与手动导入区域。它不受全局 OA 导入起始日期约束，但有自己的搜索筛选条件。用户可以搜索 OA Mongo 中的全部时间范围 OA，查看整单 OA、付款明细和附件发票识别情况，并把已选 OA 项导入 app。导入时需要连同 OA 发票附件一起进入 app。

目标不是建立一套旁路导入逻辑，而是在现有导入服务上增加一个可审计、可回滚、幂等的“手动保留 OA row_id”入口。

## 已确认口径

- 搜索框不受 `OA导入起始日期` 约束。
- 搜索框有自己的筛选条件，例如 `日常报销`、`支付申请`、`已完成`。
- 默认只允许导入已完成 OA；未完成 OA 可以显示，但不可导入，并显示禁用原因。
- 手动导入后，OA 保持源系统里的原始月份，不改写 OA 日期，不把历史 OA 挪到当前月份。
- 导入时必须复用现有 OA 导入服务和附件解析服务，不新建平行数据模型。
- 搜索结果需要显示附件数量、可导入发票数量、未识别附件数量。
- 可导入发票数量为 0 时，仍允许导入整单 OA；导入后只生成 OA 行，不凭空生成发票行。
- `oa-exp-1981` 这类旧缓存误判为 `no_evidence` 的附件，导入时必须触发定向重解析，不能继续使用陈旧缓存。
- 前端使用 MUI 原生 Table 组件族实现 data table，不使用 `@mui/x-data-grid`，不新增 `mui-datatables` 依赖。

## 用户界面设计

新增区域放在现有 `OA导入设置` 内容下方，标题建议为 `OA全量搜索导入`。

区域包含：

- 搜索框：支持按申请人、OA 编号、项目名称、申请事由、金额、日期、附件文件名等后端可索引字段搜索。
- 筛选控件：表单类型、流程状态、时间范围。表单类型至少支持 `日常报销`、`支付申请`；状态至少支持 `已完成`。
- 操作区：`搜索`、`清空`、`刷新附件解析`、`导入已选OA项`。
- 结果表：使用 MUI `Table`、`TableHead`、`TableBody`、`TableRow`、`TableCell`、`Checkbox`、`Collapse`、`TablePagination` 等原生组件。

结果表主行字段：

- 选择框。
- OA 编号。
- 申请人。
- 申请日期。
- 表单类型。
- 流程状态。
- 项目摘要。
- 整单金额。
- 附件总数。
- 可导入发票数量。
- 未识别附件数量。
- 导入状态。
- 操作：展开、刷新附件解析。

展开行显示整单 OA 的付款或报销明细：

- 明细日期。
- 金额。
- 费用内容或付款内容。
- 项目名称。
- 申请事由。
- 明细附件数量。
- 明细可识别发票数量。

选择行为：

- 支持单选、多选、全选当前页、清空选择。
- 表头显示已选 OA 数量、已选 OA 金额合计、预计可导入发票数量合计。
- 不可导入行的选择框禁用，并提供原因，例如 `流程未完成`。

## 前端约束

不使用 DataGrid。原因是这个场景不需要 DataGrid 的列状态、虚拟化和复杂选择模型，且用户已明确反馈 DataGrid 太慢。

不新增 `mui-datatables`。当前项目没有该依赖，引入第三方表格库会增加样式、类型和维护成本。这里的交互可以由 MUI 原生组件稳定实现。

前端分页使用服务端分页。后端返回当前页数据、总数和导入状态，前端只渲染当前页，避免一次性渲染大量 OA。

## 后端服务设计

新增后端能力应围绕现有服务扩展：

- `MongoOAAdapter` 负责从 OA Mongo 查询并转换为 `OAApplicationRecord`。
- `OAAttachmentInvoiceService` 继续负责附件下载、文本提取和发票解析。
- `WorkbenchQueryService.sync_oa_row_ids()` 继续负责把指定 OA row_id 同步进 app read model。
- app 层现有 retained OA payload 构建逻辑扩展为包含手动保留 row_id。

建议新增服务边界：

- `OAManualImportService`：处理搜索、导入、撤销、审计和附件刷新编排。
- `ManualImportedOARowStore` 或等价 state store 方法：持久化手动保留的 OA row_id 集合及审计记录。

核心接口：

- `GET /api/settings/oa/manual-search`：搜索全量 OA。
- `POST /api/settings/oa/manual-search/refresh-attachments`：定向刷新一个或多个 OA 的附件解析。
- `POST /api/settings/oa/manual-imports`：导入已选 OA。
- `GET /api/settings/oa/manual-imports`：查看已手动导入 OA。
- `DELETE /api/settings/oa/manual-imports/{row_id}`：撤销某个手动导入资格。

接口命名可以按现有后端路由风格调整，但职责必须保持清晰。

## 数据流

搜索：

1. 前端提交关键字、表单类型、状态、时间范围、分页参数。
2. 后端查询 OA Mongo，不应用全局 `OA导入起始日期`。
3. 后端将命中的 OA 转成搜索 DTO，附带附件解析摘要。
4. 搜索阶段默认使用当前缓存或已解析结果，不批量强制重解析，避免搜索变慢和附件服务压力过大。

刷新附件：

1. 用户点击单行 `刷新附件解析`。
2. 后端对该 OA 的附件做定向缓存失效或强制重解析。
3. 后端返回更新后的附件总数、可导入发票数量、未识别附件数量。

导入：

1. 前端提交已选 OA row_id。
2. 后端重新读取 OA，校验存在性、状态、表单类型和导入资格。
3. 后端对已选 OA 的附件强制重解析，避免使用陈旧 `no_evidence` 缓存。
4. 后端将 row_id 写入手动保留集合，记录审计日志。
5. 后端调用现有 `sync_oa_row_ids(row_ids)`，把 OA 和可识别发票附件同步进 app。
6. 后端刷新相关 read model 或触发既有失效机制。
7. 前端展示导入结果，包括成功、已存在、失败原因、发票导入数量。

撤销：

1. 用户撤销某个手动导入 OA。
2. 后端从手动保留集合移除 row_id，并记录审计。
3. 如果该 OA 没有其他关系需要保留，例如已和银行流水形成有效关系，则按当前全局导入设置从 app 视图退出。
4. 撤销不得删除 OA Mongo 源数据，也不得破坏已有审计记录。

## 附件解析与缓存治理

`oa-exp-1981` 的问题证明，附件解析缓存不能只依赖当前缓存条目存在。该 PDF 当前解析器已经可以识别出发票，但旧缓存曾把它记录为 `no_evidence`，导致 app 展示可导入发票数量为 0。

本功能采用两层治理：

- 搜索默认轻量：展示当前解析摘要，允许用户单行刷新。
- 导入强校验：导入选中 OA 前强制重解析附件，确保真正进入 app 的数据使用最新解析能力。

强制重解析应是定向的，只处理选中的 OA 附件，不清空全部附件缓存。

如果后续调整发票解析规则，应同步提升 parser version 或 cache schema version，避免旧 `no_evidence` 缓存长期污染结果。

## 数据一致性与幂等

手动导入以 OA `row_id` 为幂等键。

重复导入同一 OA：

- 不重复生成 OA 行。
- 不重复生成发票行。
- 返回 `already_imported` 或等价状态。
- 可以重新刷新附件解析摘要，但不能产生重复业务数据。

手动保留集合只保存 row_id、导入来源和审计元数据，不复制 OA 原文档。OA 内容仍以 OA Mongo 和现有 adapter 转换结果为准。

## 权限与审计

导入和撤销属于会影响 app 数据范围的操作，必须记录审计：

- 操作人。
- 操作时间。
- 操作类型：搜索、刷新附件、导入、撤销。
- row_id 列表。
- 成功、失败和已存在数量。
- 失败原因。
- 附件解析前后摘要。

如果当前系统已有权限模型，应复用设置页或数据导入相关权限。没有细粒度权限时，至少应在后端集中入口保留校验位置，避免前端按钮成为唯一限制。

## 错误处理

后端应返回结构化错误：

- `not_found`：OA row_id 不存在。
- `not_completed`：流程未完成，不能导入。
- `unsupported_form_type`：表单类型不在当前手动导入范围。
- `attachment_refresh_failed`：附件刷新失败，但 OA 本体可按规则决定是否导入。
- `partial_success`：部分 OA 导入成功，部分失败。

导入时如果附件解析失败，不应让整个批次静默成功。返回结果必须明确列出失败 OA 和失败附件。对于 OA 本体是否仍导入，按已确认口径：可导入发票数量为 0 仍可导入整单 OA，但附件解析错误要显示为未识别或失败状态。

## 验收标准

- 可以在设置页搜索早于 `OA导入起始日期` 的 OA。
- `oa-exp-1981` 陈雄兵 135 元 OA 可以在搜索结果中出现。
- `oa-exp-1981` 定向刷新或导入后，可导入发票数量应为 1，附件总数应为 2。
- `oa-exp-1947` 吴云江 282 元 OA 可以在搜索结果中出现，并展示整单多项明细。
- 未完成 OA 可以显示但不能导入。
- 选择多个已完成 OA 后，表头数量和金额合计实时更新。
- 点击 `导入已选OA项` 后，选中 OA 进入 app，且可识别发票附件同步进入 app。
- 重复点击导入不会产生重复 OA 行或重复发票行。
- 撤销手动导入后，没有其他保留关系的 OA 按当前导入设置退出 app 视图。
- 前端结果表不使用 `@mui/x-data-grid`，不新增 `mui-datatables` 依赖。

## 测试计划

后端测试：

- 搜索接口不应用全局 cutoff。
- 搜索筛选支持申请人、项目、金额、日期和表单状态。
- 未完成 OA 导入被拒绝。
- 已完成 OA 可导入并写入手动保留集合。
- 重复导入幂等。
- 导入时触发定向附件重解析。
- `oa-exp-1981` 附件解析结果从旧 `no_evidence` 场景恢复为 1 张可导入发票。
- 撤销手动导入后 read model 范围正确变化。

前端测试：

- 搜索表单渲染和筛选交互。
- MUI Table 结果渲染、分页、多选、全选和清空。
- 展开整单 OA 后显示多项付款或报销明细。
- 不可导入行禁用选择框并显示原因。
- 附件数量、可导入发票数量和未识别附件数量展示正确。
- 导入按钮状态随选择变化。
- 导入成功后刷新行状态和表头统计。

## 不在本次范围

- 不改变全局 `OA导入设置` 的含义。
- 不改写 OA Mongo 源数据。
- 不把历史 OA 移动到当前月份。
- 不引入新的表格库。
- 不重写发票解析器，只做缓存治理和导入前强制重解析。

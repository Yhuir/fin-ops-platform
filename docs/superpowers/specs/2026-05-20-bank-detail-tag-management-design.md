# 银行明细标签管理统一入口设计

## 背景

当前设置页已经有 `银行流水标签` 和 `待找发票筛选` 两个相关入口。前者实际承担银行流水/银行明细标签字典管理职责，后者承担待找发票三类筛选与标签的映射职责。

待找发票功能上线后，用户在设置页遇到 `Unknown bank transaction tag code in pending invoice group`。根因不是用户配置错误，而是标签字典与筛选映射之间的保存契约曾经不一致：筛选映射引用了自定义标签 code，但该自定义标签没有稳定进入全局标签字典。这个问题说明需要把产品边界正式收敛为一个全 app 统一标签源。

本设计将现有 `银行流水标签` 正式升级为 `银行明细标签管理`，作为全 app 唯一的银行明细标签管理入口。`待找发票筛选` 只引用这里的启用标签，不再提供快速新建标签能力。

## 目标

- 设置分类中提供正式入口 `银行明细标签管理`。
- `银行明细标签管理` 成为全 app 唯一的新建、编辑、停用银行明细标签入口。
- `待找发票筛选` 只管理业务映射，不创建标签。
- 银行明细页、待找发票页、设置页共享同一后端标签字典和版本。
- 标签更新后通过版本、事件广播和页面聚焦兜底刷新同步全 app。
- 继续保留后端强校验，防止筛选映射引用不存在、停用或重复归类的标签。

## 非目标

- 不迁移底层字段名。后端、持久化和 API 继续使用 `bank_transaction_tags` 与 `pending_invoice_tag_groups`，避免扩大迁移风险。
- 不引入第二套标签体系。
- 不做物理删除标签。历史银行明细和历史映射需要保留可解释性。
- 不重做整个设置页布局。
- 不把待找发票页面的表格实现切换到 MUI X DataGrid。涉及流水/发票/申请人的表格展示继续使用 MUI Table 或原生 table 语义组件。

## 产品边界

### 银行明细标签管理

设置分类中将现有 `银行流水标签` 改名为 `银行明细标签管理`，描述建议为 `全 app 银行明细标签字典`。

该入口负责：

- 查看系统标签和自定义标签。
- 新建自定义标签。
- 重命名自定义标签。
- 调整自定义标签路径。
- 停用标签。
- 展示标签来源和状态。

系统标签只允许查看和停用，不允许改名。自定义标签允许改名、调整路径和停用。停用不是物理删除，历史银行明细仍然能显示停用前使用过的标签。

### 待找发票筛选

`待找发票筛选` 只负责维护三类业务筛选与银行明细标签的映射：

- `需要开票`
- `流水代替发票`
- `无需开票`

该入口不允许快速新建标签。用户需要新标签时，必须先到 `银行明细标签管理` 新建并保存，再回到 `待找发票筛选` 选择。

待找发票筛选可选项只能来自 `银行明细标签管理` 中启用状态的标签。一个标签只能归入一个待找发票筛选组。

## 数据与接口

### 保持现有字段

底层字段保持：

- `bank_transaction_tags`：银行明细标签字典。
- `pending_invoice_tag_groups`：待找发票筛选映射。

这是有意保留的内部契约。UI 和文档统一使用“银行明细标签”，但内部字段暂不改名，避免影响状态持久化、银行明细页、待找发票页和既有测试。

### 标签字典

`bank_transaction_tags` 继续保存：

- `version`
- `definitions`
  - `code`
  - `label`
  - `path`
  - `source`
  - `status`

后端应继续兼容旧客户端可能发送的 `tags` 别名，但前端正式保存请求必须发送 `definitions`。

### 筛选映射

`pending_invoice_tag_groups.groups` 保存三组 `tag_codes`：

- `requires_invoice`
- `bank_statement_as_invoice`
- `no_invoice_required`

后端保存时必须校验：

- 引用标签必须存在于 `bank_transaction_tags.definitions`。
- 引用标签不能是 `archived`。
- 同一标签不能同时归入多个待找发票筛选组。

## 同步机制

同步以服务端版本为准。

- `银行明细标签管理` 保存成功后，后端递增 `bank_transaction_tags.version`。
- 前端收到保存响应后更新本页状态，并广播 `finops:bank-transaction-tags-updated`。
- 支持 `BroadcastChannel` 时同步其他 tab。
- 银行明细页收到事件后重新拉取银行明细数据和标签字典。
- 待找发票页收到事件后重新拉取列表和筛选标签。
- 另一个已打开的设置页收到事件后重新拉取设置数据。如果该设置页存在未保存更改，不能静默覆盖；应提示“银行明细标签已在其他页面更新，请刷新后再保存”并阻止保存，直到用户刷新或放弃本地修改。
- 页面重新聚焦时，如果本地版本落后，重新拉取。
- 保存前必须带上当前页面看到的 `bank_transaction_tags.version`。后端或前端保存流程必须防止基于旧版本覆盖新版本：版本不一致时返回或展示冲突提示，并要求用户刷新后重新编辑。

事件只负责通知，不能作为事实源。页面最终都以服务端返回的标签字典和版本为准。

### 实时范围

本阶段的“全 app 实时同步”定义为：

- 同一浏览器内所有已打开的 app 页面和 tab，在保存成功后通过事件和 BroadcastChannel 立即感知。
- 同一用户或不同用户在其他浏览器/设备上的页面，在下一次加载、页面聚焦、保存前版本检查或定期刷新时感知。
- 不新增 WebSocket/SSE 服务器推送通道。跨设备强实时推送不在本次范围内；本次通过服务端版本和保存冲突保护保证一致性，不允许旧页面静默覆盖新标签字典。

如果未来需要跨设备秒级推送，应单独设计 app-wide settings event stream，而不是把它塞进设置保存接口。

## UI 行为

### 设置分类

- 显示 `银行明细标签管理`。
- 不再显示 `银行流水标签`。
- 计数显示启用标签数量。

### 银行明细标签管理页

- 标题为 `银行明细标签管理`。
- 使用 MUI 原生组件。
- 展示标签名称、路径、来源、状态。
- 新建标签在该页完成。
- 自定义标签支持重命名和路径调整。
- 系统标签不允许重命名。
- 标签只能停用，不物理删除。

### 待找发票筛选页

- 移除 `新标签` 输入框和 `新建并加入` 按钮。
- 保留 `选择现有标签`。
- 空状态提示为 `请先在银行明细标签管理中新增标签。`
- 已停用或不存在的历史引用不应静默消失。如果页面拿到的映射中包含异常标签，应显示禁用/错误 chip，标注 `标签不存在` 或 `标签已停用`，并阻止保存，直到用户移除该映射或刷新到服务端最新状态。
- 当用户尝试停用一个已被待找发票筛选引用的标签时，保存必须失败并给出中文提示，要求先从 `待找发票筛选` 中移除该标签。不能自动从筛选映射中删除。

### 待找发票主页面表格

- 待找发票页面中流水、发票、OA 申请人等表格化信息继续使用 MUI Table 或原生 table 语义组件实现。
- 不引入 `@mui/x-data-grid` 或 MUI X DataGrid。
- 本任务只调整标签字典和筛选映射来源，不重做待找发票页面的信息架构。

## 错误处理

后端保留结构化错误码：

- `unknown_bank_transaction_tag`
- `archived_bank_transaction_tag`
- `duplicate_pending_invoice_tag_mapping`
- `bank_transaction_tag_in_use_by_pending_invoice_filter`
- `bank_transaction_tags_version_conflict`
- `category_version_conflict`
- `invalid_category_code`
- `archived_category_code`

前端不应直接展示后端 `message` 中的英文内部错误。设置保存、银行明细标签选择、待找发票筛选保存都必须优先读取 API 响应中的 `error` 字段，并用稳定映射表转成中文可操作提示。只有未知错误码才回退到后端 `message` 或通用错误。

设置保存错误映射：

- `unknown_bank_transaction_tag` -> `待找发票筛选引用了不存在的银行明细标签，请刷新后重新选择。`
- `archived_bank_transaction_tag` -> `该银行明细标签已停用，不能用于新的待找发票筛选。`
- `duplicate_pending_invoice_tag_mapping` -> `同一个银行明细标签不能同时归入多个待找发票筛选。`
- `bank_transaction_tag_in_use_by_pending_invoice_filter` -> `该银行明细标签仍被待找发票筛选使用，请先从待找发票筛选中移除。`
- `bank_transaction_tags_version_conflict` -> `银行明细标签已被其他页面更新，请刷新后重新保存。`

银行明细页标签选择错误映射：

- `invalid_category_code` -> `该银行明细标签不存在，请刷新后重新选择。`
- `archived_category_code` -> `该银行明细标签已停用，不能再用于新的银行明细。`
- `category_version_conflict` -> `银行明细标签已更新，请刷新后重新保存。`

## 权限、审计与一致性

- 标签管理继续走现有设置保存接口和权限控制。
- 只读用户不能保存。
- 保存成功应记录标签字典和待找发票映射的审计事件。
- 保存失败不能部分提交。
- 后端归一化、校验、版本递增和 finalizer 调用必须保持原子语义。
- 如果停用标签会导致现有待找发票筛选映射失效，本次保存必须整体失败。用户需要先移除映射，再停用标签。

## 验收标准

- 设置分类中显示 `银行明细标签管理`，不再出现 `银行流水标签`。
- 只能在 `银行明细标签管理` 中新建标签。
- `待找发票筛选` 不能新建标签，只能选择已有启用标签。
- 新建银行明细标签并保存后，待找发票筛选可选择该标签。
- 银行明细页标签选择可同步看到新增标签。
- 停用标签后不能再被新加入待找发票筛选。
- 尝试停用仍被待找发票筛选引用的标签时，保存失败并提示先移除映射。
- 另一个打开的设置页能收到标签更新事件；有未保存更改时不被静默覆盖。
- 基于旧标签版本保存时被阻止，不能覆盖新版本。
- 后端继续拒绝未知标签、停用标签和重复归类。
- 前端错误提示为中文可操作提示，不暴露英文内部错误。
- 待找发票主页面仍使用 MUI Table/native table 语义组件展示表格信息，未引入 DataGrid。
- 相关测试覆盖设置页、保存 payload、后端校验、待找发票筛选 UI 和同步入口。

## 实施分解

建议拆成三个独立任务：

1. 设置页标签入口和待找发票筛选 UI 边界。
2. 前后端保存契约、错误映射和后端校验回归。
3. 银行明细页/待找发票页同步验证与测试覆盖。

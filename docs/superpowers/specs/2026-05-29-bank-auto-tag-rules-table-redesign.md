# 银行明细自动标签规则表格化与候选确认设计

## 背景

银行明细页面已有 `自动标签规则` 入口，当前实现是右侧 60% 宽度抽屉中的卡片式规则编辑器。用户希望把该功能重构为类似 `银行流水标签ui2.numbers` 的表格形式，并且不是临时 UI 调整，而是生产级整合方案。

本次需求同时改变规则口径：现有 app 内普通自动标签规则要由文件中的规则集替换；用户后续仍可在系统中维护这些规则。规则命中也不再简单地把同级普通规则按顺序取第一条，而是需要支持多规则命中候选，由用户在银行明细行内从候选标签中确认。

## 目标

- 将银行明细页 `自动标签规则` 抽屉改为加宽的表格型规则工作区。
- 将 `银行流水标签ui2.numbers` 中的规则作为目标规则集写入系统。
- 迁移时复用同主/子标签的旧 `code`，但规则条件完全按文件覆盖。
- 文件中不存在的旧规则进入停用区，保留 code 和审计痕迹，不参与自动命中。
- `内部往来款` 保留现有系统特殊规则，固定第一优先级，不进入普通文本规则迁移。
- 普通规则同级并行评估：0 命中、1 命中、多命中分别有明确状态。
- 多命中时银行明细页显示待确认，并只允许用户从实际命中的候选标签中选择。
- 用户确认结果保存为结构化人工确认事实，优先于自动规则，规则变化不静默覆盖。
- 历史银行流水按新规则后台全量重算，但不在保存请求中同步扫库。
- 将 read model 作为一致性边界；Redis 和 RabbitMQ 只能作为既有缓存/队列实现，不作为业务事实源。

## 不做

- 不引入 `OA中的类型` 字段或下游 OA/成本映射。
- 不恢复旧的“全部标签任意人工分类”下拉。
- 不允许用户编辑或停用 `内部往来款` 系统规则。
- 不新增平行规则表来替代 `bank_transaction_tags`。
- 不在规则保存或迁移 API 的请求线程内全量扫描历史流水。
- 不为了本功能新增 Kafka、Celery、Elastic 等第三方性能服务。
- 不把 Redis 用作规则、候选或人工确认事实源。

## 文件规则来源

候选源文件：

- `/Users/yu/Desktop/sy/财务运营平台/银行明细标签/银行流水标签ui2.numbers`
- `/Users/yu/Desktop/sy/财务运营平台/银行明细标签/银行流水标签ui.xlsx`

当前机器比对结果：

- 除表头命名和 `OA中的类型` 列外，规则内容一致。
- `ui2.numbers` 导出后表头为 `流水类型 / 主标签 / 子标签 / 选择查询的项（可全选/清空） / 包含 / 必须同时包含 / 精准命重 / 不包含字样 / 优先级`，并去掉 `OA中的类型` 内容。

实现必须提供可重复的解析/校验过程：

- 将 `.numbers` 导出为临时 `.xlsx` 或由等价解析流程读取。
- 与 `银行流水标签ui.xlsx` 做机器比对。
- 忽略已确认不做的 `OA中的类型` 差异。
- 如果规则内容差异超出已确认范围，迁移必须失败并输出差异报告，不能静默选择任一文件。
- 服务端运行时不得依赖 Apple Numbers、GUI 自动化或本机桌面应用。实际迁移应消费导出的 `.xlsx`、仓库 fixture 或规范化 JSON；`.numbers` 转换只允许作为本地预处理/校验步骤。
- 文件中的 `精准命重` 视为原始文件错字，解析器必须把 `精准命重` 和 `精准命中` 都识别为精确命中列；系统 UI、API 文档和测试统一展示规范文案 `精准命中`。

## 规则语义

### 内部往来款

`内部往来款` 保留现有系统特殊规则：

- 固定第一行展示。
- 固定第一优先级。
- 灰色只读。
- 不可编辑、不可停用、不可排序。
- 命中后直接输出 `内部往来款`，不进入普通候选。
- 继续使用现有跨流水确定性配对逻辑，不靠单条文本猜测。

文件中的 `内部往来款` 行只作为展示说明，不写入普通文本规则。

### 普通文件规则

文件中除 `内部往来款` 外的规则均为普通规则：

- 优先级值为 `2` 的规则表示“同级候选匹配”。
- 普通规则并行评估，不再以文件行顺序作为唯一先命中先返回规则。
- 文件行顺序仍作为表格展示顺序和稳定保存顺序。

评估结果：

| 命中数量 | 状态 | 最终标签 |
| --- | --- | --- |
| 0 | `unmatched` | 无，页面显示 `-` |
| 1 | `auto_matched` | 自动命中的单个标签 |
| 多个 | `needs_confirmation` | 暂无最终标签，页面显示待确认并返回候选 |

### 人工确认

多命中时，用户只能从该流水实际命中的候选标签中选择。

确认后：

- 保存为该流水的人工确认标签。
- 写审计。
- 触发银行明细和下游 read model dirty。
- `manual_confirmed_category_code` 优先于自动规则结果。
- 后续规则变化只更新自动候选，不静默覆盖人工确认。
- 用户可以撤销确认；撤销后回到当前自动规则评估状态。

## 文件字段映射

文件中的 `选择查询的项` 固定映射到后端语义字段：

| 文件文案 | 后端语义字段 |
| --- | --- |
| `用途/交易用途、摘要、备注/附言/客户附言` | `purpose_text`, `summary_text`, `note_text`, `detail_text` |
| `对方户` | `counterparty_name` |

未知字段描述必须校验失败。

词条字段映射：

| 文件列 | 后端字段 |
| --- | --- |
| `包含` | `rules.contains_any` |
| `必须同时包含` | `rules.contains_all` |
| `精准命重` / `精准命中` | `rules.exact_any` |
| `不包含字样` | `rules.none_of` |

词条按换行和常见分隔符拆分，去首尾空格、去重，空项忽略。实现需要小心处理中文顿号、逗号和换行混用的单元格。

## 规则迁移策略

迁移以文件规则为准：

1. 解析文件规则。
2. 校验主标签、子标签、字段映射、词条条件和重复主/子标签组合。
3. 查询当前 `bank_transaction_tags`。
4. 对同主标签 + 同子标签的规则复用旧 `code`。
5. 对文件新增规则生成后端稳定 `custom_...` code。
6. 文件中不存在的旧普通规则进入 `archived_rules`，保留 code 和审计痕迹。
7. 写入完整规则集，递增版本，写审计。
8. 发布 `bank_auto_tag_rules_changed`，scope 为 `all`。
9. 后台刷新历史银行明细 read model。

停用旧规则时，如果旧 code 被待找发票规则或免 OA 准入引用，本次显式规则集替换可以同步清理这些引用，并写入同一审计链。不得静默留下下游引用已停用 code 的不一致状态。

## 后端模型与 API

继续以 `bank_transaction_tags` 作为唯一规则事实源，不新增平行规则表。

人工确认必须是独立、持久、可审计的事实源，不能只写入 read model 或临时 payload。PostgreSQL primary 运行时新增 app schema 事实表，例如 `app.bank_transaction_category_confirmations`：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键。 |
| `tenant_id` | 租户，默认 `default`。 |
| `bank_transaction_id` | 指向银行流水的事实 ID；如果迁移期仍有 legacy ID，必须保留可解析引用。 |
| `legacy_transaction_id` | 兼容旧 snapshot/legacy ID。 |
| `category_code` | 用户确认的标签 code。 |
| `candidate_category_codes` | 确认当时可选候选 code 列表。 |
| `rule_version` | 确认时使用的自动标签规则版本。 |
| `status` | `active` 或 `revoked`。同一流水只能有一条 active 确认。 |
| `confirmed_by` / `confirmed_at` | 确认操作者和时间。 |
| `revoked_by` / `revoked_at` | 撤销操作者和时间。 |
| `version` | 乐观锁或事件版本。 |
| `raw_payload` | 审计补充信息。 |

实现应提供对应 PostgreSQL repository 和迁移文件，版本号使用当前最大迁移号之后的下一个编号。非 PostgreSQL/legacy snapshot 运行时也必须有等价的 `bank_transaction_category_confirmations` snapshot 存储，保证本地测试和回滚观察期不丢失人工确认事实。

Read model 只投影人工确认结果，不是人工确认事实源。

需要扩展银行明细分类结果模型或 read model 投影：

| 字段 | 说明 |
| --- | --- |
| `auto_category_code` | 自动规则单命中结果。多命中时为空。 |
| `auto_candidate_category_codes` | 多命中候选 code 列表。0/1 命中可为空数组。 |
| `manual_confirmed_category_code` | 用户从候选中确认的标签 code。 |
| `effective_category_code` | 最终对页面和下游生效的标签 code。 |
| `category_resolution_status` | `unmatched`, `auto_matched`, `needs_confirmation`, `manually_confirmed`。 |
| `category_rule_version` | 生成当前自动候选结果时使用的规则版本。 |

最终标签优先级：

```text
manual_confirmed > internal_transfer > single_auto_match > null
```

### 交易列表 API

`GET /api/bank-details/transactions` 增加候选和状态字段，前端据此展示 `- / 自动标签 / 待确认 / 已确认`。

候选字段必须使用 stable code，同时提供当前主/子标签展示字段，避免前端自行猜 label。

### 确认 API

新增接口，例如：

```text
POST /api/bank-details/transactions/{transaction_id}/category-confirmation
```

请求：

```json
{
  "category_code": "custom_xxx"
}
```

后端要求：

- 用户有写权限。
- 目标流水存在且未删除。
- `category_code` 必须属于该流水基于最新规则版本实时重算得到的候选列表。确认接口不得只信任可能 stale 的 read model 候选。
- 如果无法读取目标流水事实或无法用最新规则重算候选，返回可恢复错误并要求刷新；不能基于旧投影写确认。
- 成功后保存人工确认事实，写审计，标记 dirty。
- 返回更新后的行分类状态或足够前端刷新该行的数据。

### 撤销 API

新增接口，例如：

```text
DELETE /api/bank-details/transactions/{transaction_id}/category-confirmation
```

后端要求：

- 用户有写权限。
- 目标流水存在且有人工确认事实。
- 删除或置空人工确认事实。
- 写审计，标记 dirty。
- 撤销后回到当前自动评估结果。

确认和撤销都必须处理并发：

- 如果客户端携带 `rule_version` 或行版本，后端发现与最新规则版本不一致时应重算候选；如果所选 code 仍在最新候选中，可以接受并记录最新版本；否则返回 409 或 400，提示用户刷新候选。
- 测试必须覆盖“read model stale 但确认接口使用最新规则重算”的场景。

### 自动标签规则 API

`GET/PUT /api/bank-details/auto-tag-rules` 保持现有契约，但保存后的评估引擎支持多候选。

保存仍提交：

- `expected_version`
- 完整 `active_rules`
- 完整 `archived_rules`

后端继续做最终校验、权限、乐观锁、审计和 dirty 事件发布。

## Read model、队列与缓存

Read model 是一致性边界。

银行明细 read model 需要投影候选列表、人工确认、最终标签、状态和规则版本。API 热路径优先读取 read model，不在请求中临时全量计算。

规则变更、文件迁移、人工确认和撤销确认都必须标记 dirty：

- 规则变更和文件迁移：scope 为 `all`，按既有能力可拆为月份 dirty scopes。
- 人工确认和撤销：至少标记该流水所属月份和相关下游 scope。

刷新期间：

- API 继续返回最后一版可用投影。
- 返回 `read_model_status=refreshing/stale/schema_mismatch` 等状态。
- 前端提示后台刷新中，但不清空账户和流水列表。
- 确认 API 例外：为了保证只能从当前候选确认，它必须针对单条流水读取事实并用最新规则重算候选，不能使用 stale read model 作为最终校验依据。

RabbitMQ：

- 如果生产环境已有 RabbitMQ-compatible runtime，则通过现有 queue/lifecycle 抽象发布刷新任务。
- 本地和测试环境可以继续 in-process。
- 业务代码不得直接依赖 RabbitMQ API。

Redis：

- 不得保存规则事实、候选事实或人工确认事实。
- 如已有 Redis page cache，可作为 read model 版本之后的短 TTL 查询缓存。
- 规则版本或人工确认变化后必须失效相关缓存。

## 前端 UI

入口仍为银行明细页右上角 `自动标签规则`。

抽屉：

- 仍从右侧打开。
- 桌面端加宽为接近全宽规则工作区，例如 `min(1280px, 92vw)` 或等价响应式宽度。
- 移动端全宽。
- 主要列在常规桌面下不需要左右滑动即可看到。
- 表头 sticky。
- 内容区纵向滚动。
- 底部固定保存栏。

表格列：

- `流水类型`
- `主标签`
- `子标签`
- `选择查询的项`
- `包含`
- `必须同时包含`
- `精准命中`
- `不包含字样`
- `优先级`
- `操作`

不展示 `OA中的类型`。

词条单元格：

- 3-5 项以内直接显示。
- 超过阈值显示前几项和 `共 N 项`。
- 点击单元格打开大编辑器。
- 大编辑器按一行一个词条维护。

表格操作：

- 主标签/子标签可编辑。
- 查询项用语义字段多选控件，显示文件友好文案。
- 可新增普通规则。
- 可停用普通规则。
- 可恢复停用规则。
- 可用/停用用同一抽屉内 tab 或 toggle 切换。
- 只读权限下禁用编辑和保存。

银行明细主表：

- `unmatched`：类型列显示 `-`。
- `auto_matched`：显示自动标签。
- `needs_confirmation`：显示 `待确认`，点击后只展示候选标签。
- `manually_confirmed`：显示人工确认标签和确认标识，允许重新选择候选或撤销确认。
- 不提供全部标签任意选择。

## 权限与审计

权限：

- 规则迁移/保存需要现有自动标签规则保存权限。
- 单条候选确认和撤销需要银行明细写权限或等价规则保存权限，具体实现应复用现有权限模型。
- 只读/导出用户只能查看规则和候选，不能保存、确认或撤销。

规则迁移审计：

- 来源文件名。
- 文件摘要哈希。
- 旧版本、新版本。
- 复用 code 列表。
- 新增 code 列表。
- 停用旧 code 列表。
- 同步清理的下游引用。
- 字段映射版本。

单条确认审计：

- 流水 ID。
- 规则版本。
- 当时候选 codes。
- 选择 code。
- 操作者。
- 时间。

撤销确认也必须写审计。

## 下游一致性

下游继续使用 `effective_category_code` 或现有等价分类字段作为消费入口。

- 免 OA、待找发票、关联台、搜索、导出继续按 stable code 解析当前主/子标签。
- 多候选未确认时不能被下游当成已分类标签消费，应表现为未分类或待确认。
- 人工确认后，下游消费确认后的最终标签。
- 文件外旧规则停用后不再自动命中。

## 验收标准

- 打开 `自动标签规则` 后，常规桌面下不需要左右滑动即可看到主要规则列。
- 表格结构与 `ui2.numbers` 的目标列一致。
- 当前 app 内普通规则被文件规则替换。
- 同主/子标签旧规则复用 code。
- 文件外旧规则停用。
- `内部往来款` 保持系统特殊规则，固定第一。
- 多规则命中不会随便取第一条，而是进入候选确认。
- 用户只能从候选标签中确认。
- 人工确认可审计、可撤销、不会被规则重算静默覆盖。

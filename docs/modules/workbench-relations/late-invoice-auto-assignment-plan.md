# 后到发票自动归属实施计划

日期：2026-09-20。状态：已实施并进入发布验证；实现与本地验证记录见 implementation-notes.md，生产实测随发布交付。

本计划补充当前模块合同，不把以下目标行为描述成已上线事实。执行不使用 GSD。模块入口见 [README](README.md)、[边界](boundary-io.md)；关联台现状见 [状态机](../reconciliation-workbench/state-machine.md)。

## 1. 目标与必要取舍

OA 子付款项未识别出正式发票，发票后续人工导入时，系统自动处理有依据的正式关系与明细归属，随后统一计算金额、资料异常、分区和同行展示。反向到达、补充凭证共存、跨月补导、历史遗漏、人工纠正均纳入闭环。

- 不增加审批步骤、评分平台、通用规则引擎、第二队列、第二 worker、页面 read model 或缓存。
- 复用已有正式关系 command/UoW、发票 source links、来源 CAS、审计、matching dirty scopes、任务状态和归属抽屉。
- 仅保留正确性必需条件：身份与方向合法、归属不冲突、候选唯一、提交时事实仍有效、重复执行幂等。明确证据可以建立金额不相等的归属，差额仍交由金额规则显示；金额推断要求精确到分。
- 不承诺所有发票都能自动判断。跨组缺少业务依据、多个等价目标或任意凑数不能自动认定；明确提供现有发票选择和归属纠正入口。
- 不承诺其他页面数据完全不变：正确新增关系可能正常改变待找发票、发票使用情况等结果；必须保证金额事实、API 合同、权限和各页面业务规则不被污染。

## 2. 已核实的代码事实

后端文件下文均相对 `backend/src/fin_ops_platform/services/`。

1. `confirmed_invoice_import_uow.py` 已在导入事务内按本批强身份补充 OA 附件来源，并登记 matching scope；当前导入请求 `debounce_seconds=60`。
2. `workbench_matching_dirty_scope_worker.py` 默认 poll 为 5 秒。实际生产 env 必须在性能验证时只读核实，不以默认值冒充生产值。
3. `postgres_repositories/workbench_matching_queue.py` 已支持 debounce=0 的 expedite、scope 去重及 processing 期间再次变更标记，无需另做即时队列。
4. `workbench_matching_orchestrator.py` 只在 formal plans 或 ETC enrichment 非空时进入写事务；明细归属计划必须独立成为有效写入原因。
5. `workbench_free_matching_engine.py` 的事实是父 OA、流水和发票；子付款项不能提升成正式 relation member。现有完整三栏关系的拓扑保护应保留，不能拿它阻止组内归属补齐。
6. `workbench_invoice_expense_item_assignment_service.py` 已有同组归属、事务锁、source-link CAS 和审计，但人工命令要求异常 fingerprint，且拒绝已有不同归属。自动调用不能伪造人工异常请求；人工纠正也需要明确的更改语义。
7. `invoice_expense_item_links.py` 已支持 `entry_method`，保留其他 provenance 后写入 `oa_expense_item_invoice`；可区分自动与人工来源，不需要新关系表。
8. `workbench_amount_check_service.py` 已按有效 source item IDs 判定归属，补充凭证现在与同项已归属发票合计核对（以当前 boundary-io.md 为准）。优先沿用并补回归，不预设重写金额规则。
9. `workbench_oa_supporting_document_service.py` 的删除路径目前仅删除凭证事实与对象，没有独立的发票归属补齐步骤。
10. 现有 App Health 已暴露 matching scopes/running/error 状态。应复用状态 owner，不恢复页面 freshness 队列。

## 3. 自动规则：明确顺序、有限计算

### A. 明确来源

准确票号与当前 OA 附件 owner、已登记业务引用、用户明确选择均优先。沿用现有来源识别与 alias 规则，不因先后顺序或补充凭证存在而排除。不同 OA 的冲突不得被金额推断覆盖。

### B. 同一 active relation 内补齐归属

1. 从完整 canonical 组读取子付款项、正式发票和有效归属，不能按前端分页/筛选结果计算。
2. 固定已有有效人工归属与明确来源；识别已被正式发票覆盖的明细。补充凭证不算正式发票覆盖。
3. 对其余普通正数进项发票与完整未覆盖明细，以币种、业务方向和价税合计/明细金额建立精确金额桶。
4. 仅提交双向唯一的一对一结果；同额多目标不按日期、ID、顺序打破平局。已知业务事实矛盾则不提交，不要求所有记录都填项目、对方税号等可选字段。
5. 在唯一一对一结果后，若只剩一个完整未覆盖明细，且同组全部剩余未归属普通发票合计恰好等于该明细，可将这些票共同归属该明细。不得从剩余票池任意挑子集凑数。
6. 一票多明细仅在明确来源或人工选择下保留现有能力；不增加多对多金额组合搜索。
7. 已有部分正式发票覆盖但金额仍不足的明细，不自动按差额分摊；走明确来源或人工选择，归属与金额异常分别展示。

本规则承认同组唯一金额匹配是一项业务推断，不伪装成 OA 附件解析。先构建整个候选集合再判断唯一性，不能逐票贪心提交。

### C. 尚未处于同组

先复用现有正式匹配引擎的明确引用、业务证据、唯一性和精确金额规则确定新关系/扩展关系，再对拟提交的组执行 B。已有三栏组接收新发票仍须现有明确关系依据；不能因同额就吞入其他组的票。

员工报销不要求员工姓名等于发票销方。购方公司税号只能作为一致性检查，不能单独充当归属证据。无法建立关系的票继续保留未关联状态，用户可复用现有关联流程，再由 B 自动归属。

### D. 重新检查与人工纠正

- 对没有 OA 附件来源的发票，自动流程不覆盖有效人工指定。OA 附件来源按 2026-09-20 来源接管合同优先：替换竞争的人工来源/归属边，并通过正式关系 UoW 原子迁移错误分组；来源历史保留在导入批次与审计中。
- 自动归属的 OA/item 被删除或产生明确冲突时，按受影响对象检查并呈现待处理，不悄悄跳到另一个 OA。
- “更改归属”模式仅供没有 OA 附件来源的发票：同 relation 内明确替换目标，保留 before/after 审计，以当前 source links CAS。OA 附件发票不显示此操作，服务端也拒绝人工改归属。
- 正式关系撤回继续复用现有撤回阻止语义。此次不新增“清空归属后仍参与自动匹配”的含糊按钮；跨组改错使用正式撤回/重新关联流程。
- 后来仅新增一个弱同额候选，不推翻已经提交的有效归属。明确矛盾必须呈现，不把重新计算做成持续抢占。

## 4. 模块边界与 I/O

| Owner | 输入 | 输出与责任 | 禁止事项 |
| --- | --- | --- | --- |
| 导入 / OA / 凭证 writer | 当前动作的 canonical IDs、来源变化 | 提交自己的事实；在相同 PG 事务登记受影响 matching scope | 不自行建立金额归属算法，不在 HTTP 中 OCR 或运行全量匹配 |
| Formal fact repository | scope、已发现的关系/对象 IDs | 批量读取 relation 全成员、明细、来源；明确 identity 的跨月扩展 | 不返回 UI DTO，不逐票查询，不从分页切片判断唯一性 |
| 归属纯函数 | 明确的组、明细、发票、已有来源 | 拟归属及原因、歧义/冲突原因 | 无 DB/HTTP/队列 I/O；不造字段、不泛化评分 |
| Matching orchestrator | durable scope、canonical facts | 正式关系计划 + 明细归属计划；调用同一 UoW | 不依赖 Application，不借修复脚本写生产事实 |
| 关系与归属 command/UoW | 明确计划、actor、现有版本与来源快照 | 锁内重验；原子提交 relation/source links/history/audit | 不手写旁路 SQL，不先建关系后单独补归属 |
| 关联台 query / 前端 | 已提交事实与现有任务状态 | 分区、异常、同行展示、人工选择/纠正 | GET 不建立关系；前端不本地猜 owner、不写其他页面 DTO |

纯归属规则放入一个小的专用模块，建议名 `workbench_invoice_expense_item_matching.py`。只服务该业务；不增加 factory/adapter/plugin 层。人工与自动命令共用锁后来源写入逻辑，但入口校验保持各自责任。

持久化复用 `app.invoices.source_links`；新增自动 `entry_method` 值作为本次明确合同，并记录匹配依据到已有审计结果。关系 member 仍是父 OA、流水、发票，不写子项 member。原则上无新增业务表；确有缺失的查询索引须以查询计划证明后添加。

## 5. 实施顺序与完成条件

### 步骤 1：固定业务样例与影响范围

- 用合成数据构造 34+351+52 OA、437 流水、七张票的关系，覆盖有/无补充凭证，不把生产个人资料放入 fixture。
- 扫描调用方及 source links 消费者；读取直接模块和待找发票、进项使用、成本、银行明细、OA 待付款、税金、ETC、销项、权限审计的 boundary-io。
- 先执行目标现有测试并记录现有失败；将本计划规则转成测试。不得通过跳过原失败宣布通过。
- 完成条件：正例、歧义、跨组、纠正与下游预期均有明确断言。

### 步骤 2：纯规则与批量事实读取

- 扩展 `postgres_repositories/workbench_formal_relation.py` 的窄批量读取，保留现有父 OA matcher 输入合同，单独提供归属规则所需明细。
- 实现 A/B/C 的有限步骤；输出类型明确且可测试。金额统一使用现有 Decimal/分值语义。
- 按真实单据日期与已知 relation/source identity 扩展跨月读取，不按导入发生月份截断；明确来源跨月按 ID 查询。无明确来源的跨组匹配沿用现有业务时间窗口，并显示窗口限制，不宣称覆盖任意历史弱匹配。
- 候选资源超限输出“本次未自动判断”，不得截断后宣称唯一。
- 完成条件：输入顺序无关；重复运行相同结果；候选数量增长不会引发逐行 SQL 或无限组合计算。

### 步骤 3：统一提交与人工纠正

- 从 `workbench_invoice_expense_item_assignment_service.py` 提取最小共享的锁后写入能力；自动入口不要求前端异常 fingerprint。
- 扩展 `workbench_matching_orchestrator.py` 的命令与结果，允许仅有明细归属计划时写入；原关系拓扑不变则不增加 relation version、不发布无关 OA 支付状态事件。
- 对新关系/扩展关系与其归属使用同一关系 UoW。锁后读取并重验所依赖的整个候选集合及占用，不能仅锁胜出发票而遗漏竞争者；复用现有并发控制，必要的候选集合锁保持 scope 有界。
- 复用 `invoice_expense_item_links.py` 和 source-link CAS，保留人工导入、OA 附件及其他来源。关联拓扑未变时只写来源和审计。
- 新增人工更改模式，默认读取现有目标，显式提交新目标；旧指纹、只读账户、跨组目标均明确报错。
- 完成条件：冲突零覆盖；单组 relation/归属无半写；重试零重复；一个冲突不能永久阻塞其他独立组，按现有任务边界记录失败并继续独立可提交单元。

### 步骤 4：触发、时延与补充凭证

- `confirmed_invoice_import_uow.py` 的相关匹配登记使用现有 debounce=0 expedite；持续导入不得不断后移执行时间。
- OA 事实真实变化、正式关系确认/更改、人工归属纠正登记受影响 scope；自动提交不反向重复登记自己，避免循环。
- 凭证新增/删除通过自己的 PG repository 事务登记相关 scope，不让文件存储 owner 写关系。保留现有对象存储失败处理；PG 提交后匹配任务不能丢失。
- 复用 matching worker 的 processing 再变更标记与 lease/retry，核实和调整该实例的实际 poll（以 1 秒为优化目标，不影响其他 worker）。
- 人工/来源已有有效归属时，删除凭证后的 normal GET 可直接正确计算，不等后台才承认已存在事实。
- 复用现有状态 owner 输出处理中/错误与匹配结果；一次运行完成后回读业务页。状态轮询期间不轮询整个 workbench 列表，不打断用户打开的抽屉或选择。
- 完成条件：新事实提交必有可恢复任务；并发到达不漏处理；失败不伪装成功；无永久等待状态。

### 步骤 5：页面闭环

- 在现有发票归属抽屉和明细缺票入口中支持“选择已有发票”；已在同组时复用归属命令，尚未同组时通过现有正式关联流程，不从前端直接改归属字段。
- 发票维持“人工导入”真实来源，另显示“明细归属”；自动来源原因在详情/审计中可查看，不增加一组抢占主表的状态标签。
- 未找到、歧义、冲突、处理失败分别给出可操作说明；金额推断失败时不退回按名称/日期模糊自动绑定。
- 普通 API 只增加必要可选信息，不移除旧响应字段；下游页面继续消费原 canonical facts/active relations。
- 完成条件：34 元场景自动同行；删除凭证后不丢有效归属；人工可纠正；只读用户仅查看；查询与任务失败均有反馈。

### 步骤 6：历史处理与旧代码清理

- 使用同一规则和提交入口，按未归属发票/未覆盖明细分批检查历史 active relations，包括已经显示 paired 的关系；不只扫描未配对区。
- 对尚未关联的历史发票复用正式 matcher；无来源则遵守现有窗口，不能全库金额碰撞。运行前输出有界检查报告，明确预计新增关系与仅补来源的数量。
- 历史批次可重入、可中止、可重试，完成后复跑应零新增。不得通过修改 rule version 无控制地触发所有历史 scope 重放。
- 不新增 34 元硬编码、临时 SQL 修票分支或线上开机自动修复。
- 完成条件：历史和未来导入使用相同规则；旧入口引用清零；失败项及原因可追踪。

## 7. 性能目标与测量

以下是待验证目标，不是已测结果；在固定测试环境和数据规模下报告 p50/p95、SQL 次数、查询计划、候选数量、提交时间与队列等待。

- 常规单组归属数据库读取为批量查询；每组不随发票数产生 N+1 查询。金额桶构建接近 O(n)，排序最多 O(n log n)，不增加指数级子集枚举。
- 代表性单组（不超过 100 个明细和 200 张发票）计算与提交 p95 目标不超过 500ms；大组按资源边界报告，不冒充小组指标。
- 无积压常规补导，从 canonical 导入提交到自动归属完成 p95 目标不超过 5 秒；分别记录导入时间、queue 等待、matching 执行、页面回读，不能隐藏 60 秒等待。
- 100/1,000 张导入场景分别测量；一万条历史事实测试集合查询与分批吞吐，不用单组小样证明批量性能。
- 工作台 GET 仍为纯读，不新增匹配/OCR/写入。相同数据量下目标 p95 退化不超过 10%，同时报告绝对耗时。
- 先使用现有索引、source-link 索引与批量接口；仅有 `EXPLAIN (ANALYZE, BUFFERS)` 证据时增加必要索引，不加缓存掩盖问题。

# 发票与支付状态规则设置 UI Spec

> 本文是 `进项发票使用情况` 页面右侧抽屉的小范围 UI 合同。它只约束“发票与支付状态规则设置”抽屉，不改变 OA/流水/发票关系事实源，也不替代 `state-machine.md`、`tests.md` 或 API 契约。

## GSD 上下文

- Goal：让财务用户理解并维护“已有 OA/流水/发票关系如何映射为支付状态”。
- Scope：`PaymentStatusRulesDrawer`、对应规则读取/保存 API、保存后的当前页 direct refetch 反馈。
- Design tone：浅色企业后台、信息密度高、低装饰、可扫读、可追溯。
- Non-goal：本抽屉不负责发现、补全或修正 OA/流水关联；关系事实仍来自 `workbench_relation` distribution 和进项使用 direct query boundary。

## 业务定位

右侧抽屉的作用是维护支付状态解释规则：

```text
已确认关系事实 + 规则优先级 -> paymentStatus
```

示例：

| 发票事实 | 关系事实 | 命中规则 | 列表支付状态 |
| --- | --- | --- | --- |
| 发票 100.00 | 陈秀云 OA 100.00 + 支出流水 100.00，linked，完全匹配 | 陈秀云 OA + 流水 + 完全匹配 | 现金往来 |
| 发票 300.00 | 普通 OA 300.00 + 支出流水 300.00，linked，完全匹配 | 有 OA + 有流水 + 完全匹配 | 已付款 |
| 发票 500.00 | 周洁莹 OA 500.00，无流水，linked，发票/OA 金额匹配 | 周洁莹 OA + 无流水 + 金额匹配 | 冲 |
| 发票 800.00 | 无 linked OA、无 linked 流水 | 默认兜底 | 待处理 |

`candidate` 关系只能作为证据展示，不能参与“已付款”“冲”“现金往来”等自动闭环状态判断。

## 信息架构

抽屉宽度：`min(880px, 100vw)`。

### 1. 顶部摘要

必须显示：

- 标题：`发票与支付状态规则设置`
- 状态标签：`可编辑` / `只读` / `无保存权限`
- 生效提示：`保存后重新读取进项发票使用情况`

不得显示：

- 版本号
- settings key
- source version field
- 任何后端内部字段名

实现约束：前端可以在内存中保留 `version` 并随保存请求提交 `expectedVersion`，用于后端冲突校验；但 UI 不展示版本号。

### 2. 影响预览

第一阶段可以是只读摘要；如果后端暂未提供 preview API，则展示当前规则命中统计为空状态，不伪造数据。

推荐字段：

| 指标 | 说明 |
| --- | --- |
| 已付款 | 当前规则下命中 `paid` 的发票数 |
| 待付款 | 当前规则下命中 `waiting_payment` 的发票数 |
| 冲 | 当前规则下命中冲抵类状态的发票数 |
| 现金往来 | 当前规则下命中现金往来的发票数 |
| 待处理 | 未被任何自动规则闭环的发票数 |

保存前若有草稿变化，显示：`预计影响数据将在保存并重新读取后更新`。没有 preview API 前，不显示“预计影响 N 张”。

### 3. 规则列表

规则列表使用紧凑行，不使用大卡片。每条规则展示：

- 启用状态
- 优先级
- 输出状态名称
- 条件 chips
- 原因文案
- 当前命中数，如果可用

示例行：

```text
启用  优先级 1  现金往来
条件：申请人=陈秀云 · 有 OA · 有流水 · 完全匹配
原因：自动识别陈秀云 OA，有流水且完全匹配
命中：23 张
```

第一阶段可编辑字段：

- 启用/停用
- 优先级
- 输出状态名称
- 原因文案

第一阶段只读字段：

- status code
- 条件表达式
- 申请人约束
- fallback 规则

原因：条件表达式属于业务口径，不应在没有完整 preview、审计和回归保护前开放任意编辑。

### 4. 待处理方向

如果继续放在本抽屉内，标题必须改为：`待处理发票处理方向`。

展示要求：

- 用列表或小表格展示方向名称。
- 明确是否被 OA 反提流程使用。
- 如果当前后端未消费这些方向，必须显示只读提示：`当前仅作为待处理方向标签，不影响自动分流`。

长期建议：将“待处理方向”和“OA 反提目标申请人配置”拆成独立设置区，不与支付状态解释规则混在同一抽屉中。

### 5. 底部操作区

固定在抽屉底部，包含：

- `还原`
- `保存并重新读取`
- 保存中状态：`保存中...`
- 保存成功反馈：`规则已保存，正在重新读取进项发票使用情况。`
- 冲突反馈：`规则已被其他人更新，请重新打开后再编辑。`
- 权限反馈：`当前账户没有保存权限。`

按钮规则：

- 只读或无保存权限时，不显示保存按钮。
- 没有草稿变化时，`保存并重新读取` 禁用。
- 保存成功后关闭或不关闭抽屉都可以；第一阶段推荐不自动关闭，保留成功反馈。

## 视觉约束

- 不使用营销式说明区、大面积插画、渐变背景或装饰性卡片。
- 使用表格、标签、分组标题和稳定间距表达规则。
- 规则行高度稳定，避免编辑状态导致列表跳动。
- 条件 chips 使用低饱和背景，强调可读性，不用强色块堆叠。
- 文案短句化，避免解释已经可见的字段。

## 状态设计

| 状态 | UI 表现 |
| --- | --- |
| loading | 抽屉主体显示规则加载中，底部按钮禁用 |
| read-only | 显示规则和处理方向，不显示保存动作 |
| editable | 显示可编辑控件和保存动作 |
| dirty | `保存并重新读取` 可点击，`还原` 可点击 |
| saving | 禁用所有编辑控件和底部动作 |
| saved | 显示成功反馈，并触发当前页 rows direct refetch |
| version conflict | 显示冲突错误，引导重新打开抽屉 |
| validation error | 行内标记具体错误字段，顶部显示摘要错误 |

## API 合同

读取规则：

- UI 需要 `rules`、`pendingDirections`、`readOnly`、`permissions.canSave`。
- UI 可以接收但不展示 `version` 和 `sourceMetadata`。

保存规则：

- 请求继续携带 `expectedVersion` 和 `idempotencyKey`。
- 保存成功后触发 `input_invoice_usage` 当前查询 direct refetch。
- 后端继续负责审计、版本冲突、幂等冲突和真实派生数据后台任务。

## 验收标准

- 抽屉内不显示版本号。
- 用户能看懂每个支付状态由哪些条件触发。
- 用户不会误以为本抽屉能补全 OA/流水关联。
- 只读用户能查看规则，不能保存。
- 可编辑用户修改后可以还原、保存并触发当前页 direct refetch。
- 保存冲突、权限不足、校验失败都有明确反馈。
- `candidate` 关系不会被规则算成已付款或冲抵。

## 测试建议

按七类测试中适用部分覆盖：

- Business core：规则优先级、启用状态、fallback、candidate 不参与自动闭环。
- Service-layer：保存规则后的 app settings、审计、派生数据后台任务。
- API contract：GET/PUT shape、权限、版本冲突、幂等冲突、校验错误。
- Read model/background job：规则版本变化后不得恢复 `input_invoice_usage` / `invoice_lifecycle` 页面 read-model freshness；真实后台任务只覆盖保留的派生数据。
- Frontend interaction：只读、可编辑、dirty、保存成功、冲突、无版本号展示。
- E2E business flow：保存规则 -> 当前页 direct refetch -> 支付状态更新。
- Regression：既有 OA/流水 relation 展示、`+N` 明细、OA reverse drawer 不受本抽屉误影响。

## 后续待决

- 是否开放条件编辑；第一阶段建议不开放。
- 是否将“待处理发票处理方向”拆成独立设置。

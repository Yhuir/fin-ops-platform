## 2. 设计任务

保持财务运营平台现有语言，改善右侧抽屉内「看付款证据 → 在OA单元下拆分 → 选来源 → 核对 → 保存」的效率。设计者可以改善排版和交互，不改变金额规则、自动分配条件、权限或数据来源。

- 保留右侧 AppDrawer、顶部关闭、待分配/人工已分配、搜索与按关系保存。
- 一个 OA 成本单元下允许动态新增/删除多条分配行。
- 每行主要编辑项：来源流水、分配金额。选择来源后自动展示银行账户、主标签、子标签；不设计三个可以自由组合的独立选择框。
- 项目、OA 类型、原费用类型、申请人、原 OA 金额作为依据；本项最终计入成本合计随分配行显示，不能将原金额伪装成分配结果。
- 来源卡显示账户、付款时间、对方、原额、银行完整标签路径、当前分配/剩余金额。标签完整路径可能超过两段，允许换行。
- 每条已分配明细使用来源付款月份。例如同一 OA 成本 600 元，8 月建行 350 元、9 月民生 250 元；保留两条明细及各自日期，不把两条都放在最后付款月。不提供手工改月份的输入框。
- 可用来源只有本关联实际支出，不提供全库账号或全局流水搜索。
- 退款和非成本有事实时按需展开；退款选择原支出并填写冲减金额，非成本选择来源支出和金额/原因，不制造负成本行。
- 顶部/底部用紧凑金额核对帮助用户发现未分配/超额；避免每个字段周围反复解释同一业务规则。
- 保留每组独立草稿和保存状态；不能一个任务保存清空其他任务输入。
- OA总额与净支出相等时，每个OA单元目标只读；用户拆分来源，不能把原600/400改成500/500。金额差异场景继续允许人工决定最终成本。
- 已保存但标签/账户资料待完善的任务仍可pending：展示保存结果和剩余问题，重新打开完整回填，不重复输入、不无条件移到已分配。

## 3. 需要产出的界面和状态

| 场景 | 设计必须表现 |
| --- | --- |
| 初次打开 | 抽屉立即打开，任务列表加载/空/失败/重试 |
| 任务概览 | 一眼看懂待分配原因；列表不铺开全部复杂表格 |
| 单OA、多来源 | OA下新增两条或更多分配行；来源账户/标签联动 |
| 多OA、多来源 | 每条OA有清晰边界；同一流水剩余额度随当前草稿变化 |
| 金额已知、来源未知 | 保留已知金额，明确剩余需分配；不预选任意来源；月份待确定，不能冒充属于当前月份 |
| 金额差异 | 原OA金额作为参考，输入后展示最终成本及非成本合计 |
| 退款 | 原额、退款、可计成本关系清楚，退款账户不能冒充原付款账户 |
| 非成本 | 来源明确、正金额和原因，不把未填当零 |
| 银行信息缺失 | 显示待完善标签/账户的原因与维护方向，不假造选项 |
| 输入错误 | 行级金额格式、单元不平、来源超额分别定位；纯色彩不足以传达错误 |
| 已保存编辑 | 按有效决定回填多行，不要求状态必须allocated；修改后能保存，保留原身份和证据 |
| 版本变化/网络不确定 | 草稿不丢，明确重新读取和冲突；不能伪报成功 |
| 关闭/切任务 | 有未保存内容时沿用应用的丢弃确认；保存中不能重复提交 |
| 窄屏和长文本 | 880px及较窄空间仍能阅读/输入，长项目名与标签路径换行 |
| 键盘和焦点 | 新增后焦点进入新行；删除后焦点合理；弹层关闭回到来源控件 |

配套三视角需要提供宽屏4/3/5栏和窄屏折叠导航的排版建议，保证成本明细有足够宽度；不能只完成抽屉却忽略页面无法承载新增层级。

各栏只受已选上游条件限制：选一个子标签后，同级其它子标签和上游项目仍可直接切换。页头保留期间/搜索根合计，当前路径金额在分面/明细上下文显示，不能混淆。未知日期在全部时间中排末尾，有日期限制的导出不把它当作符合范围。

## 4. 样例数据

以下都是设计演示，不对应生产交易。任何具体分配均注明「人工已确认的演示结果」，禁止表现成系统推算。

1. 单一明确来源：OA成本100元，一笔付款100元，可自动显示来源。
2. 跨月拆分：OA成本600元，来源A为8月建行350元，来源B为9月民生250元；两条分配行分别进入8月/9月，原成本仍600元，各自使用来源银行标签。
3. 等额歧义：OA单元A600元、B400元；两笔付款各500元。初始不分配、不预选来源，不提示某一种600/400拆分为推荐答案。
4. 退款：支出1050元、明确付错退款35元，单元成本1015元；退款冲减同一支出后再分配净成本。
5. 非成本：支出100元，其中成本80元、非成本20元，需要明确来源和原因。
6. 历史金额：已保存单元成本600元、来源尚未确定；金额可见，来源需补。
7. 长标签：保留三段路径示例「外部往来款付款 / 借出款 / 业务往来」作为布局压力测试，不新增第三层统计导航。
8. 未标记、空账户、版本冲突、跨月付款分别有独立状态示例。

额外复验：保存后标签仍缺失，关闭再打开应完整回填；切子标签时同级选项不能消失；O=N不能修改单元目标；零净成本不产生无意义任务。实际PUT演示采用主计划16.1的700/600人工变体，自动600/600场景验证读取与展示。

## 5. 组件与实现约束

- 当前前端为 React + TypeScript，项目内 HeroUI 3.1、FinanceTable、AppDrawer；实际实现复用现有组件和图标库，不另带一套设计系统。
- 原抽屉宽度为 `min(880px, 100vw)`，先在此范围设计。若要增宽，应展示窄屏效果与明细可读性理由，不任意改全局 Drawer。
- 金额无千分位、两位小数；布局支持中文长项目名和标签自然换行。
- 保存是按关系的一次操作，新增/删除行是本地草稿操作；不设计输入即请求后端、自动保存或后台分配进度。
- 不设计拖拽画线、OA×银行大型矩阵、自动比例按钮、AI推荐、独立银行账户编辑或成本专属标签规则。
- 不显示内部 case ID、hash、版本号、SQL/worker等实现细节；冲突提示使用业务语言。
- Make 原型只用演示数据，不调用生产接口，不接生产身份，不更改任何财务事实。
- 交付包括布局、交互状态、组件与响应式说明。实际视觉是App移植依据；可复用的展示结构/CSS/资源经检查后迁入，业务计算/API访问按仓库边界实现。不能覆盖整个工程，也不能以“代码仅供参考”为由忽略外观还原。

## 8. App移植和高还原复验

### 8.1 实现边界

- AppDrawer继续拥有弹层、焦点、滚动锁和关闭基础行为。当前已有width/className/footer/headerActions，优先用这些参数还原设计。
- 成本容器负责加载/错误/保存/任务选择；局部编辑器渲染草稿并抛事件；必要纯helper做分运算/提交对象；网络只经现有Cost client。
- 移植展示结构、局部样式和可用资源，接入现有HeroUI/FinanceTable。保留Make最终信息结构、比例、视觉层级和操作方式，不自行换版。
- 样式限定在成本class范围，现有tokens/参数优先，差异局部表达。不改全站字体、通用按钮/表格/Drawer，不复制第二套框架、reset或路由。
- 旧单金额draft、费用导航、被替代成本CSS和独占fixture随调用迁移删除；扫描真实引用，保留其他页面使用的公共符号和现有保护。
- Make演示数据/假接口只用于设计和测试；App失败时明确显示错误，不回退演示数据、旧费用类型或虚构保存成功。

### 8.2 App浏览器对照和修正

使用与Make相同浏览器、CSS窗口尺寸、缩放、已加载字体、数据和展开/选中状态，按内容区域并排对照截图，并实际重做关键操作。核对抽屉/栏宽、字体/行高、padding/gap、颜色、图标、边框/圆角、状态、滚动和来源弹层。

先消除比例、信息遗漏、截断和行为差异，再修细节。不以笼统“95%还原”代替证据；不同系统字体栅格化可注明，明显错位不能解释成环境差异。

App样式覆盖、组件参数或数据接线错误，在App局部修正后复验，无需Make重生成。Make设计遗漏或与已确认业务/可访问性/实测性能冲突时，先修正Make参考再同步App；常规修正不逐项审批，不私自降低还原目标。留下简短已处理问题和剩余差异说明。

先用同数据样例比较视觉，再接真实测试API验证加载、权限、保存/重读、冲突和导出。Mock不替代真实后端验证，真实数据不同也不是省略视觉比较的理由。

### 8.3 性能与回归

在App测普通任务及100条分配行任务的打开、输入、选来源、增删和保存刷新，区分网络和渲染耗时。输入/增删不发HTTP、不整页刷新、不预取全部任务；发现卡顿再局部优化，不默认引入昂贵动画或重型新库。

使用现有Vitest/Playwright和主计划后端集成命令。验证Cost闭环、原银行流水两个视角和真实受影响页面，核对共享样式、跨页面请求与刷新。此流程不新增截图baseline或发布门禁。

# 待分配与自动成本分配收敛计划

日期：2026-09-24。状态：实现及本地回归完成，待正式发布后执行等价历史决定迁移和生产验收。当前合同同步到 boundary-io.md。

## 目标与已核实事实

- 自动能确定来源、金额及归属且符合成本条件的部分直接统计，不需要人工保存，不出现在人工待分配/已完成列表。
- 人工决定仍有实际作用时保留；审批未完成、资料缺失和事实变化不能伪装成分配歧义或已完成。
- 2026-09-24 只读核验：CASE-AUTO-0016 去掉人工决定的内存模拟，来源和成本明细与保存版完全一致；CASE-AUTO-0256 的百万 OA 已自动对应 10 万、42 万、48 万。
- 当时 33 条人工已完成中 31 条来源与成本结果可由自动计算等价产生；这只是候选清单。执行时必须重读，并补查金额锁定、人工覆盖、范围外来源等业务语义。
- CASE-AUTO-0102 存在 OA 2308.02 / 实付2038.02的人工减额；CASE-BATCH-txn_imported_1210 有192元人工补充，不能清除。
- 当前前端标题将所有非 pending 状态显示为已完成，需显式处理 stale。

## 规则

1. 输入单位是 OA 成本子项与银行有效用途子项，不能只数父 OA 或父流水。
2. 未拆分使用原流水用途；已拆分只使用子项用途金额，父金额仅做凭据，禁止重复统计。分类依据银行 owner 的标签语义与成本范围配置。
3. 只在现有正式关系及允许来源范围内确定成本，不跨关系按同金额自动建关联。
4. 支持来源明确、目标闭合的一对一、一对多、多对一、独立组件组合和唯一逐笔等额对应。
5. 400+600 对800+200、重复金额且来源不明确、金额差额、退款归属未知等不能猜测；不比例平摊、不按显示顺序配对。
6. 已明确独立部分可先计入；未解决部分保留原目标和剩余金额，不重复消耗来源。
7. 审批/分类/账户/日期等资格和资料检查继续有效。纯等待问题显示待审批/待补资料；同时有来源问题时同时保留原因。
8. 建议草稿不等于正式来源。保留不能自动证明的组合建议能力，不把预填或展示同行当成成本事实，不引入全局子集搜索。
9. 自动成本按实际来源账户、标签和付款时间生成，三个成本视角、明细、搜索和导出共用同一结果。

## 模块与 I/O

| 责任 | 输入 | 输出 | 文件/限制 |
| --- | --- | --- | --- |
| Canonical repository | 当前关系、OA、银行用途、配置、人工记录 | 同一快照及必要正式来源历史 | cost_statistics_canonical_repository.py；集合读取；无逐行查询 |
| 纯业务规则 | 快照、成本资格、来源范围 | source_allocations、状态、原因、剩余、成本事件 | cost_statistics_policy.py / cost_statistics_source_allocation.py / cost_statistics_allocation_scope.py；无 I/O |
| 人工服务 | 完整决定、版本、actor | 事务决定与审计、最新任务 DTO | cost_statistics_manual_allocation_service.py；不改上游事实 |
| 持久化 | 决定及当前修订版本 | 同一事务的模式、版本、审计 | postgres_repositories/cost_statistics_manual_allocation.py |
| 查询/UI | 同一任务 DTO 与计数 | 列表、原因、详情、编辑 | 现有 features/components/cost-statistics；不重做业务推算 |
| 运维迁移 | 当前人工候选及当前事实 | 等价候选/保留原因/实际变更计数 | 成本 owner 的窄 service + CLI；不做 GET 副作用 |

关联、银行拆分、OA、标签配置是输入 owner。外部往来、银行余额、发票与关联台作为隔离回归对象。本次不改变其业务规则或写入入口，不新增 read model、worker、缓存或依赖。

## 实施顺序

### 1. 固化旧链路清单与回归样例

- 对 policy、source allocation、scope、canonical repository、人工 GET/PUT、统计查询、导出、前端草稿/保存核实、拆分撤销调用点、tests/docs 做符号和文字扫描。
- 标注保留/替换/删除，不扩大到与成本分配无关的旧模块。
- 将真实金额结构变为脱敏 fixture，先复现重复已完成、stale 标错、部分自动分配和差额保留。

### 2. 明确自动/人工模式，保持连续版本

- 复用既有人工分配表，新增一个明确的决定模式字段（automatic/manual），不建第二张成本结果表。
- 存量记录迁移填 manual。退出人工决定时模式改 automatic、版本递增，保留原完整决定的审计；自动模式旧载荷不参与任何计算。
- 未产生过记录的关系仍可无记录自动计算。版本用于并发，不再用 version=0 判断业务模式。
- 同步 repository、policy、API DTO、前端类型/建议条件/响应核实及 owner 内撤销入口。成本模式不得借用关系版本，不能修改关联 owner 的事实。
- 证明退役→再人工编辑→旧页面提交不会发生版本复用。无变化请求幂等，不产生有效人工覆盖。
- 模式由后端验证和计算产生，客户端不得凭 mode 绕过来源校验。
- 模式与完成状态正交：automatic 表示没有生效的人工覆盖，不保证 allocated。automatic + pending 仍按原因进入待处理列表；manual + stale 不得回退套用自动结果；不能因 mode=automatic 隐藏尚未解决的成本。

### 3. 收敛任务判定与自动计算

- 复用现有自动来源纯函数，删除外层数量直接决定人工、仅因历史行存在就使用人工、版本号代替决定模式等路径。
- 只有有效 manual 模式覆盖自动结果；automatic 模式不参与人工计算，源事实变化后正常重算。
- manual 模式原决定过期时，保持待复核且不使用失效决定，也不静默改成自动模式。自动计算可以用于核对，但未经明确处理不得覆盖原人工含义。
- 等价比较覆盖完整当前关系与范围外决定、来源金额、OA/项目、标签覆盖、补充项、退款、非成本及金额锁定语义；不能只比较总额或当前页面可见行。
- DTO 复用既有 status/pending_reasons，新增模式只用于区分自动与有效人工。列表、计数、搜索、分页采用同一筛选。
- 明确部分单独生成成本；不完整资料不生成貌似完整的统计，不能靠保存绕过。

### 4. 历史决定迁移与未来保存

- 默认 dry-run 输出候选及保留原因，不写数据，不硬编码31条或具体case。
- 候选扫描覆盖全部持久化人工记录，不受当前页面、月份、成本范围或分页限制。非 active 关系及无法取得完整事实的历史项单列保留原因，不重新激活；当前范围外人工语义也不得丢弃。
- apply 在现有事务/锁顺序下重读事实和版本，重新证明等价，更新模式并同事务审计；并发变化则该项明确冲突，不沿用旧预览。
- 同一批次小范围原子处理；重复运行零重复退役/审计。失败回滚，不出现已退出人工但丢失成本的中间状态。
- 有自定义金额、标签覆盖、补充项、退款/非成本决定、非默认锁定或无法证明完整等价时保留。
- 后续保存只有实质人工决定才进入人工已完成；恢复自动默认且完整等价时同样走成本 owner 的退出人工路径。GET 永不迁移。
- 回滚使用本次审计前镜像，在当前版本/事实相符时恢复为新的递增版本，禁止覆盖迁移后用户的新编辑。

### 5. 前端交互

- 自动完成在两个人工标签页均不显示，从成本明细保留调整入口。
- 已完成仅显示有效人工决定；pending/stale 显式显示，stale 为待复核。
- 利用已有原因显示短状态：待分配/待审批/待补资料/待复核，不新增页面或审批流程。纯等待问题无修改时不诱导保存；已完成部分仍可按原规则处理。
- 多对多数量标题改中性“关联明细 · N项/M笔”，不把数量当作歧义；明确来源从同一任务结果展示，不让前端独立求解。
- 保留加载、失败、权限、草稿、409、保存响应丢失核实等行为，核实覆盖模式和连续版本。
- 前端列表、页头数量、分页游标及三成本视角的待处理数量统一采用后端任务筛选；保存后重读服务端结果，不通过前端加减计数猜测。纯等待事项仍留在现有入口并显示具体原因，不另建队列。

### 6. 测试与性能

- 核心：一对一/一对多/多对一/混合组件、相同金额歧义、400+600/800+200、OA子项、缺资料、部分审批、退款、范围内外、精确分和来源容量。
- 服务/真实PG：迁移等价与非等价、事务审计、失败回滚、幂等、并发编辑、旧版本拒绝、退役再编辑、来源变化后重新计算。
- 模式矩阵：无记录自动完成、自动模式未解决、人工模式完成、人工模式过期；覆盖从自动到人工再恢复自动、重复提交以及晚到的旧请求/响应。并行读取只应看到迁移前或迁移后的完整结果。
- API：模式与版本完整返回；列表计数/搜索/分页一致；错误、权限、冲突；自动 GET 零业务写入。
- UI：自动退出两列表、stale 不显示已完成、短原因、调整分配、保存/核实/刷新、筛选和草稿保护。
- 端到端：原流水或拆分→正式关联→自动成本→三视角/明细/导出；歧义→人工保存→修改事实→复核；历史迁移前后等价。
- 回归：关联台、银行明细、外部往来、OA/发票页面、批量账务及权限；各 owner 原始事实/关系/余额不因成本迁移改变。
- 不引入 read model/cache/worker，相关新增生命周期测试不适用；继续验证 canonical 直读与无意外后台任务。
- 热路径不逐关系重算“人工与自动是否等价”，历史比较只在运维命令和实际写入边界做；正式历史批量获取，避免迁移后自动关系增多造成 N+1。
- 使用既有性能合同：核心读 p95≤1000ms、p99≤2000ms、错误0；相同数据/请求范围记录改前改后延迟、SQL次数、响应体及样本数。目标规模未测则明确未测。

## 自审与完成条件

- 简单架构：原成本 owner、原纯函数与原UI；只增加解决模式/版本混淆所需的表字段及窄迁移入口。
- 旧代码：替换影响当前链路的判定、版本推断和错误UI状态，不删除仍有作用的人工编辑、审计和来源约束。
- 安全边界：金额精确、唯一来源、权限、版本、事务为必要条件，不添加审批链或双引擎兜底。
- 性能：有界批量查询，在线不做组合穷举或双全量计算，以实测为准。
- 完整闭环：规则→持久化/版本→历史数据→UI→统计/导出→回归→部署→生产验证→临时备份清理。
- 不承诺绝对零bug；交付必须列明已验证的页面、命令、性能与剩余未测风险。此计划尚未执行上述验证或发布。
- 必要的校验与错误处理不是兜底：非法金额、未知来源、权限不足和版本冲突明确失败；不能靠默认值、吞错、切旧算法或重试写入掩盖失败。真实网络结果不明确时按现有只读核实流程处理。

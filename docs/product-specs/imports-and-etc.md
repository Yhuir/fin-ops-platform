# 导入、预览确认与 ETC 业务批次

本文维护文件导入、预览确认、幂等防重、外部文件生命周期和 ETC 业务批次的当前业务口径。

## 导入通用流程

1. 上传文件，按 SHA-256 登记原件并拒绝已确认的同内容重复文件。
2. 后端在有界资源内验证文件签名、解析并生成 preview rows、错误、摘要和 source version。
3. 能从文件元数据取得行数或借贷合计时，必须与解析结果核对；不一致时禁止确认。
4. 用户确认导入，系统通过 durable job 执行幂等 canonical 写入。
5. 文件对象、session、批次、行、job 和审计记录进入可追溯生命周期；其他页面下次访问时读取已提交事实。

银行流水预览若证明全部记录已存在、没有疑似项、解析错误或账户冲突，页面必须明确显示“无需导入”并禁止创建零变更确认任务；`preview_ready` 只表示解析完成，不等于一定存在可写入记录。多文件预览只提交实际包含可处理记录的文件。

导入确认必须能防止重复提交、重复文件和半写入状态。失败时要保留足够的错误信息用于人工修复。

发票导入页同时提供单张“发票录入”。附件上传可选，一次只解析首个 JPG/JPEG/PDF；识别结果只预填统一发票池需要的字段，用户可修改或完全手工填写。服务端预览必须校验票据方向、蓝/红字、购销双方、发票号、条件式发票代码、日期、金额、税率和精确重复；红字由用户输入正数，系统以负数写入 canonical 金额。最终确认复用普通发票导入 durable job，不自动关联 OA 或银行流水，也不建立第二发票池。

同一强发票身份只能对应一张 canonical 发票，但可以同时保留“导入记录”“OA附件”“明细归属”等多条来源证据。正式 Excel 导入维护经过校验的发票表头事实；OA OCR 只补充缺失字段，并以附件中的明确 OA / 子付款项身份建立归属，后到的 Excel 导入不得删除既有 OA 来源或子付款项归属。反向顺序同样成立：如果当前版本 OA 附件缓存已经形成强发票身份和明确子付款项，Excel 确认创建或命中 canonical 发票后必须在同一事务内定向合并该 OA 来源。未识别、弱身份、过期缓存或缺少明确子付款项的附件不得按金额、项目、文件名或顺序自动归属。

App 不提供第二份导入汇总页。侧栏“导入”只展开三个正式导入工作流；旧 `/imports` 入口仅兼容重定向到银行流水导入，不持有业务状态或发起数据请求。

### 银行流水表头归一

- 银行流水导入以 canonical 业务字段为合同，不以银行名称或某一版 Excel 列名作为模板事实源。同义表头、单位和半角/全角符号差异先做确定性归一；账号、账户名等文件级字段允许从表头上方元数据读取。
- 系统只自动采用有明确别名证据的映射，不使用模糊字符串、固定列号或模型推断直接写入金额、方向、日期等核心事实。
- 核心字段无法完整确定时，文件保持不可确认并返回源列候选；用户在导入页明确完成字段映射后只重试该文件。相同标准化表头签名可复用最近一次已确认映射，签名变化必须重新确认。
- 页面所选银行账户是用户明确配置，但不能覆盖文件内可证明的真实账号。文件识别银行/尾号与所选账户不一致时必须前后端 fail closed，用户改选正确账户并重新预览后才能确认；人工字段映射不能绕过金额、日期、方向、去重、preview stale 和账户冲突校验。
- 银行流水有官方参考号时，强身份使用“账户 + 官方参考号种类/值 + 交易业务指纹摘要”；业务指纹由交易时间、方向、金额和规范化对方名称组成。部分银行会在同一文件内复用官方参考号，因此官方参考号单独不能证明同一笔交易。历史 `bank-v2` 记录只在业务指纹一致且双方官方参考号存在唯一交集时自动判重；缺失或多义证据进入 `suspected_duplicate`。没有官方参考号时业务指纹仍只是弱疑似身份。
- 文件头出现的账号、账户名称、借贷笔数和借贷合计属于来源控制证据；与解析结果不一致时 fail closed。文件未提供控制合计时明确显示“未提供”，不能伪装为已核对。

## 文件生命周期

- 已完成的银行流水导入若只创建新流水、owner 数量可证明一致、未更新既有流水、未核销且没有其它生效业务引用，管理员可以在导入历史撤回。撤回删除本批次独占流水和可撤销 current state，但保留 OA、发票、导入 batch/file/row、原文件对象和 append-only 审计；批次/file 标记为 `withdrawn`，原文件可在选择正确银行后重导。
- 普通 Workbench active relation 在撤回事务内通过正式 relation command 移除目标流水；已核销、收款收据、OA 待付款、往来闭环、免 OA/流水规则批次等业务引用不能强删，返回冲突并要求先从对应业务模块解除。

- 原始文件保存在对象存储或兼容存储中，业务记录只保存对象引用、checksum、大小、文件名和导入批次。
- XLSX 必须验证 OOXML 结构、路径、成员数、展开大小和压缩比并以只读方式解析；XLS 必须验证 OLE 签名并限制 sheet、行、列和单元格数量。单个损坏文件只形成文件级错误，不中断同批其它文件。
- 不允许测试或自动化流程依赖真实业务文件。
- 删除、重置和回滚必须同时考虑对象存储、数据库记录和 read model。

## ETC 业务批次

ETC 批次覆盖票据导入、OA 草稿创建和人工提交确认：

- 用户点击创建 OA 草稿后，批次立即进入“暂存”，并显示“我已经在 OA 系统提交草稿，本批次进入已提交”和“我已经在 OA 系统删除草稿，本批次保留在未提交”两个决定。App 不检测 OA 是否已生成草稿；创建中与已返回草稿信息都使用同一人工决定合同。
- 草稿创建请求结果未知时不得自动重试。用户依据自己在 OA 系统中的实际操作作出决定；App 只用版本 CAS 持久化和审计该声明，不创建第二套 OA 检测或恢复 UI。
- OA 草稿创建成功后，或业务批次已经进入正式提交状态后，用户可从暂存确认区或已提交批次的“发票明细”标题栏下载该业务批次关联的全部 ETC 发票 PDF；历史已提交批次即使没有 OA 草稿 ID 也可下载。下载文件按开票日期、发票号稳定排列，每张 ETC 发票恰好一页；任何一张来源 PDF 缺失、损坏、完整性校验失败或不是单页时，本次下载整体失败并明确提示，不生成少页文件。
- 历史已提交批次的附件恢复只允许管理员提交原始 ZIP、当前版本和原因。既有附件 hash 存在时必须严格相等；仅当历史后补成员仍是 `canonical_invoice:` 合成来源、PDF/XML 路径与 hash 以及导入来源均为空，且 business/submission 成员完全一致时，才允许用原始 XML/PDF 建立附件事实。建立前必须核对发票号、日期、购销双方名称与税号、金额/税额/价税合计以及 PDF 内发票号；成功后只补附件并以原始 XML 纠正该成员的通行日期、车牌、车型和来源汇总，不改变成员、OA、关联台关系或 submitted 状态。
- ETC 创建 OA 草稿时，OA 上传接口返回的已知绝对 `/fileManager/` 或 `/profile/` 文件地址必须在外部 adapter 边界归一为 OA 根相对路径，再写入附件 `response.data` 与 `response.extra.filePath`；未知绝对 host/path 必须 fail closed。页面和 Nginx 不得保留错误绝对地址兼容拼接。
- “已提交”通过 ETC business batch manual OA status API 推进到已提交口径，并同步闭环该业务批次绑定的 ETC 对账任务；“未提交”释放本地 ETC 发票占用并回到未提交链路。
- “已提交”不会直接代表关联台三项已配对。系统会把该批次下 ETC 发票折叠成一条 `source_kind=etc_invoice_summary` 的未配对汇总发票行，金额使用业务批次上报金额，等待未来 OA 单据和银行流水进入后由关联台普通配对逻辑闭环。
- ETC 发票属于进项发票，正式发票事实只进入统一发票池 `app.invoices`。ETC ZIP 导入的职责是保存本批次命中的 PDF/XML 附件和 ETC metadata，并建立批次/附件/已存在发票之间的关系；ZIP 内未命中本批次的发票直接丢弃，不进入任何正式发票池。
- ETC 业务批次允许用户在任意流程阶段删除本地批次记录，不因已确认对账、已创建 OA 草稿、已人工确认提交或任务已关闭而阻塞。删除只处理本地业务批次、导入事实和发票占用；不得删除或撤销真实 OA 草稿、OA 流程或 OA 已提交事实。
- 删除未提交批次会清理本地创建的对账任务、上传文件、导入批次和 ETC metadata/附件关系；删除已提交批次会取消 `etc_invoice_summary` 合并。只有原本已存在于统一发票池的发票才可能回到普通发票视图；ETC ZIP 不得为删除后的“散票恢复”创建新的 canonical invoice。若该 summary 已参与关联台 active relation，系统取消该 relation，且不恢复历史 OA+银行流水二栏配对。
- ETC 票据管理页不提供月份、车牌或关键词搜索框；用户可见列表直接展示当前用户范围内全部业务批次，并按“未提交 / 暂存 / 已提交”三个互斥 bucket 分组。后端 `GET /api/etc/business-batches` 仍保留可选 `month`、`plate`、`keyword` 参数作为兼容/运维查询合同；传入 `month` 时优先按业务批次归属月份匹配，历史迁移或运维补录批次必须写入明确 `scope_month`，避免跨月发票让同一批次在多个月份重复出现。
- ETC 票据管理页按 `准备核对资料 → 确认核对结果 → 导入 ETC 发票 → 提交 OA 审批` 展示四阶段只读进度。进度只投影当前 business batch 与绑定 reconciliation task 的已有状态，不新增持久化阶段、接口、read model 或 worker；失败、部分失败、回退和待人工确认必须使用非完成状态，`oa_confirmation_pending` 不得显示为已提交。
- 未提交业务批次允许在提交前编辑标题；标题必须持久化在 business batch payload，并同步该批次绑定的 ETC 对账任务标题，使 ETC 发票导入页 ready task 下拉显示最新标题。已提交、人工确认已提交或 closed 批次标题锁定，不允许继续修改。
- 人工确认必须记录操作者、范围、原因、状态和审计。
- 历史 ETC OA 检测状态通过迁移归并为待人工确认；当前业务口径不再保留 ETC 专用自动检测、刷新检测或检测异常处理链路。
- 迁移或 dry-run 需要输出受影响批次、对象数量和可回滚边界。

## 导入后的影响

| 导入类型 | 受影响页面 |
| --- | --- |
| 银行流水 | 银行明细、关联台、往来款、成本统计 |
| OA 单据 | 关联台、OA 待付款、ETC 批次 |
| 进项/销项发票 | 待找发票、税金抵扣、成本统计、关联台 |
| ETC 票据 | ETC 批次、关联台 summary、税金抵扣/成本统计的刷新；不创建新的统一发票池事实 |

6. 现金收付与非现金冲抵必须区分。报表可以同时展示两者，但只有实际现金账户变动进入现金流水池。

## 2. 已确认要求与明确排除项

| 项目 | 已确认要求 |

| 扩展 | 为其他账簿、子表和任务类型留下结构空间，不预建没有业务用途的表、接口或大块空白 |

### 3.2 现金流水的目的

`2026年1月份现金账!A1:L1` 包含：日期、用于项目名称、报销人、费用类型、费用内容、招行收入、陈秀云收入、招行支出、陈秀云支出、招行余额、陈秀云余额、备注。

它回答“钱何时从哪个受管理账户进出、用于什么、当前还剩多少”。月账和全年账是同一流水事实的时间视图，不是不同业务类型。旧表无正式表头的辅助标记不自动变成字段或金额规则；有票回款按本文明确公司应收/现金到账关系处理，其他参考说明保留为说明。

第二张表是录入参考，不是批量导入文件；独立现金流水 Tab 完整显示所有未删除的手工和任务现金，可筛选、分页、查看详情、编辑和删除。普通工资、房租、水电等直接收支不进入往来总表，仍完整留在现金流水；确属垫款/借款时按真实往来处理，不能按费用名称一刀切。来源区分“手动录入 / 每月任务”，任务可追到归属月份，后续认领手工现金不改来源。实际日期、金额、账户和可信录入人直接保存在现金记录，不从全局历史补取；删除范围见第 7.5 节。

App 支持当月计划日调整、真实付款日期、账户说明和账单用途明细。同一现金可关联多个同项目事项，不支持跨项目金额分摊；同银行卡须以稳定身份区分。Excel 提到“公账”只是背景，不授权读取现有 App 公账/OA/ETC 数据。

### 3.5 有票支付与刘树刚账

- `有票支付!C1:F1` 包含金额、状态、使用日期、“谁拿来的票给谁抵账”；`G20:G21` 有“票已给，等待回款”的说明。它是票据使用和回款跟进账，不等于发票池，也不意味着有票就已经收到现金。
- `刘树刚账!A4:P11` 是银行 × 12 个月的还款矩阵；`O4` 特别写“12月提前还”，不是普通全年合计列。
- `A20` 为还现金情况；`A32` 为还票情况，`H33:H54` 标注有票直接冲；`A55` 为无票报销冲抵；`F93:G94` 为共计及年度欠款。
- 同一个人可能通过现金归还、有票直接冲、无票报销冲抵三种渠道减少欠款。后二者可能没有现金收付，必须保留区别。

已接受的 App 口径：个人矩阵标题为“实际代付/新增借款”，只统计明确由刘树刚承担的本金，按实际发生月展示；公司 ETC 等公司用途不混入。账单归属月独立保存，11 月代付 12 月账单只计 11 月一次，“提前还”作为说明/筛选属性。未还金额 = 起算未结 + 起算后新增本金 − 现金归还 − 有票冲抵 − 无票冲抵，均按对应金额及实际日期计，起算已含的旧欠款不再新增一次。

### 3.6 基础设置及办理说明

`费用类型&项目名称` 的 `A2:A9` 为收入费用类型、`A11:A23` 为支出费用类型、`A25:A35` 为往来类、`A38:B54` 为项目名称。项目区域保留为需求来源证据，按用户最新要求，不将它复制成另一套可手工修改的项目字典；OA 当前项目资料为准。历史 Excel 名称不能按相似名称自动匹配 OA ID。

`B10:L33` 是现行与修改方式的支付办理对照，涉及类别、概要、申请人、渠道、单据和收款方。UI 提供只读“支付办理说明”，保留参考性质；具体说明内容由业务资料维护，不加在线编辑/CMS、OA 审批或自动付款。

### 3.7 业务关系不等于 Excel 公式关系

业务关系拟按以下方式表达：

```text
现金专属账户 / 费用类型 + OA 只读项目资料
          ↓
手工实际收付 ─┬→ 现金流水池 → 现金流水 Tab（月度 / 全年 / 分账户）
任务实际确认 ─┘       │
                     └→ 关联现金事项 → 往来账总表 / 有票支付 / 刘树刚账
非现金冲抵登记 ─────────→ 事项归还或冲抵记录（不改变现金余额）
仅核对 / 催办任务 ───────→ 处理状态（不制造现金流水）
```

这里各账簿是现金模块内部的不同观察角度。后台不是先写“主表往来账”，再复制到“子表流水总账”，也不是反过来复制。删除唯一现金事实时同步移除其分配影响，各账簿重读后共同反映删除结果，不逐本账发送独立删除命令。

实际公式检查结果：

- 2026 年往来账没有公式；2025 年往来账、有票支付、刘树刚账均没有跨工作表公式。
- 2025 年全年汇总没有跨工作表公式，不能声称已经通过公式自动汇总 12 张月账。
- 可确认的跨表引用主要是月账 `J2/K2` 的上月余额承接。
- 2026 年现金账 `J2:K2` 引用了外部工作簿 `[1]` 中的 2025 年 12 月，不能将缓存金额当独立、已验证的期初真值。
- 2025 年往来账 `J42`、`J97` 已存在 `#REF!`。
- 有票支付 `C19` 只合计 `C2:C13`，后方还有记录；不能据此给 App 汇总截掉后续行。App 按全部匹配有效事实汇总，不使用此局部公式。
- 刘树刚账 `G94=P11-G93`，其是否包含期初欠款、跨年承接和未录事项未被说明，不直接升级为 App 通用欠款公式。
- 任务表中信/花呗为 5/8 日，办理说明 `C31` 为 6/9 日，图片又说明日期浮动。具体执行日由任务设置时填写并可调整当月计划；不从冲突说明替用户填值。
- 多表合并单元格承载共同日期、人员、项目或备注；不能把合并区域每一行都自动理解成独立现金交易。

### 3.8 录入条件与五列金额的已确认映射

来源 manual/task 只决定溯源，不决定费用方向、往来类别或花销。现金总量来自唯一 flow，事项/分配表达义务、用途及对应金额，不复制现金。

| 输入/处理 | 现金影响 | 总表/子账落点 |
| --- | --- | --- |
| 普通工资、房租、水电等直接收付 | 一笔实际 flow | 完整现金流水；没有明确往来则不进入往来总表。真实费用另按一次费用事实记录 |
| 公司/外部人员借款、垫款及归还 | 有实际收付才生成 flow；本金与偿还分别关联事项 | 每次往来处理一行，公司淡黄、外部蓝；初始事项与来源现金不重复展示本金 |
| 刘树刚借款/代付 | 实际支付记录一次，新增其承担的本金 | 总表橘黄；个人矩阵按实际月统计新增本金，不含公司用途 |
| 刘树刚现金归还/非现金冲抵 | 现金归还引用 flow；非现金不改变现金 | 总表绿色，分别进入现金归还、有票冲抵、无票冲抵子表 |
| 提供票据 / 使用但无抵债目标 | 无现金，无债务减少；使用占用来源额度 | 有票支付跟进，不伪造债务或总表现金处理 |
| 使用票据抵债 | 无现金；一次占用来源、减少目标义务 | 同一使用记录转为票抵，按目标往来类型进入总表及有票子表 |
| 无票/其他已明确非现金冲抵 | 无现金；减少明确目标义务 | 总表冲账列及对应个人/往来明细，不再计票抵 |
| 公司实际报销/垫款回款 | 一笔实际收入结清明确公司应收 | 报账提现/有票回款跟进；不再冲减此前已经票抵的个人债务 |
| 两个受管理账户互转 | 一笔 flow，两端变动，全池净额零 | 现金流水/分账户余额；不属往来或费用，不进入往来总表 |
| 任务新确认 / 关联已录现金 | 新确认仅建一次；关联不新增现金或原分配 | 按实际用途进入相应账簿，并更新当月累计；一 flow 最多一任务 |
| 核对/催办完成 | 无 flow、无金额变化 | 月度核对状态，不产生总表金额 |

| 总表列 | 固定业务含义 | 唯一金额依据 |
| --- | --- | --- |
| 冲账 | 无票或其他明确非现金冲抵，不含单列的票抵 | 非现金结算分配；不是删除或改错 |
| 还款 | 现金偿还借款 | 已有 flow 分配到借款的金额 |
| 报账提现 | 公司实际到账的报销/垫款回款 | 收款 flow 对公司应收的分配；交票/申请不算到账 |
| 票抵 | 票据用于清偿明确义务 | 有票来源与目标之间的一次结算，不再计冲账 |
| 真实花销 | 明确发生的费用净额 | 一次费用事实减已确认费用退款；不是五列相减 |

五列是观察口径，不能横向全部相加当现金总额。费用复用 items 的 expense 类型；直接费用付款可在统一录入中同时建立费用，已在账单用途中记录过的费用只关联，不再建第二份。借款本金、代付给个人的本金、还本金、互转不是费用；费用退款实际到账才建现金，对原费用只减少一次，普通报销回款结应收不再确认费用。无事实依据不填假 0，不建成本模块或读取普通成本表。

同一真实代付100可以建立借款100并明确支付已有费用100：两种观察各自引用同一现金，不是新增现金200。技术上分别校验义务资金份额、费用支付/退款份额，每一口径不超现金原额、不相加。往来总表现金列只计义务资金贡献，费用事件现金列为空、详情跳转同一flow；全池收支以现金流水为准。费用可退额为min(累计实付,原费用)减已有退款，不能退过真实已付款；同时还借款需明确另一归还分配，不能自动推断。

实现采用明确类别/方向/金额及来源 ID，禁止从备注、名字、颜色或 hash 猜分类。总表每行是明确业务处理，不强迫每行都有 flow；有多项分配只按对应份额显示。账户列从实际受管理账户映射，不将历史“招行”名称硬编码成唯一账户或漏掉其他账户。

一对多关系不能放大金额：一笔 100 元流水分配给两个事项 40/60，现金总额仍为 100，不得把 JOIN 后两行相加成 200；两个恰好各 100 元的独立流水又必须合计 200，不能用 `SUM(DISTINCT amount)` 去重。按事实 ID 先聚合分配，再组合显示。

## 4. UI 修订方案

### 4.1 导航树与 Tab 数量

```text
现有 App 左侧导航
└─ 现金账（一个页面权限）
   ├─ 账簿报表                       一级 Tab 1
   │  ├─ 往来账总表（默认入口）       同级账簿 1
   │  ├─ 现金流水                   同级账簿 2
   │  ├─ 有票支付                   同级账簿 3
   │  ├─ 刘树刚账                   同级账簿 4
   │  └─ 后续账簿扩展位置
   ├─ 每月任务                       一级 Tab 2
   │  ├─ 本月处理
   │  └─ 任务配置
   └─ 基础设置                       一级 Tab 3
      ├─ 现金账户与期初
      ├─ 费用类型
      ├─ OA 项目与可选阶段
      └─ 支付办理说明
```

明确计数：**3 个一级 Tab；账簿区域 4 个同级视图；任务区域 2 个子视图；设置区域 4 个子视图。** 不是 13 个按钮平铺在同一栏，也不按 Excel 的 21 张工作表建立 21 个 Tab。

刘树刚账的矩阵、现金归还、有票直接冲、无票冲抵作为当前账簿内的表格视图切换；优先使用工具栏的小型“表格视图”选择器，不再堆第三条通栏 Tab。年份/月度是筛选器，不是导航层级。

### 4.2 首屏排版

```text
现金账                                      新增流水 ▾
账簿报表          每月任务          基础设置
往来账总表   现金流水   有票支付   刘树刚账   [后续账簿位置]
期间 / 账户 / 项目 / 类型 / 来源 / 搜索 / 查询
当前账簿对应的紧凑汇总（按已确认业务口径）
──────────────── 主表（固定表头、内部滚动） ────────────────
分页 / 每页条数
```

只在“账簿报表”显示账簿选择行；任务和设置显示各自小型子视图。主操作随所在区域变化：任务页为新增/编辑任务，设置页为当前字典操作，不在所有 Tab 固定摆一组无关的记账按钮。

首次进入默认显示往来账总表。切到现金流水时展示期初/本期收付/期末及筛选合计的明确口径；不把现金账户汇总原样当作往来总表的应收应付。现金流水每行或详情提供“删除”操作，确认框显示目标流水的日期、金额、来源及关联影响，只有一次明确确认，不增加审批层级。接口未成功不先假删；成功后关闭该流水详情并重读，取消/失败保留当前记录并明确提示。

扩展留白：设计稿可在账簿选择行右端放两个低强调的预留标记；实际产品未开发前不显示可点击的空业务 Tab。窄屏使用“更多”承接同级账簿。主表下允许添加有明确用途的子表，不预建空接口、空表或虚线卡片。扩展不设“最多只能两本账”的硬限制。

### 4.3 各视图内容与操作

| 视图 | 主要内容 | 操作及边界 |
| --- | --- | --- |
| 往来账总表 | 默认主表；公司/外部人员/刘树刚分类整行着色；保留冲账、还款、报账提现、有票回款、真实花销、票抵 | 查看原事项及归还/冲抵明细，从既有事项办理真实结算时项目只读沿用；现金收付与非现金登记明确区分；关联流水删除后不再展示/计入该笔影响 |

| 本月处理 | 6 收入 + 6 支出；月度目标、实际累计、执行/提醒日；核对跟进及逾期待办 | 允许分次，一 flow 一任务；未办跨月保留；核对任务不要求金额 |
| 任务配置 | 内容、任务类别、默认执行日、提前提醒天数、启停与必要默认录入信息 | 配置不直接产生流水；当月调整与模板变更分开 |
| 现金账户与期初 | 本模块账户、启用日期、期初余额 | 不读取普通银行账户余额；不能每月把同一期初重复计入 |
| 费用类型 | 本模块专属分类 | 可参考 Excel，经确认后手工配置；不读取普通账分类规则 |
| OA 项目与可选阶段 | OA 项目编号、名称、阶段、最近读取时间；含已结束项目 | 只读项目资料；仅编辑自由新增/改选的允许阶段集合，不提供修改项目阶段按钮，也不改变既有现金事项的归属/结算资格 |
| 支付办理说明 | 现行/调整方式比较、渠道、单据、申请人、收款方说明 | 只表达办理参考，不自动审批、不执行银行付款 |

字段清单在技术稿落实到严格 DTO：内容必填，收/付款分类必选，互转不提供分类并提交 null，人员是可空的报销/经办对象而非录入 actor；具体账户/分类值日后配置。列表放高频字段，备注和多段明细进入详情，不能为简洁隐藏关键金额。

首次使用：账户/流水成功读取为空时分别显示未配置或空表；按本笔业务所需配置账户期初、分类及项目允许范围即可录入，不要求先配全部任务。无项目流水可不选项目。GET 不创建业务资料，读取失败不冒充首次空态。账户/分类停用只影响新选择，历史保留。已有流水后可更正期初/起算日，但必须提示全部后续余额影响，新起算日不能遮住已有有效流水。

期初尚有旧欠款时，先在期初未结登记中建立真实历史义务，再从该事项办理后续收付。仅 `is_opening=true` 的 `loan` / `company_receivable` 非现金登记可从 OA 全项目资料识别历史归属（含已结束），不按新增现金允许阶段过滤；登记本身不产生流水，也不开放普通现金新增的结束项目下拉。没有可核验的真实项目且无既有现金项目快照时，明确提示资料缺失，不猜 ID、不擅自改成无项目。完整初始化边界见 §7.1。

项目输入明确区分两种上下文：自由录入使用 `selection`，只展示当前允许的真实非结束项目；从既有现金事项收款/还款/付款使用 `existing_item`，显示“沿用历史事项项目（不可改选）”，由服务端读取本地事项 ID、项目 ID 和名称快照，不打开 OA 选择器或触发 OA 请求。项目已结束、从 OA 移除或 OA 不可用不妨碍真实结算；事项不存在、版本冲突或已无可结算额度则明确提示，不能自动退回自由选择、清空项目或创建替代事项。两者不是两套现金账，收付仍只写同一现金流水池。

### 4.4 “内部转账”到底是什么

Excel 的 `2025年3月份现金账!E3` 明确写“现金内部互转不计入开销”，`L3` 说明两个受管理账户之间转移。所以该业务不是凭空增加，但当前按钮名称和位置缺乏解释。

例如，仅作虚构说明：现金模块内 A 账户转给 B 账户 1000 元。A 减少 1000，B 增加 1000，整个现金池总额不变，不作为新的经营收入或开销。**这只是记录已经发生的资金转移，App 不替用户真正转账。**

边界要求：

- 两端都必须属于现金模块管理的账户；不是在现金池与 App 普通流水池之间搬数据。
- 只产生一个转账业务记录，两个账户余额同时变化；若一端失败则整体不保存。
- 信用卡是待还/代付账单，不是现金账户；还款不能因收款方是银行而认定为池内互转。
- Make 目前把信用卡还款标成内部转账且只表现支出腿，不能采用该规则。

UI 将互转收进“新增流水”菜单，名为 **“现金账户互转”**：日期、转出账户、转入账户、金额、说明。抽屉只是录入载体，不是另一个模块；不能把互转记成开销。

## 6. 后端架构与模块 I/O

### 6.1 最小结构

```text
CashPage（局部 UI 状态）
  → cash 专属 API client
  → cash route（认证、页面授权、参数/响应映射）
  → cash service（业务规则、事务编排）
  → cash repository（SQL、持久化、只读组合查询）
  → 现有 PostgreSQL 中的 cash.*
```

查询与写入方法在清晰边界内分开，文件变大或有实际复杂度时再分 query/command 文件。不预建工厂、适配器套娃、插件平台或通用报表引擎。service 接收明确 repository、时间来源等必要依赖，不接收整个 Application；不读 HTTP cookie，不生成 HTTP response。SQL 留在 repository。

### 6.2 I/O 约束

| 模块 | 输入 | 输出 | 禁止 |
| --- | --- | --- | --- |
| 身份/页面授权 | 现有可信 session、页面 ACL | 账号身份、现金页面是否可用 | 前端 body 冒充 actor；重建权限档位 |
| 现金录入 | 经确认的字段、可信 actor、编辑版本；自由选择或既有现金事项的项目上下文 | 一个现金事实及必要的本模块事项关联；历史结算项目由服务端沿用本地事项 | 普通流水/发票写入、全局操作历史、重复报表副本；借历史结算新建事项/改项目/混项目 |
| 现金删除 | 现金页授权、流水 ID、预期版本；本模块已有任务/事项关联 | 单事务移除该流水及其结算影响、校正相关任务/事项；现金视图重读 | 只隐藏一张表、逐本账分次删除、误删独立事项/其他流水、后台补偿、OA 读取/写回或全局历史 |
| 每月任务 | 任务模板、月份、实际处理输入 | 本月处理状态；确认收付时引用现金流水 | 到日自动伪造付款；未付生成流水；跨页通知读取现金数据 |
| 往来/冲抵 | 本模块事项、归还金额/类型、关联现金流水或票据事项 | 本模块事项结算结果 | 非现金冲抵生成现金支出；读取普通往来款页面 |
| 账簿查询 | 授权、期间、筛选、排序、分页 | 当前现金视图 rows/summary/pagination | 全量浏览器聚合；逐行查询；后台重建报表 |
| 现金配置 | 本模块账户、分类、允许 OA 阶段与任务设置 | 现金专属配置 | 写入全局 settings payload，或通过配置修改 OA 项目 |
| OA 项目读取 | OA 集成 owner 的项目只读方法、阶段字典、查询条件 | 有界项目列表、真实阶段及读取时间 | 读取付款/报销/发票；OA 写回；普通 App 的项目完成/删除 override |

共享身份及页面 ACL 属安全控制面，不属于现金或普通流水池。现金账簿查询只读取 cash.*；OA 项目选择走第 6.6 节的窄只读边界，不加入账簿 SQL。不得跨 schema JOIN 普通财务事实，不建指向普通流水/发票/OA 业务表的外键。OA ID 作为来源标识保存，不建立跨数据库外键。

### 6.3 同库隔离与数据库访问

建议在同一数据库内使用 `cash` schema。它只是表的命名空间，不是新数据库。用 `cash_*` 表名前缀也能表达归属，但 schema 更清楚；**仅命名不同并不能阻止错误 SQL 读到现金表。**

为落实“其他页面严禁读取”的要求，推荐一个同库的现金专用数据库运行角色及有界连接入口，复用现有连接池实现，不创建另一套持久化框架：

- 普通 App API/worker/通用查询角色不获得 cash schema 的业务表权限。
- 现金 repository 只使用现金专用连接；该角色不获得普通业务表、audit.events、job.* 的读写权限。
- 认证和 ACL 仍先经过现有安全边界；现金业务 service 不自行读取全局设置。
- 不依赖 search_path 隐藏表，使用明确 schema；迁移拥有者与 API 运行角色分离。实施时检查默认 GRANT、角色继承及 owner 权限，而不是假设已经正确。
- 不把现金角色授予普通运行角色，不依靠同一连接反复 SET ROLE 实现隔离。两边连接数量合并纳入现有 PostgreSQL 总预算。

具体失败场景：未来普通统计代码误写 `SELECT ... FROM cash.flows`。不同表名、主键、事务和类型不会拒绝这条合法 SQL；普通测试不能穷尽未来查询。数据库最小权限可以在这条安全边界上直接拒绝。因此这是针对明确隐私要求的权限隔离，不是新增用户角色档位，不需要 hash 或新 gate。

这仍不是抵抗整个服务器被攻陷、数据库超级用户或合法备份管理员的物理隔离；同一进程、同一数据库仍共享故障和资源边界。不得承诺“绝对不可见”或“零影响”。本次未连接数据库核实实际部署角色，也未更改任何 GRANT。

只增加实现隔离必需的现金运行凭据，不增加用户权限层级、RLS 策略平台或多租户系统。检查角色时还要覆盖 PUBLIC/default privileges、SECURITY DEFINER 函数和视图是否形成旁路。角色访问控制与快照语义采用 PostgreSQL 原生能力，分别参见[权限说明](https://www.postgresql.org/docs/current/ddl-priv.html)和[事务隔离说明](https://www.postgresql.org/docs/current/transaction-iso.html)；不要求升级数据库版本。

### 6.4 全局操作历史必须从入口排除

已查到现有 `backend/src/fin_ops_platform/app/server.py`：`handle_request` 会记录 mutation completion，`_handle_request_untracked` 会在写操作前记录 requested。**仅让 cash service 不调用 audit，不足以满足用户要求。**

实施设计应采用一个明确、仅对现金已登记路由生效的记录策略；前后两个通用审计位置使用同一决策。现金写请求仍是写请求，仍通过鉴权、输入校验和适用的安全检查，不能伪装成只读 POST 来逃避审计。

需要验证的完整出口：HTTP requested/completed、service 审计、repository/数据库触发器、导出审计、领域事件/job、异常元数据和前端全局状态。现金业务内容不得进入全局历史，不能“先写进去再在操作历史页面过滤掉”。失败请求和配置操作同样适用。其他模块的 requested 写入失败即拒绝业务等现有保护保持不变。

全局 HTTP 性能/安全日志与操作历史不同。保留不含业务内容的技术信息，不记录金额、人员、项目、账户、请求体、响应体、原始查询字符串或动态业务 ID；路由使用不含业务 ID 的模板或粗粒度类别。现金详情不进入全局搜索、通知摘要或 App Health。

当前 App Health 会编排各页面事实审计；新增现金页不能机械加入全局现金条数/金额查询，也不能为满足页面数而伪造“现金已审计”。设计为明确的数据隔离排除项，保留现有普通页面的审计要求；现金业务一致性在本模块测试/受控验证中完成。不新增“现金审计”页面或本地日志引擎。

005 在现有设置页修改页面可用性属于既有安全控制面操作，建议继续保留既有 ACL 审计，不包含现金流水/任务内容。这与现金页面内操作不入全局历史区分；若用户要求连该控制面授权变更也不记录，须单独审阅，不能顺手删除既有安全措施。

### 6.5 隔离还涉及哪些外围

- 其他页面、全局侧栏 badge、全局搜索/导出/报表不请求或缓存现金事实。
- 退出现金页面后卸载页面及其抽屉；不把现金 rows、摘要、人员、金额或搜索正文存到全局/localStorage/sessionStorage。可只保留非敏感 Tab/期间/分页偏好；初版也可不持久化这些偏好。
- 撤权、退出登录、账号切换后，清理现金内存状态；旧请求不能重新填入页面。
- 既有 App 外层仍有 session、health 等全局 provider，不为现金重建第二套 App；现金不向这些容器发布事实，也不订阅普通财务状态作自己的事实源。“现金不触发普通业务取数”不等于承诺现有身份/安全技术请求在该路由全部停止。
- 现金响应不落浏览器持久缓存；敏感检索值不放页面 URL、浏览历史或全局状态。复用基础请求能力时核对服务端/代理技术日志及响应缓存策略，防止遗漏查询字符串出口，不新建缓存层。
- 全局业务重置不得顺带清空 cash.*；现金资料不加入普通文件池或公开附件预览。附件不在当前范围，不建上传功能。
- 同库备份通常会包含 cash.*，备份读取者可能看到现金数据；须沿用并核对备份访问和恢复权限，不能把页面隔离误说成备份隔离，也不能通过不备份来“保护”现金。
- “同一现实交易不在两个池中重复录入”与技术隔离不同：系统不会跨池复制，但在禁止互相读取的前提下，也不能自动跨池查重。应先确认业务归属，由录入流程明确提示；不能新增跨池金额比对或 hash。

| 已结束 | 设置及历史中展示；禁止自由新增/改选；既有现金事项真实结算沿用原项目，不加入可选下拉 |

十个名称是核查时的源数据，不是新的硬编码枚举。用户之前的五个名称是估计，已明确不作为分组或映射目标。

**最小实现建议：**复用 OA 集成 owner 的连接、认证配置和只读查询基础，在该 owner 内提供窄的项目资料方法；现金 service 接收这个明确依赖。列表读取真实项目 ID/编号/名称/阶段，阶段选项从 OA 表单定义或权威字典读取，不能仅对当前项目的阶段去重，否则没有项目使用的阶段会丢失。只投影需要的字段，不读取附件、付款申请或报销单。不复用带 `active` 假状态的项目 DTO，不为现金重写普通 App 的项目行为。

现有 OA 边界禁止财务页面在 HTTP 中直读 Mongo/inline sync。本设计提出的是**仅项目基础资料的按需只读例外**，实施时必须同步 OA `boundary-io.md` 明确允许方法/字段；绝不扩大为财务事实直读、全量 OA 同步或浏览器直连。若实际基础设施无法提供有界项目只读方法，先报告事实与延迟，再修订这一项；不私自改用全局项目快照兜底。

| 操作 | 来源与输出 | 写入 |
| --- | --- | --- |
| 打开“OA 项目”或点击刷新 | 读取当前 OA 项目/阶段，返回总数、分页、`read_at`；设置中可查看所有状态 | 无 |
| 打开自由新增流水的项目选择器（`selection`） | 按现金允许阶段过滤；已结束、空/未知阶段不进入候选 | 无 |
| 保存允许阶段集合 | 校验真实字典、排除结束编码；检查本地配置版本 | 只写 `cash.settings`，无全局 audit/无 OA 写 |
| 自由新增或改选项目（`selection`） | 服务端按稳定 OA ID 再读该项目及阶段，再检查本地允许集合 | OA 零写；现金事实与关联在现金事务内提交 |
| 登记期初未结历史义务 | 仅 `is_opening=true` 的 `loan` / `company_receivable` 使用 OA `all` 识别真实历史项目，含已结束，不受新增允许阶段筛选 | 只建真实期初事项，不产生 flow、不开放普通现金新增；真实项目身份与既有现金快照皆无则报资料缺失 |
| 从既有现金事项办理真实结算（`existing_item`） | 服务端读取该事项本地项目 ID/名称快照及版本；项目只读沿用，不请求 OA、不复核当前可选阶段 | 同一现金事务校验事项、版本与额度并写实际收付/结算；不新建事项、不改项目、不混项目 |
| 查询历史账/修改无关备注 | 使用该笔现金记录保存的 OA ID 和项目名称快照 | 不因项目结束或 OA 不可用而拒绝历史查询；不改归属就不重验候选 |

- 初始允许集合必须显式保存，不自动把“除了已结束之外全部允许”当成用户已确认；新出现的阶段默认未选。无法识别的阶段在设置中如实标识，不能改成 `active` 或“其他”。
- 没有项目归属的真实收付仍可明确选“无项目”，不查 OA、不要求先配置允许阶段；这不允许把有项目的既有事项改成无项目来规避限制。
- 不新增 `cash.projects`、项目同步表、定时 worker、消息队列或常驻服务端轮询。现金记录保存必要的项目名称快照用于历史显示及既有事项结算时沿用归属，不是第二套项目主数据，不作为自由新增候选。
- 页面会话内复用本次已成功读取的选项，手动刷新和重新打开录入时重读；不持久化到全局状态或浏览器磁盘。只有项目区域在用时才请求，报表筛选、翻页不触发 OA。
- 历史账簿的项目筛选选项从 cash.flows/items 中已有项目 ID/名称快照做有界去重，不使用新增录入的 selection 候选接口；同一 ID 在不同记录出现历史名称时明确按本地最近记录的名称展示选项，行详情保留各自快照。这样已结束/已从 OA 删除的项目仍能筛选历史，也不发生查询时逐行补资料。
- 当前 OA 资料更新含义是“按需重读 + 自由选择提交前复核”，不是零延迟推送。OA 与 PostgreSQL 不存在同一事务；复核后 OA 再次变化的极短竞争窗口无法在禁止写 OA 的前提下完全消除。自由选择以服务端复核时刻为准，不为此建设分布式事务；既有事项结算始终使用现金本地归属，不走这条 OA 读取链。
- 提交先完成授权和原提交 ID 的持久化事实重放判断，再进行必要的 OA 读取或首次结算资格校验；已成功提交且最终项目、现金和原关联相同的重试返回已有事实，不因之后项目结束或已被该笔结清而拒绝。不将未存入数据库的 `mode` 当成可验证的原提交身份：它只决定首次资格路径，同事实 200 且零写，不同事实或已被修改的事实 409，不另存一套请求/mode/hash 库。
- 自由选择在 OA 请求完成后才开始现金写事务，事务内再检查允许集合版本与项目阶段适用性；外部等待不占用现金行锁。配置发生并发变化时明确提示重选。既有事项结算在现金事务内锁定并复核本地事项/关联版本与实际结算资格，不读取或要求当前阶段配置版本。
- OA 故障时自由项目选择/需要新项目验证的提交明确失败，保留未提交表单；历史查询与 `existing_item` 真实结算照常走本地现金事实。不读取老项目表、硬编码阶段或空成功响应兜底。源读取有分页时必须保持完整总数/分页语义，不能把第一页说成全部。
- `existing_item` 仅用于结算已经存在且有真实可结算额度的现金事项；同笔所有关联事项必须与锚定事项项目一致（无项目也按同样一致性校验）。不能仅引用一个历史 ID 就跳过校验，不能夹带新事项、补建本金、改项目或混合项目，也不能把普通财务事项当现金事项。服务端确定项目 ID/名称快照，客户端不得提交替代归属；资格/版本失败整笔拒绝，不自动切换 `selection` 或清空项目。该规则同样适用于任务确认中的实际收付，不需要新增表、后台同步或例外开关。
- 在现金设置管理允许阶段属于现金页面正常能力，所有现金页获权账号均可用；这不授予管理其他账号页面权限的权力，该权力仍只属于 005。

## 7. 数据与业务闭环（设计，不是已执行 DDL）

### 7.1 事实按业务存储，不按工作表存储

下列是实现已确认业务的逻辑实体，不代表表已经存在或本轮已执行 DDL：八类核心实体，加最小账单别名字典及已删除身份技术表。账单别名字典只解决同银行两张卡跨月稳定归组，避免名称变动或某账单删除改变矩阵身份；不存卡号、额度或导入账单。不机械守住八表，也不为每个 Tab 建表或把不同事实塞进任意 JSON。

| 实体 / 暂定表 | 保存什么 | 关键关系或约束建议 |
| --- | --- | --- |
| 现金账户 `cash.accounts` | 本模块账户名称、启用/期初时点、确认后的期初金额、启停 | 独立 ID；期初时点规则明确，不从普通银行余额推导 |
| 现金设置 `cash.settings` | 允许 OA 阶段代码集合与配置版本 | 固定一条配置；只保存本模块配置，不复制 OA 项目主表 |
| 费用类型 `cash.categories` | 收入/支出/往来分类 | 分类与现金方向分开；具体分类日后配置，收/付款必选、互转不选择并提交 null |
| 现金流水 `cash.flows` | 实际日期、金额、流入/流出账户、内容、分类、来源、OA 项目 ID/名称快照及本模块关联 | 唯一现金事实；不保存月账/年账副本；一月任务可有多笔，一 flow 最多关联一任务 |
| 任务模板 `cash.task_templates` | 内容、默认月执行日、提醒天数、现金收付或核对类型、启停 | 模板修改不能回写已经确认的历史发生事实 |
| 月度处理 `cash.task_occurrences` | 模板对应月份、当月执行日/处理状态、实际确认信息、关联流水 | `任务 ID + 归属月份` 唯一；不是后台 job 表 |
| 业务事项 `cash.items` | 借款/往来、账单义务、票据来源、费用、公司应收 | 固定类型分别表达真实义务/费用/来源，不复制现金；费用只确认一次 |
| 处理分配 `cash.settlements` | 现金归还、票据使用/票抵、无票冲抵及费用退款等明确处理 | 同项目可多事项；ticket_use 可无抵债目标，ticket_offset 必有目标；同一次使用转票抵不重复占额 |
| 账单标识 `cash.bill_labels` | 稳定 ID、银行名、别名、启停与版本 | 最小本地字典，用于跨月区分同银行不同卡，不建设信用卡系统 |
| 已删除身份 `cash.deleted_submission_ids` | 已删 flow/item 的 entity_type 与 ID | 不含原正文，仅防延迟旧创建复活；无用户列表/恢复入口；分配旧重试由相关版本保护 |

字段与最少约束如下；人民币两位、单项目、分次任务及删除语义均已接受。技术命名/尺寸和各类型适用矩阵由技术稿落实，不要求用户再决定 SQL 字段。

这里是模型概要，不是全部字段表。完整类型/精度/空值/默认值/写入来源/可修改性在[技术设计§2–3](../dev/cash-module-technical-design.md)，事务版本传播在其§5.7，完整列表/详情/选择器/汇总DTO在§8.7。普通银行流水仍属原`app.bank_transactions`；手工录入只是产生`cash.flows`的入口，与任务确认共用同一现金模型，**不再建“录入流水表”或把普通银行字段复制进现金表**。

| 实体 | 拟议关键字段 | 约束/读取路径 |
| --- | --- | --- |
| accounts | `id, name, kind, opening_date, opening_amount, enabled, version` | kind 为实物现金/储蓄；引用后不硬删；期初只生效一次；停用不移除历史余额 |
| categories | `id, name, enabled, version` | 按 ID 关联；名称变更不修改历史事实含义；不得凭分类决定非现金事件是否生成流水 |
| settings | `id, allowed_project_stage_codes[], project_selection_configured, personal_opening_date, version` | 固定 ID、版本 CAS；阶段是否配置明确存储，个人起算更正不误判阶段已配置；不写 App settings |
| flows | `id, occurred_on, kind, amount, from_account_id, to_account_id, category_id, oa_project_id, project_name_snapshot, person_name, source_kind, task_occurrence_id, content, remark, created_by_account, created_by_name, version, created_at, updated_at` | 来源/身份由入口及 session 确定；稳定 ID、正金额、账户组合约束；物理清正文，不加 posted/void/deleted_at 双路径 |
| task_templates | `id, title, kind, execution_day, remind_days, effective_from_month, effective_to_month, enabled, version` 及确认后的默认表单字段 | 生效月份有序；任务不能被无条件追溯生成到启用前月份 |
| task_occurrences | `id, template_id, month, due_on, planned_amount, processing_state, template_values_snapshot, version` | 月唯一；目标与有效现金累计分开，核对任务目标为空；快照不保存流水副本 |
| items | 基础 ID/type/对象/日期/金额/项目/来源版本；条件字段包括义务方向、账簿分组、账单月及稳定账单标识、票据提供信息、内容/备注 | 字段适用性见技术 §3.8；不混淆债务对象、报销人、提供人；origin_flow_id 仅表达源所有权，同卡按 bill_labels ID 跨月归组 |
| settlements | `id, item_id?, flow_id?, source_item_id?, kind, amount, occurred_on, version` | 目标按类型必填；无目标使用不减债务，票抵有两端；现金/非现金来源互斥；同事务按固定义务/费用口径分别验额度，不相加冒充现金 |

所有时间/actor 仅保存必要业务溯源，不引入私有审计事件平台。录入人需要显示时由可信 session 写入现金记录，不读取全局操作历史补齐。未决定的人员字典、票据附件、币种扩展不提前建表。

删除按真实所有权处理，禁止无差别级联事项、模板或其他现金。目标专属分配与正文同事务移除，独立事实保留并校正。物理删除同时保留最少已删除身份，见第 7.5 节；不存在的原主键不能独自识别旧提交。

当前范围是单 flow 一个项目或无项目，可分配多个同项目事项；无项目不造“其他项目”。复合创建需要多个事项时使用一个有界 related_items 列表，不并存单项别名。跨项目金额拆分不在本次范围，不预建分摊表；未来明确提出后再改项目金额归属，不能现在复制现金或随意挂一个项目掩盖真实跨项目付款。

项目上下文不增加业务实体：`selection` 为自由新增/改选，选择非空项目时经真实 OA 阶段校验，无项目不查 OA；`existing_item` 为既有现金事项的实际结算，由服务端沿用锚定事项本地项目 ID/名称快照。后者不新增事项、不补建借款来源、不改变任何项目归属；同笔多事项仍须同项目，并在事务内校验实际结算、版本和额度。历史项目结束或 OA 源不可用不阻断这条本地结算链，不能将其扩成自由选择历史项目的旁路。

已真实发生的独立借款仅迟录现金时，用origin_items绑定原ID/原额/实际日期，不另造本金；已有费用付款只用expense_payment关联。origin_mode明确区分随flow新建的事项与既有借款补绑定：后者删除现金只解除来源，不误删真实借款。尚未实际代付账单只作为月任务计划，不提前造真实个人债务。

个人账有独立的声明起算日期，在现有“账户与期初”中小分组设置，再手工登记该日未结事项；不是先要求录完才能设日期。未配置/起算前未知，覆盖后零代表没有已录贡献，不证明资料已全部核对。与现金账户期初分开，不通过最早借款日期猜个人账范围。字段、CAS和并发锁见技术稿§3.4。

期初未结初始化具体化：现金资料为空也可以登记起算时真实存在的旧义务；仅 `is_opening=true` 且类型为 `loan` / `company_receivable` 的独立非现金事项采用历史项目识别，可读取 OA `all` 的真实 ID/名称，包含已结束项目，不要求符合新增现金允许阶段。原项目在 OA 已不存在时必须有可核验的既有现金项目快照；两者皆无则明确资料缺失，不按相似名称猜 ID、不擅改无项目。金额为起算时未结部分，不回造旧现金或再次累计已包含的本金；既有初始记录仍受普通 ID、类型、日期、版本和输入校验约束，不增加导入器/初始化平台。普通非期初事项及现金自由新增仍遵守原项目选择限制。

这属于 R3 已要求的期初初始化的具体实现边界，而不是新增 R8 或声称用户此前逐条确认了这项技术细节。登记完成后，真实后续收付按 R7 从既有事项结算，项目本地只读沿用；不能把两步合成任意选择已结束项目的新现金/新义务快捷入口。

支付办理说明是本地只读参考文本，不预建 CMS；票据只登记来源、使用与抵账/回款关系，不新增普通发票库或 OCR。

“业务事项”与“现金流水”不是两个互相竞争的现金池。例如一笔应还债务是义务事实，实际归还现金才是现金事实；用票冲抵是债务减少事实。各自只保存自身含义的金额，使用 ID 关联而不是复制现金流水供报表读取。

### 7.2 收付、转账、余额

一条 flow 使用一个正金额和明确收付方向：收款只有转入账户，付款只有转出账户，互转两端非空且不同。资金账户仅为实物现金与纳入管理的储蓄账户；信用卡作为账单/义务，不计信用额度余额。互转只有一个事实，查询贡献两端，不建设通用分录系统。

- 采用人民币两位小数，Decimal / PostgreSQL numeric 和 API 十进制字符串，不用浮点累计。技术尺寸见技术稿；拒绝超精度、NaN、Infinity，不用数据库舍入代替输入校验。null 显“—”，已知零才显 0.00。
- 业务日期用日期类型，系统处理时间用带时区时间；月份/提醒按 Asia/Shanghai 业务日期处理。
- 账户期初只在一个经确认的起算时点生效；查询开始不早于账户起算时，查询期初=起算金额+起算后、查询开始前净变动，查询期末=查询期初+期间实际流入−实际流出。全池互转净额为零。
- 查询完全早于起算时显示未启用/未知；跨起算日期时明确“仅自起算日起”，完整期间期初为空，并单列已知起算余额。不同起算日的账户逐一说明覆盖范围，不倒填未来余额或伪造全期间期初。
- 汇总展示建议：全池“本期现金收入/支出”只统计池外收付，不包含池内互转；分账户“流入/流出”包含互转，并单列或标明其中的互转金额。不能仅保证净额为零，却把全池收入和支出同时放大。
- 本期“现金支出”与“真实花销”分开。还借款、垫付等可以改变现金但未必构成真实花销。
- 建议账序按 `occurred_on, created_at, id` 稳定排序；同日未要求手工先后调整时以录入时间及 ID 消除同值歧义，不新增排序引擎。逐笔余额以账序计算，不跟着金额排序或搜索重新定义；索引/分页游标必须使用同样的确定性末级顺序。
- 不默认存储每月余额快照、每本账汇总表或每行可编辑余额。初期有界 SQL 足够；出现测量证据后才评估优化。
- 补录只在已知起算范围内；更早真实记录先明确更正起算日与相应期初，不再叠加原期初。可更正期初/起算日并提示全部后续影响；新起算日不能晚于已有有效流水而遮住旧事实。
- 允许暂时负余额并提示核对，不阻止真实补录、不自动造收入补平、不加审批。真实退款另记实际现金，费用退款只减原费用一次；删除记账不等于真实退款。
- 起算未结义务与资金期初分开；跨年余额按以前剩余事实承接，不同时累计期初已含旧欠款。提前代付按实际月记本金，账单月仅作独立归属。

### 7.3 任务确认的事务闭环

1. 模板定义默认日期及提前提醒天数；生成的是本月应处理事项，不代表钱已支付。
2. GET 将有效模板派生待办与已有月份记录组合，零写、零入队。首次办理/调整创建实例；模板写操作还会按下述边界保存必要旧月快照。
3. “未收/未付/未还”不产生 flow、不代表完成，保留待办和到期/逾期提示，不反复弹窗。
4. 收付任务明确当月目标，默认金额只是用户显式预填；未知目标显示“待填写本月金额”，可在首次确认表单同时填写目标和本次实际金额。确认实际日期、金额、账户及归属后才提交，不取 0 或上月数值兜底。
5. 同一事务内锁定/创建唯一月度记录，检查状态与版本，保存 flow、事项关联、处理状态。任何一步失败全部回滚。
6. 同一提交 ID 重试不新增，不同内容冲突；一个月实例允许多笔实际收付。按有效现金累计与当月目标判断未处理、部分办理、已完成；达到目标即完成，超额明确“超出计划”，不截断现金或改计划。债务分配仍不能超额，真实多付部分明确保持未分配。
7. 提交成功后只重新读取当前现金视图；不通知普通账、全局状态或后台报表链。
8. 已手工录过的现金由用户明确选中关联，校验方向、账户、金额、项目和认领情况；一笔 flow 最多一个月任务。保持 manual 来源和原有结算，仅补任务关系；已经完全分配不等于不能认领任务。归属冲突明确拒绝，不覆盖原分配、不按同日同额猜匹配。
9. 核对/催办任务使用“核对完成”分支，只保存当月处理状态与必要说明，输出无 flow；不得要求收付金额/账户，也不得悄悄调用现金新建方法。与“未处理”区分，完成与否不制造金融事实。

任务新建实际收付采用与手工录入相同的项目规则：自由选择走 `selection`；从既有现金事项真实结算走 `existing_item`，沿用本地项目且不查 OA，不能因任务入口而创建结束项目的新事项或混项目。认领已录现金只校验和保留其本地归属及关联，不把认领当一次新的项目选择，不重复现金或原分配。

防重复依靠主键、月度唯一约束、行锁、版本检查和事务，不增加内容 hash。手工录入重试可采用一次提交稳定的记录 ID；同内容重放不新增，不同内容明确冲突，不建立通用 hash 幂等平台。

首次确认若已成功但响应丢失，先识别可证明的原现金确认结果，再判断首次空版本；不能因为月实例已经建立就把成功重放一律判409。复合确认比较现金、自己新建的事项和分配完整意图，不只比金额；只读返回原结果，不重做结算。核对/未付/调整等无现金命令用普通版本冲突+重新读取即可，不另建命令表。更正关联须同时校验并更新flow及受影响事项/月实例版本，具体传播见技术§5.7。

分次删除后按剩余有效金额重判任务，不能一律清零。模板和月度实例不因现金删除消失，旧确认重放不能补回已删现金；核对任务不需要目标或实际金额，可纠正错误核对状态。

未办/部分办理跨月保留在“逾期待办”，按原归属月显示；不追造模板使用前历史。当月调整独立，模板更改只作用未来，已形成的办理/待办保留原值。复用 templates/occurrences 与必要快照，不新增 worker 或模板历史平台：

- 模板创建从当月或未来生效。GET 先查已有实例，再从当前有效区间计算缺项，并分页；GET 不保存实例。
- 旧模板仍启用时，写操作在同一事务按旧值补齐“旧有效起止区间 ∩ 截至当前月”中的缺失月份，再更改未来模板；不覆盖已有实例。
- 停用先保存停用前应保留的旧月份并明确停止范围；已停用模板的编辑或重新启用不补停用期间，重新启用使用新的明确生效月。
- 未来已单独调整的实例保留自身数据，模板停用不能隐藏既有旧待办；集合补齐受月份范围和短事务测量约束，不靠后台补偿漏月。

任务来源与已关联的手工现金都可从现金流水统一编辑/删除，关联版本与金额同事务更新。不得“有引用就禁删”，也不能绕过来源所有权直接改金额；源事项纠正见第 7.5 节。

### 7.4 非现金冲抵闭环

提供票据只登记来源、提供人和金额，不增加现金或减少债务。使用可分次、多目标，占用总额不能超过来源可用额；无抵债目标时使用记录可不带目标，不能伪造债务承接。票抵必须同时有来源和目标，减少目标义务；**ticket_use 转 ticket_offset 是更正同一记录**，来源占用不再扣第二次。技术稿按固定类型定义条件目标，不新建发票库或状态引擎。

登记无票/其他明确冲账时选择目标、类型、金额、实际日期和说明，校验目标未结额度；没有票据来源就不造票据。有票处理同时校验来源可用额和目标未结额，全部在同一事务受锁校验；现金归还则引用已有 flow 的可分配额，不再建现金。

公司应回款必须作为真实公司应收明确建立，不能由交票自动产生。收到回款时登记一次收入并结该公司应收，不能再次冲减已经票抵的个人欠款：刘欠 1000，票抵 100 后欠 900，公司随后回款 100，刘仍欠 900。

允许更正/撤销错误非现金分配：事务内释放旧来源占用和目标贡献，再校验新值/新目标；失败保持原状，其他真实使用/现金不可误删。无现金处理始终不改变现金余额。撤销后来源/目标版本推进，使旧 POST 不能用旧预期版本重建；不为此复制非现金删除 ID 平台。

### 7.5 删除现金流水：全现金模块一致生效

**已确认的用户行为：**现金流水 Tab 完整列出全部未删除的手工和任务流水，提供单笔删除。删除成功后，该笔流水不再出现在任何现金账表、关联明细或普通详情接口中，也不再计入收付、余额、还款、回款、冲抵或其他由它贡献的汇总。不是仅隐藏一行，也不是保留一条仍参与计算的“已作废”行。未要求批量删除、回收站、恢复界面、私有操作历史或删除审批。

| 受影响内容 | 删除后的要求 |
| --- | --- |
| 现金流水列表/详情 | 移除目标；分页总数、筛选合计、来源筛选和余额重新查询；原详情地址不再返回该笔业务内容 |
| 往来账总表、有票支付、刘树刚账及其全部子表 | 移除这笔流水在各处的明细与金额贡献；汇总行保留其他事实的结果，不删除整个人/项目/月份 |
| 归还/回款/冲抵分配 | 移除目标专属贡献；独立借款、费用、票据使用、其他真实现金/非现金保留；仅由其建立的源事项按下方明确纠正规则处理 |
| 月任务 | 保留模板/月实例；按剩余有效金额对当月目标重判，唯一收付被删不能仍显示已付，分次不一律清零 |
| 账户余额与后续期间 | 删除往期收入/支出后，后续逐笔余额、月份期初/期末、全年及分账户汇总均按剩余事实计算；互转同时移除两账户变动，全池净额仍为零 |
| 现金项目/对象筛选 | 不从已删除流水提取候选；相同项目/对象还有其他有效事项或流水则继续保留；OA 项目设置本身不变 |

例如仅作虚构说明：某借款应还 1000，已还 200 和 300；删除还款 200 后，保留借款和还款 300，已还变为 300，未还变为 700。不能删除整个借款，也不能让已还仍为 500。删除记账记录不等于现实中撤回银行付款；真实退款应另行记录实际收付，不能靠删除伪装资金退回。

最小处理过程：

1. 现金页权限下展示目标及已知关联影响，用户一次确认；不增加 005 专属删除档位。版本发生变化时提示重新查看，不默默覆盖别人修改。
2. service 在一条现金事务内按统一顺序锁定目标流水和受影响的任务/事项，重新读取关联并核对版本。新增分配、编辑、任务确认也遵守相同锁/版本约束，不能与删除竞争产生悬空关系。
3. 同事务移除流水及其专属分配影响、校正必要任务/事项状态。任何一步失败全部回滚，不先报成功再靠队列逐表清理；不增加反向现金流水作为暗中替代。
4. 提交后只重读当前现金视图；失效的本页面其他账簿/任务数据不再复用，切换时重读；取消/忽略删除前旧请求，避免已删行重新出现。其他浏览器会话在后续刷新/读取时看到提交后事实，本需求不默认新增跨会话推送。
5. 删除不检查项目是否仍可新增选择，也不依赖 OA 在线；不调用普通财务池、全局历史、App Health 或全局 job。只锁目标涉及的现金资料，不全表重建报表副本。
6. 重复删除不能重复调整金额/任务；旧创建、旧任务确认、旧编辑请求不能使已删流水复活。用户明确重新录入/确认是新提交，不能由刷新、提醒或旧重试自动再生成。

**已确定的存储和源事项纠正：**

- 物理删除在线现金业务正文和专属分配，只保留最少已删提交 ID，不含金额、人员、账户或备注；无回收站/恢复入口/私有审计。原内容不再由业务接口可读；既有受保护备份不随单笔删除销毁。
- 删除正文和保留 ID 必须同事务。针对“创建成功→删除→原创建延迟重试”，按技术稿的原生事务/ID 方案拒绝复活，不加 hash 或通用幂等平台。重复删除只确认已删、不重复改余额；未知 ID 与已删 ID 的接口语义由技术稿统一。
- 允许编辑错误现金/事项及其关联。来源借款 1000、已还 200，更正真实本金为 800 时同步校正源现金/事项，真实还款保留，剩 600；不由此改掉独立原义务。
- 最初借款不存在：移除错误源现金及仅由其建立的借款；真实收款 200 保留，解除错误归还分配后显示未分配，不造退款/新债务，不后台把假借款转独立。无后续结算时直接清掉该错误来源事项。
- 借款仍真实而来源重复/录错：在同一纠正输入中明确正确来源，或由用户明确确认独立原义务；不能仅凭系统需要就保留无依据债务。
- 有后续真实非现金事件，或改为 100 却已还 200 时，同一纠正操作必须明确调整受影响分配；错误分配可撤，独立真实事件不可误删。没有正确目标时不伪造、不截额，不先删源后留下半状态；普通还款删除无须这些源归属步骤。
- 费用事项同样按真实所有权区分：已独立成立的费用不能随一次错误付款删除；付款与费用同时误建时在源事项纠正中一并处理，不复制费用/退款补平。删除造成暂时负余额仍如实提示，不新增负余额禁删限制。

## 8. API、提醒和性能方案

### 8.1 API 家族草案

以下是待实现的设计接口，不是当前可调用功能；DTO 按已确认业务和技术稿收口，错误格式沿用现有 App。

| API 家族 | 范围 |
| --- | --- |
| `/api/cash/flows` | 手工收付/互转、全部现金分页/详情、编辑及统一单笔物理删除，关联一次事务校正 |
| `/api/cash/reports/...` | 往来账总表、有票支付、个人账的本模块组合查询；删除规则与流水一致 |
| `/api/cash/tasks`、`/api/cash/task-occurrences/...` | 模板/月目标配置、当月及逾期待办、分次实际确认、核对与未处理登记 |
| `/api/cash/items/...`、`/api/cash/settlements/...` | 固定义务/费用/来源事项，现金分配、票据使用/票抵、无票冲抵与纠正，不做动态 CRUD |
| `/api/cash/settings/...` | 现金账户、费用类型、允许 OA 阶段集合；项目资料仅通过只读 projects 接口取得；不包含账户访问权限配置 |

进一步明确拟议请求（不是当前可调用接口）：

| 方法/路径 | 输入 | 输出与副作用 |
| --- | --- | --- |
| `GET /api/cash/projects` | `purpose=all/selection`、keyword、真实阶段/可选性筛选、page/page_size | rows含id/code/name/stage_code/stage_name/selectable/unavailable_reason；另有字典、分页、read_at、selection_settings_version/configured；缺失code/阶段明确null，源故障不伪装空成功 |
| `GET/PUT /api/cash/settings/project-selection` | PUT：`expected_version, allowed_stage_codes[]` | `version,allowed_stage_codes,configured`，PUT另有changed；未配置与显式允许空集合分开；只写现金配置，无OA编辑接口 |
| `GET /api/cash/flows` | 期间、账户、项目、类型、来源、搜索、排序、分页 | 全部未删除的手工/任务流水 `rows,summary,pagination`；来源与任务关联可见；summary 分开余额口径与筛选合计 |
| `GET /api/cash/reports/project-options` | 账簿范围、keyword、分页 | 从现金历史 ID/名称快照给出历史筛选选项，含已结束/已删除 OA 项目，不读 OA |
| `POST /api/cash/flows` | 稳定提交 `id` + 已确认表单字段；明确 `selection` 或 `existing_item` 项目上下文 | `flow,version`；首次 201，同内容重放 200，冲突 409；既有事项结算由服务端沿用本地项目，单现金事务 |
| `POST /api/cash/flows/{id}/delete` | 流水 ID、expected_version；源冲突时附明确纠正输入，actor 来自 session | 第 7.5 节全部影响同事务完成；只返有界关联摘要/计数，不返已删正文；重试不重复贡献 |
| `GET /api/cash/task-occurrences` | month 或明确提醒/逾期范围、分页 | 模板派生待办与已有实例，跨月未办保留；零写 |
| `POST /api/cash/task-occurrences/confirm` | template_id、month、预期/首次模板版本、月目标及实际输入；新 flow 稳定 ID 和适用项目上下文，或既有 flow ID/version | 允许分次，实际累计对目标判断；历史事项结算沿用本地项目；同事务，认领不重复现金或原分配 |
| `POST /api/cash/task-occurrences/mark-unpaid` | template_id、month、expected_version（如存在） | 未处理状态，不生成 flow；最终名称随收/付/还/核对语义统一 |
| `POST /api/cash/task-occurrences/complete-check` | 核对任务/月、当前处理版本，首次提交模板版本和必要说明 | 仅核对完成的处理状态，无 flow/settlement；不接受现金任务冒用 |
| `POST /api/cash/task-occurrences/adjust` | 任务/月、已有版本或首次模板版本、当月计划日/目标/说明 | 首次可建实例，只调当月，不改其他月份/真实收付 |
| `POST /api/cash/task-occurrences/{id}/reopen-check` | 预期版本 | 纠正错误核对为待核对，无现金变化 |
| `GET /api/cash/reports/turnover / ticket-payments / personal` | 每个视图自身的年份/月份/对象/分页 | 只读 items/settlements/flows 的组合，不生成账簿副本 |

任务模板、账户、分类与最小账单别名字典采用明确本地接口，不建设 CRUD 注册器。收付 confirm 与核对 complete-check 分开；首次月份动作带 expected_template_version，独立非现金纠正不能由现金删除冒充。精确 DTO、来源/目标版本、错误及事务以[技术设计](../dev/cash-module-technical-design.md)统一；日期 ISO、金额字符串、月份 YYYY-MM、分页与排序白名单，身份来自 session。OA read_at 是读取时间，不伪称源更新时间。

删除只调用一个现金命令，不提供逐本报表的删除接口。所有账表/详情/汇总及筛选选项必须使用一致的剩余有效事实范围；不提供绕过删除范围读取原文的别名接口。再次录入使用新提交身份，旧 POST 重放不能被上述首次 201 规则重新插入。

每条受保护 API 都登记为仅属于现金页，不能通过“拥有任一普通页面权限”放行。401/403、参数错误、对象不存在、版本或已结算冲突、数据库不可用要有明确响应。禁止先查询对象内容再决定用户有没有现金页权限。

读响应沿用直接查询，给出 rows、summary、分页及业务版本，不返回已退役 read-model 状态或刷新任务。导出不在当前范围，UI 可保留扩展位置，不默认实现下载或接全局历史。

选择器不是另一个事实池：已录流水选择复用cash flows，事项/来源选择复用cash items，返回明确资格、不可选原因、可分配/可结算额度与版本；完整详情子表从相同列表分页读取，不依靠当前50行猜候选或额度。既有事项结算候选按本地事实和结算资格读取，不按当前 OA 允许阶段过滤、不查 OA；它不是项目自由下拉。详情/删除摘要有界，但真正修改处理全部受影响关联；客户端重读所有相关现金视图，不拿预览数组逐项模拟数据库级联。

阶段配置首次显式保存空集合也属于完成配置；后续仍不允许自由新增/改选任何项目，但不再误提示从未配置，不阻断既有现金事项的本地真实结算。使用 `project_selection_configured` 显式布尔值表达：首次 PUT 即使保存 `[]` 也设为 true；settings 同时承载个人起算配置，不能用 `version > 1` 推断阶段已经配置，不新增配置状态平台。`selection` 嵌套新事项中选择的项目也必须只读复核；不能只验证顶层flow项目而遗漏子对象，也不在持有现金数据库锁时查OA。`existing_item` 首次提交必须带有效本地事项与版本和真实结算，项目 ID/名称由服务端确定；不接受新事项/改项目/混项目。重放比较最终项目、flow 和原关联等已持久化事实，不比较未存储的首次 mode；先于 OA 与当前已结清等首次资格判断，相同事实 200 零写，不同事实 409，不能用换 mode 新建第二笔。

### 8.2 仅现金页内提醒与明确日历规则

- 只在现金页面内按计划日、提前天数和未处理状态展示提醒；关页不发系统/邮件/OA 消息，其他页面无现金任务正文或金额，不新增调度器、worker 或通知中心。
- 重新进入、聚焦或跨业务日期时更新。未收/未付/未还继续显示待办与到期/逾期标记，不反复弹窗；跨月待办按原归属月保留。
- 当月不存在的 29/30/31 日取当月最后一天，页面显示当月具体计划日并允许调整；这是用户已接受的日历规则，不是隐藏兜底，也不改变银行约定或实际付款日期。
- 提醒日 = 当月实际计划日 − 配置提前天数，提醒可落在上月，归属月份不变。具体每项执行日和提前天数日后配置，不再作为设计前置问卷。

### 8.3 性能与不影响旧页面

- 仅当前现金页面懒加载与取数；不在启动、普通页面、全局状态中批量加载现金数据。
- rows、summary 与分页在一个短 `REPEATABLE READ READ ONLY` 快照中查询，避免表格和汇总看到不同提交。
- 日期/账户先限定范围，SQL 筛选分页与集合聚合，不在 Python/浏览器全量筛选，不逐行查询事项。
- 先使用日期、账户/日期、任务/月唯一键、事项关联键等与实际查询相配的少量索引；不为每个筛选任意建复合索引。
- 页大小、查询日期跨度、SQL 超时和连接等待有明确上限；具体值根据数据规模和现有模式确认。不能承诺无限行即时展示。
- 现金短写事务只锁现金记录；慢查询及时失败，不占满共享数据库连接。现金池连接与现有池合计预算，不能仅新增连接数。
- 沿用现有性能目标作为实施期测量参照（当前核心 GET p95 ≤ 1000ms、p99 ≤ 2000ms），不是声称现金功能已达到。用代表规模假数据、EXPLAIN/查询次数和并发读写实测。
- 同进程同库不可能理论保证零资源影响；通过局部改动、连接/查询限额和旧页面回归降低风险。不要为“高性能”预建缓存、物化视图或分区。
- OA 项目请求与现金报表分开，自由选择提交校验的 OA 等待不放在数据库事务内；慢 OA 不阻塞现金历史查询或既有事项真实结算，后两者不请求 OA，也不拉取普通账事实。性能目标与实际执行方案见实施计划第 6 节，不将当前尚未开发的功能写成实测通过。

R7 必须有正反两类算例：项目结束、源项目移除、OA 不可用及允许阶段未配置/空集合时，既有现金事项仍能通过 `existing_item` 完成真实结算，服务端沿用本地项目、OA 调用次数为零，现金/事项/任务及各账簿一致；自由 `selection` 仍拒绝结束/不允许/未知阶段，源不可用明确失败。同样覆盖首次提交中不存在或无结算资格的锚定事项、旧版本、客户端伪造项目、新事项、混项目的拒绝路径；并发编辑/删除事项不能绕过事务资格校验。成功提交后，即使原事项已结清或请求 mode 变化，最终项目、flow、原关联均相同的合法重放仍 200 零写且不查 OA；改变实际持久化事实则 409。UI 的历史项目只读与服务端限制必须同时成立，不能仅禁用控件。

期初空库算例：OA 中真实项目 A 已结束，起算时仍有公司应收 1000。用 `is_opening=true, type=company_receivable` 从 OA 全项目识别 A，只登记期初未结 1000，现金收付与余额不增加；以后实际收到 200，从该事项走 `existing_item`，即使 OA 不可用也只新增现金收入 200、应收剩余 800。必须另测：同样项目不能用于普通现金自由新增/普通非期初事项；冒用其他事项类型、没有真实项目且无现金快照、猜 ID 或改无项目均拒绝；已有期初不能因重试重复建立或回造旧流水。

隔离测试不能只验证页面“看不到”：需要数据访问角色权限测试、route/service/repository 负向调用断言、audit.events 写入零新增断言、正常旧页面写入仍有审计、旧页面金额不受现金写入影响，以及现金查询不依赖普通财务表。使用测试专有数据，不依赖用户真实 Excel。

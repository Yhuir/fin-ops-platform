## 1. 结论与本次交付范围

1. 当前 Figma Make 的视觉方向可以采用：沿用现有 App 外壳、紧凑工具栏、单行汇总、通栏表格、右侧抽屉。不重新设计品牌，不增加大卡片、海报式页头。

3. Figma 是视觉及交互参考，不能原封不动作为生产代码或业务规则使用；示例中的任务方向、内部转账和余额计算存在问题。
4. 已重新检查 Excel 全部 21 张工作表、全部已存储单元格、公式依赖、辅助区域、隐藏状态和一张嵌入图片。**结构审阅完成，不等于全部业务规则已确认，更不等于真实金额已逐笔审计。**

6. 现金收付与非现金冲抵必须区分。报表可以同时展示两者，但只有实际现金账户变动进入现金流水池。
7. 正确顺序是先确认最少必要业务口径与隔离边界，再并行细化 UI 和后端逻辑模型，最后确定字段/API/数据库并审阅完整实施计划。不是先把某一端实现完再补另一端。

## 2. 已确认要求与明确排除项

| 项目 | 已确认要求 |
| --- | --- |
| 数据库 | 使用现有 PostgreSQL；用独立现金表隔离，不使用另一数据库 |
| 现金事实 | 所有手工和任务生成的现金流水只进入现金流水池 |
| 双向隔离 | 其他页面不读现金业务数据；现金页面不读 App 普通流水、发票、OA 业务事实或普通报表 |
| 不重复 | 同一现金事实可以出现在多个现金报表中，但不能为每本账复制一笔流水；不跨池同步 |
| 公共能力 | 复用身份认证、页面访问控制、纯 UI 组件和基础技术设施，不复用普通账业务数据查询 |
| 操作历史 | 现金模块的录入、编辑、任务、配置等任何业务操作都不进入 App 全局操作历史 |
| 页面权限 | 每页只有“可用 / 不可用”；现金页面内各 Tab 不再分 guest/reader/editor/admin |
| 权限管理 | 只有现有固定账号 `YNSYLP005` 可以设置其他账号可访问的页面 |
| 录入 | 手工逐项录入；没有流水文件导入需求，不建设现金 Excel 导入器 |
| 字段 | 具体必填、选填、选项和校验在设计相应步骤时向用户确认；不把 Excel 标注或 Make 示例当最终规则 |
| 任务 | 可编辑任务内容、每月日期、提前提醒天数；实际已收/已付确认才生成对应现金流水，未处理不生成 |
| 扩展 | 为其他账簿、子表和任务类型留下结构空间，不预建没有业务用途的表、接口或大块空白 |
| 实施许可 | 完整设计和计划经用户审阅确认前，不实施 |

本次不新增 hash、冻结 contract、baseline 或 gate，不删除既有安全措施。不设计通用规则引擎、可视化报表搭建器、审批系统、双重记账引擎、自动银行付款、跨池查重或跨池对账。查询失败、配置缺失、数据冲突必须明确报错，不能回退普通流水池、模拟数据或旧快照。

“现金”在 Excel 中包含所管理银行账户，并非仅指纸币。其准确账户范围仍需确认。用户要求的是内部业务数据隔离；本文不作会计合规或报表合法性判断，也不设计隐瞒法定记录的功能。

### 3.2 现金总账的目的

`2026年1月份现金账!A1:L1` 包含：日期、用于项目名称、报销人、费用类型、费用内容、招行收入、陈秀云收入、招行支出、陈秀云支出、招行余额、陈秀云余额、备注。

它回答“钱何时从哪个受管理账户进出、用于什么、当前还剩多少”。月账和全年账是同一流水事实的时间视图，不是不同业务类型。旧表的有票回款说明及无正式表头的辅助标记，需确认含义后落入事项/备注/处理状态，不机械转换成新数据库列。

### 3.3 往来账的目的

两年工作表 `A4:N4` 字段一致：日期、用于项目名称、报销人、费用类型、费用内容、招行收入、招行支出、**冲账、还款、报账提现、备注、有票回款情况、真实花销、票抵**。

`A1:A3` 用颜色区分刘树刚还借款、与公司往来、与外部人员往来。UI 将其变成文字分类，颜色仅辅助。

它回答“与谁有往来，原事项是什么，已经如何归还或冲抵，尚有哪些未结项”。**冲账、还款、报账提现、票抵不是可以任意互换的标签；真实花销也不能直接等同全部现金支出。** Excel 未提供完整自动分类与计算定义，不能提前合并这些字段。

### 3.5 有票支付与刘树刚账

- `有票支付!C1:F1` 包含金额、状态、使用日期、“谁拿来的票给谁抵账”；`G20:G21` 有“票已给，等待回款”的说明。它是票据使用和回款跟进账，不等于发票池，也不意味着有票就已经收到现金。
- `刘树刚账!A4:P11` 是银行 × 12 个月的还款矩阵；`O4` 特别写“12月提前还”，不是普通全年合计列。
- `A20` 为还现金情况；`A32` 为还票情况，`H33:H54` 标注有票直接冲；`A55` 为无票报销冲抵；`F93:G94` 为共计及年度欠款。
- 同一个人可能通过现金归还、有票直接冲、无票报销冲抵三种渠道减少欠款。后二者可能没有现金收付，必须保留区别。

### 3.6 基础设置及办理说明

`费用类型&项目名称` 的 `A2:A9` 为收入费用类型、`A11:A23` 为支出费用类型、`A25:A35` 为往来类、`A38:B54` 为项目名称。

`B10:L33` 是现行与修改方式的支付办理对照，涉及类别、概要、申请人、渠道、单据和收款方。这块内容不能遗漏，也不能据此建设 OA 审批引擎。UI 提供“支付办理说明”；哪些方案已经采用、是否需要在线编辑，仍由用户确认。

### 3.7 业务关系不等于 Excel 公式关系

业务关系拟按以下方式表达：

```text
现金专属账户 / 项目 / 费用类型
          ↓
手工实际收付 ─┬→ 现金流水池 → 现金总账（月度 / 全年 / 分账户）
任务实际确认 ─┘       │
                     └→ 关联现金事项 → 往来账 / 有票支付 / 刘树刚账
非现金冲抵登记 ─────────→ 事项归还或冲抵记录（不改变现金余额）
仅核对 / 催办任务 ───────→ 处理状态（不制造现金流水）
```

这里各账簿是现金模块内部的不同观察角度。后台不是先写“主表往来账”，再复制到“子表流水总账”，也不是反过来复制。

实际公式检查结果：

- 2026 年往来账没有公式；2025 年往来账、有票支付、刘树刚账均没有跨工作表公式。
- 2025 年全年汇总没有跨工作表公式，不能声称已经通过公式自动汇总 12 张月账。
- 可确认的跨表引用主要是月账 `J2/K2` 的上月余额承接。
- 2026 年现金账 `J2:K2` 引用了外部工作簿 `[1]` 中的 2025 年 12 月，不能将缓存金额当独立、已验证的期初真值。
- 2025 年往来账 `J42`、`J97` 已存在 `#REF!`。
- 有票支付 `C19` 只合计 `C2:C13`，后方还有记录；是阶段小计还是漏算，需确认。
- 刘树刚账 `G94=P11-G93`，其是否包含期初欠款、跨年承接和未录事项未被说明，不直接升级为 App 通用欠款公式。
- 任务表中信/花呗为 5/8 日，办理说明 `C31` 为 6/9 日，图片又说明日期浮动。应让用户确认默认日期，并可修正当月日期。
- 多表合并单元格承载共同日期、人员、项目或备注；不能把合并区域每一行都自动理解成独立现金交易。

## 4. UI 修订方案

### 4.1 导航树与 Tab 数量

```text
现有 App 左侧导航
└─ 现金账（一个页面权限）
   ├─ 账簿报表                       一级 Tab 1
   │  ├─ 现金总账（原“流水总账”）     同级账簿 1
   │  ├─ 往来账                     同级账簿 2
   │  ├─ 有票支付                   同级账簿 3
   │  ├─ 刘树刚账                   同级账簿 4
   │  └─ 后续账簿扩展位置
   ├─ 每月任务                       一级 Tab 2
   │  ├─ 本月处理
   │  └─ 任务配置
   └─ 基础设置                       一级 Tab 3
      ├─ 现金账户与期初
      ├─ 费用类型
      ├─ 项目名称
      └─ 支付办理说明
```

明确计数：**3 个一级 Tab；账簿区域 4 个同级视图；任务区域 2 个子视图；设置区域 4 个子视图。** 不是 13 个按钮平铺在同一栏，也不按 Excel 的 21 张工作表建立 21 个 Tab。

刘树刚账的矩阵、现金归还、有票直接冲、无票冲抵作为当前账簿内的表格视图切换；优先使用工具栏的小型“表格视图”选择器，不再堆第三条通栏 Tab。年份/月度是筛选器，不是导航层级。

### 4.2 首屏排版

```text
现金账                                      新增流水 ▾
账簿报表          每月任务          基础设置
现金总账   往来账   有票支付   刘树刚账     [后续账簿位置]
期间 / 账户 / 项目 / 类型 / 来源 / 搜索 / 查询
期初余额 · 本期现金收入 · 本期现金支出 · 期末余额
──────────────── 主表（固定表头、内部滚动） ────────────────
分页 / 每页条数
```

只在“账簿报表”显示账簿选择行；任务和设置显示各自小型子视图。主操作随所在区域变化：任务页为新增/编辑任务，设置页为当前字典操作，不在所有 Tab 固定摆一组无关的记账按钮。

扩展留白：设计稿可在账簿选择行右端放两个低强调的预留标记；实际产品未开发前不显示可点击的空业务 Tab。窄屏使用“更多”承接同级账簿。主表下允许添加有明确用途的子表，不预建空接口、空表或虚线卡片。扩展不设“最多只能两本账”的硬限制。

| 往来账 | 公司/外部人员/刘树刚分类；保留冲账、还款、报账提现、有票回款、真实花销、票抵 | 查看原事项及归还/冲抵明细；现金收付与非现金登记入口明确区分 |
| 有票支付 | 票据提供人、使用日期/用途、抵账对象、状态、实际回款和备注 | 事项详情、登记使用/冲抵/实际回款；不读取现有发票池 |
| 刘树刚账 | 银行/具体账单 × 月份矩阵、提前还款、全年合计；三类归还/冲抵子表；期初及未结金额 | 点击月度项看账单与分配明细；“提前还款”归属期间确认后再确定列名 |
| 本月处理 | 6 收入 + 6 支出；执行日期、提醒日、实际处理状态；其他核对与跟进 | 已收/未收、已付/未付、已还/未还分别用合适文案；不能全部叫“已还” |
| 任务配置 | 内容、任务类别、默认执行日、提前提醒天数、启停与必要默认录入信息 | 配置不直接产生流水；当月调整与模板变更分开 |
| 现金账户与期初 | 本模块账户、启用日期、期初余额 | 不读取普通银行账户余额；不能每月把同一期初重复计入 |
| 费用类型/项目 | 本模块专属字典 | 名称可参考 Excel 手工初始化；不连接现有 App 项目/OA 分类 |
| 支付办理说明 | 现行/调整方式比较、渠道、单据、申请人、收款方说明 | 只表达办理参考，不自动审批、不执行银行付款 |

字段为概念清单，不是最终必填合同。列表放高频字段，宽表可横向滚动；备注和多段明细在详情抽屉展示，不能为了简洁隐藏关键金额口径。

### 4.4 “内部转账”到底是什么

Excel 的 `2025年3月份现金账!E3` 明确写“现金内部互转不计入开销”，`L3` 说明两个受管理账户之间转移。所以该业务不是凭空增加，但当前按钮名称和位置缺乏解释。

例如，仅作虚构说明：现金模块内 A 账户转给 B 账户 1000 元。A 减少 1000，B 增加 1000，整个现金池总额不变，不作为新的经营收入或开销。**这只是记录已经发生的资金转移，App 不替用户真正转账。**

边界要求：

- 两端都必须属于现金模块管理的账户；不是在现金池与 App 普通流水池之间搬数据。
- 只产生一个转账业务记录，两个账户余额同时变化；若一端失败则整体不保存。
- 信用卡还款通常是清偿债务，不能因为“从银行转出”就自动认定为池内互转。是否属于现金账户边界须按实际账户确认。
- Make 目前把信用卡还款标成内部转账且只表现支出腿，不能采用该规则。

UI 建议：取消右上角独立、含义不明的“内部转账”主按钮，收进“新增流水”的菜单，改名 **“现金账户互转”**。选中后右侧打开短表单：日期、转出账户、转入账户、金额、说明。抽屉只是输入载体，不是一个单独模块。若账户边界确认后不需要独立入口，可合并到录入方式中，但不能错误记成开销。

### 4.5 保持现有 App 的视觉与交互

- 复用现有 `AppSidebar`、页面外壳和品牌，不复制 Make 的示例侧栏。
- 使用 `web/src/app/styles.css` 的现有变量：主色 `#1d4ed8`，表头 `#eef3f8`，正文 `#1f2937`，页面底色以现有 `--fp-page` 为准。

## 6. 后端架构与模块 I/O

### 6.1 最小结构

```text
CashPage（局部 UI 状态）
  → cash 专属 API client
  → cash route（认证、页面授权、参数/响应映射）
  → cash service（业务规则、事务编排）
  → cash repository（SQL、持久化、只读组合查询）
  → 现有 PostgreSQL 中的 cash.*
```

查询与写入方法在清晰边界内分开，文件变大或有实际复杂度时再分 query/command 文件。不预建工厂、适配器套娃、插件平台或通用报表引擎。service 接收明确 repository、时间来源等必要依赖，不接收整个 Application；不读 HTTP cookie，不生成 HTTP response。SQL 留在 repository。

### 6.2 I/O 约束

| 模块 | 输入 | 输出 | 禁止 |
| --- | --- | --- | --- |
| 身份/页面授权 | 现有可信 session、页面 ACL | 账号身份、现金页面是否可用 | 前端 body 冒充 actor；重建权限档位 |
| 现金录入 | 经确认的字段、可信 actor、编辑版本 | 一个现金事实及必要的本模块事项关联 | 普通流水/发票写入、全局操作历史、重复报表副本 |
| 每月任务 | 任务模板、月份、实际处理输入 | 本月处理状态；确认收付时引用现金流水 | 到日自动伪造付款；未付生成流水；跨页通知读取现金数据 |
| 往来/冲抵 | 本模块事项、归还金额/类型、关联现金流水或票据事项 | 本模块事项结算结果 | 非现金冲抵生成现金支出；读取普通往来款页面 |
| 账簿查询 | 授权、期间、筛选、排序、分页 | 当前现金视图 rows/summary/pagination | 全量浏览器聚合；逐行查询；后台重建报表 |
| 现金配置 | 本模块账户、项目、分类与任务设置 | 现金专属配置 | 将现金字典写入全局 settings payload |

共享身份及页面 ACL 属安全控制面，不属于现金或普通流水池，不受“禁止读取其他流水”的误解限制。业务查询阶段只读取 cash.*；不得跨 schema JOIN 普通财务事实，不建指向普通流水/发票/OA 业务表的外键。

### 6.3 同库隔离与数据库访问

建议在同一数据库内使用 `cash` schema。它只是表的命名空间，不是新数据库。用 `cash_*` 表名前缀也能表达归属，但 schema 更清楚；**仅命名不同并不能阻止错误 SQL 读到现金表。**

为落实“其他页面严禁读取”的要求，推荐一个同库的现金专用数据库运行角色及有界连接入口，复用现有连接池实现，不创建另一套持久化框架：

- 普通 App API/worker/通用查询角色不获得 cash schema 的业务表权限。
- 现金 repository 只使用现金专用连接；该角色不获得普通业务表、audit.events、job.* 的读写权限。
- 认证和 ACL 仍先经过现有安全边界；现金业务 service 不自行读取全局设置。
- 不依赖 search_path 隐藏表，使用明确 schema；迁移拥有者与 API 运行角色分离。实施时检查默认 GRANT、角色继承及 owner 权限，而不是假设已经正确。
- 不把现金角色授予普通运行角色，不依靠同一连接反复 SET ROLE 实现隔离。两边连接数量合并纳入现有 PostgreSQL 总预算。

具体失败场景：未来普通统计代码误写 `SELECT ... FROM cash.flows`。不同表名、主键、事务和类型不会拒绝这条合法 SQL；普通测试不能穷尽未来查询。数据库最小权限可以在这条安全边界上直接拒绝。因此这是针对明确隐私要求的权限隔离，不是新增用户角色档位，不需要 hash 或新 gate。

这仍不是抵抗整个服务器被攻陷、数据库超级用户或合法备份管理员的物理隔离；同一进程、同一数据库仍共享故障和资源边界。不得承诺“绝对不可见”或“零影响”。本次未连接数据库核实实际部署角色，也未更改任何 GRANT。

### 6.4 全局操作历史必须从入口排除

已查到现有 `backend/src/fin_ops_platform/app/server.py`：`handle_request` 会记录 mutation completion，`_handle_request_untracked` 会在写操作前记录 requested。**仅让 cash service 不调用 audit，不足以满足用户要求。**

实施设计应采用一个明确、仅对现金已登记路由生效的记录策略；前后两个通用审计位置使用同一决策。现金写请求仍是写请求，仍通过鉴权、输入校验和适用的安全检查，不能伪装成只读 POST 来逃避审计。

需要验证的完整出口：HTTP requested/completed、service 审计、repository/数据库触发器、导出审计、领域事件/job、异常元数据和前端全局状态。现金业务内容不得进入全局历史，不能“先写进去再在操作历史页面过滤掉”。失败请求和配置操作同样适用。其他模块的 requested 写入失败即拒绝业务等现有保护保持不变。

全局 HTTP 性能/安全日志与操作历史不同。保留不含业务内容的技术信息，不记录金额、人员、项目、账户、请求体、响应体、原始查询字符串或动态业务 ID；路由使用不含业务 ID 的模板或粗粒度类别。现金详情不进入全局搜索、通知摘要或 App Health。

当前 App Health 会编排各页面事实审计；新增现金页不能机械加入全局现金条数/金额查询，也不能为满足页面数而伪造“现金已审计”。设计为明确的数据隔离排除项，保留现有普通页面的审计要求；现金业务一致性在本模块测试/受控验证中完成。不新增“现金审计”页面或本地日志引擎。

005 在现有设置页修改页面可用性属于既有安全控制面操作，建议继续保留既有 ACL 审计，不包含现金流水/任务内容。这与现金页面内操作不入全局历史区分；若用户要求连该控制面授权变更也不记录，须单独审阅，不能顺手删除既有安全措施。

### 6.5 隔离还涉及哪些外围

- 其他页面、全局侧栏 badge、全局搜索/导出/报表不请求或缓存现金事实。
- 退出现金页面后卸载页面及其抽屉；不把现金 rows、摘要、人员、金额或搜索正文存到全局/localStorage/sessionStorage。可只保留非敏感 Tab/期间/分页偏好；初版也可不持久化这些偏好。
- 撤权、退出登录、账号切换后，清理现金内存状态；旧请求不能重新填入页面。
- 全局业务重置不得顺带清空 cash.*；现金资料不加入普通文件池或公开附件预览。附件需求未确认，不预建上传功能。
- 同库备份通常会包含 cash.*，备份读取者可能看到现金数据；须沿用并核对备份访问和恢复权限，不能把页面隔离误说成备份隔离，也不能通过不备份来“保护”现金。
- “同一现实交易不在两个池中重复录入”与技术隔离不同：系统不会跨池复制，但在禁止互相读取的前提下，也不能自动跨池查重。应先确认业务归属，由录入流程明确提示；不能新增跨池金额比对或 hash。

## 7. 数据库逻辑设计（候选，不是 DDL）

### 7.1 事实按业务存储，不按工作表存储

下列是逻辑实体与暂定名称，**不是已经决定的建表数量或已存在字段**。当前可明确六类核心实体；“事项/冲抵分配”的细分必须随业务口径确认，不能为了少几张表把不相同的事实塞成任意 JSON。

| 实体 / 暂定表 | 保存什么 | 关键关系或约束建议 |
| --- | --- | --- |
| 现金账户 `cash.accounts` | 本模块账户名称、启用/期初时点、确认后的期初金额、启停 | 独立 ID；期初时点规则明确，不从普通银行余额推导 |
| 现金项目 `cash.projects` | 本模块项目选项 | 独立 ID；被引用后停用而非默默删除或改写历史归属 |
| 费用类型 `cash.categories` | 收入/支出/往来分类 | 分类与现金收付方向分开；具体分类和必填由用户确认 |
| 现金流水 `cash.flows` | 实际发生日期、金额、流入/流出账户、内容、分类、来源及本模块关联 | 是唯一现金金额变动事实；不保存月账/年账副本 |
| 任务模板 `cash.task_templates` | 内容、默认月执行日、提醒天数、现金收付或核对类型、启停 | 模板修改不能回写已经确认的历史发生事实 |
| 月度处理 `cash.task_occurrences` | 模板对应月份、当月执行日/处理状态、实际确认信息、关联流水 | `任务 ID + 归属月份` 唯一；不是后台 job 表 |
| 业务事项（候选） | 需要持续跟踪的借款/往来、信用卡账单、有票支付事项 | 保存业务应收应还或票据使用事实，而非再次保存一份现金流水；是否按事项种类拆表待确认 |
| 归还/冲抵分配（候选） | 归还或冲抵到哪个事项、金额、类型、关联实际流水或非现金来源 | 解决分次归还/一笔收付涉及多个事项；不把“同一金额在多个报表显示”当重复结算 |

支付办理说明初版可作为现金模块内的静态参考文本维护；只有用户确需在线编辑时才设计对应持久化，不为一张说明表预建 CMS。票据若只登记使用与抵账，不新增完整发票库/OCR。

“业务事项”与“现金流水”不是两个互相竞争的现金池。例如一笔应还债务是义务事实，实际归还现金才是现金事实；用票冲抵是债务减少事实。各自只保存自身含义的金额，使用 ID 关联而不是复制现金流水供报表读取。

### 7.2 收付、转账、余额

候选简化模型：一条 flow 包含一个正金额及可空的现金转出/转入账户，显式区分收款、付款、池内转账：收款只有转入账户，付款只有转出账户，转账两端都存在且不同。对方个人或信用卡不是默认现金账户。这样互转可作为一笔事实保存，查询时分别贡献两个账户变动，不必预建通用分录系统。

- 金额后端使用 Decimal / PostgreSQL numeric，API 使用明确的十进制字符串；不使用浮点累计。精度与上限在字段确认阶段确定。
- 业务日期用日期类型，系统处理时间用带时区时间；月份/提醒按 Asia/Shanghai 业务日期处理。
- 账户期初只在一个经确认的起算时点生效；查询期初 = 起算金额 + 起算后、查询开始前的净变动。
- 查询期末 = 查询期初 + 期间该账户实际流入 − 实际流出；全池互转净额为零。
- 汇总展示建议：全池“本期现金收入/支出”只统计池外收付，不包含池内互转；分账户“流入/流出”包含互转，并单列或标明其中的互转金额。不能仅保证净额为零，却把全池收入和支出同时放大。
- 本期“现金支出”与“真实花销”分开。还借款、垫付等可以改变现金但未必构成真实花销。
- 流水顺序使用业务日期与稳定 ID 等明确排序，不依赖浏览器顺序。逐笔余额以账序计算，不跟着金额排序重新定义。
- 不默认存储每月余额快照、每本账汇总表或每行可编辑余额。初期有界 SQL 足够；出现测量证据后才评估优化。
- 期初之前的补录、跨年欠款、提前还款归属、币种范围、退款与冲正规则未确认前不自动推断。

### 7.3 任务确认的事务闭环

1. 模板定义默认日期及提前提醒天数；生成的是本月应处理事项，不代表钱已支付。
2. 打开本月处理时，根据模板和本月记录计算列表；普通 GET 不写数据库、不入队。首次编辑/确认时才创建对应月度记录。
3. “未收/未付/未还”只记录处理状态或保留待处理，不生成 flow，也不自动当作“本月已完成”。是否再次提醒待确认。
4. 点击“已收/已付/已还”打开实际确认抽屉；用户确认实际日期、金额、账户及必要归属后才提交。没有实际金额，不以 0 或上月金额静默代填。
5. 同一事务内锁定/创建唯一月度记录，检查状态与版本，保存 flow、事项关联、处理状态。任何一步失败全部回滚。
6. 同一月度确认重试返回已有结果或明确冲突，不能产生第二笔流水；不同内容重试不能静默当成原请求成功。
7. 提交成功后只重新读取当前现金视图；不通知普通账、全局状态或后台报表链。

防重复依靠主键、月度唯一约束、行锁、版本检查和事务，不增加内容 hash。手工录入重试可采用一次提交稳定的记录 ID；同内容重放不新增，不同内容明确冲突，不建立通用 hash 幂等平台。

上述最简过程暂按“一项月任务对应一次实际确认”设计。若用户需要分次还款、分笔收款，应在本文件中把月度完成条件改为已确认明细累计，允许多条 flow，而不是用唯一约束错误阻止真实分次业务。撤销确认、修改已生成流水、作废与金额冲正方式必须一起确认，避免任务显示已还但流水已不存在。

### 7.4 非现金冲抵闭环

登记非现金冲抵时：选择现金模块内事项、冲抵类型、金额、实际日期及票据/报销说明 → 同事务保存本模块冲抵记录并校验可冲余额 → 往来或个人账更新 → 现金总账余额保持不变。

已发生现金收付又用于归还某事项时，引用已存在的 flow 并登记分配，不再新增第二笔现金。实际回款也必须和“票已给/已抵账”分开。归还、票抵、冲账、报账提现如何作用到应收/应付和真实花销，仍见第 10 节，不能以通用减法替代业务确认。

## 8. API、提醒和性能方案

### 8.1 API 家族草案

以下路径只是拟议命名，当前不存在；具体 DTO 在字段确认后与现有错误格式一致化。

| API 家族 | 范围 |
| --- | --- |
| `/api/cash/flows` | 手工收付/互转、分页查询、详情；修改/作废规则确认后再定方法 |
| `/api/cash/reports/...` | 总账、往来、有票支付、个人账的本模块组合查询 |
| `/api/cash/tasks`、`/api/cash/task-occurrences/...` | 模板配置、当月列表、实际确认与未处理登记 |
| `/api/cash/items/...`、`/api/cash/settlements/...` | 经确认后定义的事项与归还/冲抵记录，不提前做通用动态 CRUD |
| `/api/cash/settings/...` | 现金账户、项目和费用类型；不包含账户访问权限配置 |

每条受保护 API 都登记为仅属于现金页，不能通过“拥有任一普通页面权限”放行。401/403、参数错误、对象不存在、版本或已结算冲突、数据库不可用要有明确响应。禁止先查询对象内容再决定用户有没有现金页权限。

读响应采用当前 App 的直接查询模式，给出 rows、summary、分页及必要的业务版本，不返回已退役的 read-model 状态或刷新任务。是否需要导出尚未得到明确要求：UI 可保留工具栏位置，不能先默认实现下载或把现金导出接到全局历史。

### 8.2 提醒方式不能凭空确定

已确认“提前几天提醒”，但尚未明确页面关闭后是否还必须提醒：

- **页内提醒**：进入现金页面/本月任务时按日期计算待处理列表；页面保持打开时可在重新聚焦或日期变化时更新。无须常驻 worker，也不向其他页面展示现金任务摘要。
- **页面关闭后外部提醒**：涉及外部通知、投递记录、失败处理与隐私边界，必须用户明确渠道与可见内容后单独设计。本草案不默认新增调度服务、共享任务队列或系统通知。

提醒日可以跨月。例如每月 1 日、提前 2 天，应归属于下个月的任务实例；不能按提醒发生月记到错误任务。29/30/31 日不存在时的处理、节假日、当月日期浮动规则均需用户选择，不静默改成月末。

### 8.3 性能与不影响旧页面

- 仅当前现金页面懒加载与取数；不在启动、普通页面、全局状态中批量加载现金数据。
- rows、summary 与分页在一个短 `REPEATABLE READ READ ONLY` 快照中查询，避免表格和汇总看到不同提交。
- 日期/账户先限定范围，SQL 筛选分页与集合聚合，不在 Python/浏览器全量筛选，不逐行查询事项。
- 先使用日期、账户/日期、任务/月唯一键、事项关联键等与实际查询相配的少量索引；不为每个筛选任意建复合索引。
- 页大小、查询日期跨度、SQL 超时和连接等待有明确上限；具体值根据数据规模和现有模式确认。不能承诺无限行即时展示。
- 现金短写事务只锁现金记录；慢查询及时失败，不占满共享数据库连接。现金池连接与现有池合计预算，不能仅新增连接数。
- 沿用现有性能目标作为实施期测量参照（当前核心 GET p95 ≤ 1000ms、p99 ≤ 2000ms），不是声称现金功能已达到。用代表规模假数据、EXPLAIN/查询次数和并发读写实测。
- 同进程同库不可能理论保证零资源影响；通过局部改动、连接/查询限额和旧页面回归降低风险。不要为“高性能”预建缓存、物化视图或分区。

隔离测试不能只验证页面“看不到”：需要数据访问角色权限测试、route/service/repository 负向调用断言、audit.events 写入零新增断言、正常旧页面写入仍有审计、旧页面金额不受现金写入影响，以及现金查询不依赖普通财务表。使用测试专有数据，不依赖用户真实 Excel。

### 9.1 预期涉及的模块

直接新增现金局部页面/API/service/repository；最小集成点是 App Shell/page registry、页面 ACL/route policy、通用审计记录策略、数据库连接/授权。App Health 的事实审计编排与全局 reset/backup 范围需要审阅隔离影响，不扩成全局重构。普通财务业务计算、导入匹配链和四个现有 worker 不因本功能改变。

正式实施时再按仓库规范登记现金模块及其 boundary-io、同步真正变化的权限/审计/运行事实文档；不能提前把草案写成运行时 registry 或删除旧保护。这次只新增本文件，未修改其他长期事实源。

### 9.2 回滚与上线边界

未批准前不执行。将来实施优先新增现金表和局部入口，避免改造普通账核心表。发布沿用已有流程，不新增现金专用发布门禁体系。启用前必须核对现金权限、日志出口与备份访问范围。

如页面停用，保留已经录入的现金表及资料，不能随 UI 回滚删库。因数据已经存在，回滚到不知道现金 schema 的旧版本前需确认备份/角色/日志策略仍安全。破坏性迁移、清理或对外通知需要单独明确授权。

不要求用户一次回答全部，也不在未回答时猜测实现。优先确认会同时影响 UI 和数据模型的前四项。

| 优先顺序 | 问题 | 为什么不能从 Excel 直接推断 |
| --- | --- | --- |
| 1 | 冲账、还款、报账提现、票抵、真实花销分别怎样影响公司/个人应收应付？有票提供、抵账与回款是不是独立事件？ | 决定事项/冲抵结构，避免同一金额被扣两次或伪造现金 |
| 2 | 现金模块到底管理哪些账户？启用时点、期初现金余额和期初欠款怎样确认？ | 两账户互转、信用卡/储蓄卡边界、跨年公式均不能靠名字判断 |

| 4 | 提醒只在现金页面内，还是关闭页面后也要通知？“未还”后如何再提醒？日期不存在/浮动如何处理？ | 决定是否真的需要调度与通知，而不是提前新增后台系统 |

| 6 | 旧 Excel 的初始数据是否仅用于设计，还是将来需手工建立期初/未结事项？ | 目前没有文件导入需求；不偷偷增加导入迁移 |
| 7 | 是否需要附件、导出、本模块内的修改痕迹？ | 均不默认加；不写全局历史不等于已要求建设一套私有审计系统 |
| 8 | “12月提前还”、有票小计、跨年欠款、辅助标记、现行/调整办理方式的正式口径是什么？ | 存在日期冲突、局部公式和人工说明 |

上述第 1 项最适合用少量**虚构例子**逐条走通，而不是先问几十个字段：一笔垫付、一次现金归还、一次有票冲抵、一次无票冲抵、一笔报账提现。例子确认后同步更新本文相关 UI 和逻辑模型。

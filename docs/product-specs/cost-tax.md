# 成本统计、项目归因与税金抵扣

本文维护成本统计、项目成本归因、税金抵扣、已认证发票和发票使用/收款 read model 的当前业务口径。

## 成本统计

成本统计页面以银行成本事件为唯一金额事实：

- 五个视图 `按项目`、`按银行`、`按费用类型`、`按标签`、`按时间`消费同一组 signed bank cost events，并统一按银行交易日期筛年/月。相同 scope 和搜索集合的根层净额必须可对账；页面只负责筛选、聚合、分页和导出，不重新定义金额。
- active 正式关系中必须同时存在银行流水和 OA。只要关系内有一张 OA 尚未明确完成，整组流水不进入五个视图，也不能作为无 OA 流水；不新增“待分摊”或“数据异常”页面状态。
- 全部 OA 已完成时，每条支出流水独立形成正成本事件。只有与该支出和 OA 同处一个 active 关系、且银行标签明确为“付错退款”的收入才形成负成本事件；普通收入、关系外退款和仅凭同标签猜测的收入都不得冲减。
- 每条正/负银行事件独立按关系内 OA 原始金额比例分摊。支付申请以父单原始金额和项目作为权重单元；日常报销逐个使用 canonical `expense_items` 的原始金额、项目、费用类型和内容。金额按分使用确定性最大余数法，保证每条银行事件的分摊合计严格等于该事件金额。
- OA 权重合计为零或缺失只在计算内部防止除以零并排除该关系，不扩展为产品状态。项目或稳定身份缺失仍按内部质量原因排除；费用类型缺失不再隐藏，统一归入“未填写 OA 费用类型”。禁止按事由猜测或统一填“其他”。
- `按银行`使用每条银行流水的真实账户；多账户关系按各自流水分别归属，不再生成“混合支付账户”。三种归因视图的每行最小粒度为 `bank_transaction × OA_unit`。
- 详情必须明确展示 OA 原始金额、OA 权重比例、当前银行事件原金额、关系 OA 原额合计、银行总支出、同关系付错退款、实际现金成本、与 OA 原额差额和现金比例。例：同关系 1050 支出与 35 付错退款的实际现金成本为 1015，再分别按 OA 权重分摊。
- 没有任何 active OA 关系的支出流水可由现有右上角“无 OA 成本范围”抽屉纳入。虚拟项目名称和标签默认都为空；候选仅来自当前全历史实际存在的无 OA 支出标签。规则保存后对全部历史期间生效，但执行时仍逐笔判断无 OA；某标签下已有 OA 的流水绝不能因标签被选中而进入虚拟项目。无 OA 行的费用类型固定为“无 OA 分类”。
- “付错退款”是收入，禁止作为无 OA 候选。标签归档不得静默改写已保存的成本规则；不可用选择必须可见并由用户显式取消。
- 成本统计 API 每次请求都在一个 PostgreSQL `REPEATABLE READ READ ONLY` snapshot 中读取 canonical 银行流水、OA、active 正式关系、标签和设置；不依赖其它页面 payload/read model，不使用 Cost version、freshness、dirty scope、outbox、worker 或 Redis cache。
- 银行、OA、关系或设置写入只提交各自 owner facts，不 fan-out 成本统计刷新；下一次访问或浏览器刷新直接读取已提交事实。读取失败返回明确错误，不能把旧数据或空数据伪装成 fresh。
- 五个视图搜索都先作用于各自对同一成本事件的展示行，再计算 summary、facets、row count 和 cursor 分页；搜索词规范化后最长 200 字符，并绑定分页游标。
- 页面和导出逐行保留资金方向；支出为正成本，“付错退款”为负成本。页头 `total_amount` 表示净成本，支出与退款绝对额仍分别公开，不能把负成本伪装为普通正收入。
- 明细分页使用表格内部滚动接近底部自动加载；下一页失败只在当前明细区提供重试，不清空已加载内容或刷新整页。

## 项目归因

项目归因至少需要考虑：

- OA 单据项目、发票项目、银行流水摘要/对手方、人工修正关系。
- 日常报销明细拆分、缺失项目、冲突项目和撤回关系。
- source version、归因来源和审计记录。

## 税金抵扣

税金抵扣页面关注可抵扣发票、已认证发票和发票使用状态：

- 认证状态、税额、发票类型和使用状态必须由统一 policy 判定。
- 发票关系确认/撤回会影响税金抵扣和成本统计。
- backfill/refresh 需要按月份或发票对象范围执行，避免逐行重建。

# 流水、发票与 ETC 导入简化实施计划

日期：2026-09-21。状态：**代码已部署，已证实的数据修复与普通导入验收完成；生产性能部分未达标，ETC 正向生产实测受合法输入限制**。代码核对基线：`501f72273`。本任务不使用 GSD 命令、阶段执行或自动编排。

本文保留已审核的实施范围与验收要求；代码实施不代表已完成生产部署。实际验证状态见 [实施验证记录](import-architecture-verification.md)。实际实施后，最终合同必须同步到各模块 boundary-io/state-machine/tests 与产品/API/运维文档。先前取证报告在 `.planning/debug/`，只作为历史证据，不作为当前架构事实源。

## 1. 评审结论与必要修正

方案通过本轮计划审阅：保留三个业务入口，共用导入生命周期、任务执行与结果呈现；业务去重逐项进行；普通发票、流水和 ETC 各自拥有解析/写入规则。使用现有 PostgreSQL 和现有 import worker，不增加消息代理、页面 read model、通用工作流引擎或第二事实池。

对上一版方案作以下修正：

1. **ETC 零新增不等于零变更。** 已有票据可能仍需加入本次 import/business batch，或者补齐附件；当前 `b1fddc907` 已修复重复票成员遗漏。只有新票、附件、成员关系和允许的 metadata 全部零变更才是无需提交。迁移必须保护这项新行为。
2. **单任务队列需要迁移全部现有消费者。** import worker 还执行 `tax_certified_import.confirm`、`oa_manual_import.create`，不能只改三个页面而使这两个入口失效。
3. **关联台手工补录不是普通页面导入。** 它通过既有窄入口把整批发票与 OA 明细/关系一起提交。保留该原子命令，只复用领域校验和事务 writer，不强迫改成异步导入或二次关联。
4. **少门禁不等于不校验。** 保留权限/owner、来源完整性、身份与财务字段、提交并发及事务五类必要检查；缺少可选字段、名称展示差异、没有外部控制合计等不能一律阻断。
5. **高性能必须量测完整耗时。** 不能把 HTTP 快速返回 202 当作导入变快；必须同时测预览、排队、正式提交、最终可见和页面并发读。
6. **“其他页面不出 bug”是验收目标，不能事先绝对保证。** 用不变的 owner/I/O、已有业务链回归和真实存储故障测试证明影响范围，不用伪造成功或跳过失败测试达成。
7. **重试不是兜底。** 重试只能执行同一明确意图；字段猜测、旧快照回写、坏文件静默跳行、缺依赖改走同步/本地存储均禁止。
8. **备份必须有结束动作。** 默认不为代码重构复制主库；历史修复只创建必要的本任务恢复工件。完成验证后精确清理本任务工件/临时备份，禁止删除、清空、替换或重建主数据库，不清理既有平台备份。

## 2. 目标合同与范围

### 2.1 用户可见行为

- 每次主动上传，都按文件中的真实业务项重新比较当前事实池；文件名或 hash 相同不能阻断整份文件。
- 展示即将新增、APP 已存在、本次重复；有值时再展示更新、补齐、关系变更、疑似、冲突和错误。所有数字来自后端同一份逐项计划。
- 一张发票的商品明细先按现有表头/明细规则形成逻辑票；同张 ETC 的 XML/PDF 是配套来源。表格行数、唯一票数、ZIP 数、附件数分别标单位。
- 银行/发票没有实际变化时显示“无需导入”；ETC 还必须检查附件与当前批次成员的变化。
- 预览中的错误只影响问题文件/本次选择。用户可以移除问题文件再确认；不引入逐行任意放行界面或全 App 阻断。
- **本次明确确认的有界范围整体提交。** 合法重复是有解释的无写入结果；错误/冲突在提交前处理。数据库失败整体回滚，不把部分成功显示为完成。
- 已提交任务可从历史/全局进度查看和继续；新进入上传页仍为空草稿，不自动确认历史 preview。
- 成功结果来自正式事务：逐条结果、批次证据、事实和任务成功一并提交。
- 普通页面读取失败只重试读取；不能因此再次创建发票或流水。

### 2.2 不改的业务边界

- app.invoices/app.bank_transactions 仍是普通财务事实；cash 独立域零写入。
- OA 来源优先保留，OCR 不获得财务覆盖权限。合法名称展示差异保留双方原值，不一律升级成财务冲突。
- ETC 仅写自有 metadata/附件/批次，并通过已有受控端口关联已存在 canonical 发票；不新增统一发票，不改正式税额/金额/身份。
- ETC 对账、创建 OA 草稿、人工提交声明仍由 ETC 模块拥有；导入不触发这些外部动作。
- 已核销、已确认关系、成本分配、银行分类、税金业务规则不随导入重构改变。
- 现有批次撤回、补录、原件访问和审计权限继续由各 owner 控制。
- “全量文件”仍是逐项导入，不是以文件替换整个池；文件中缺少某项不是删除依据。普通导入不删除任何既有票/流水，不通过保存旧集合覆盖最新集合。合法撤回/删除仍走原有显式领域命令并保留审计；删除文件、清空草稿和暂存对象清理不得级联删除正式事实。

## 4. 数据与状态的最小改动

1. 复用 job.import_jobs 作为导入执行状态与待执行工作唯一来源。现有 pending/processing/succeeded/failed/canceled 保留，增加必要的待确认语义；stage 区分 prepare/review/commit，不为每个阶段增加一种任务。
2. 复用既有 session/file/batch/row 和 ETC session/manifest 存储原件引用、规范化候选及逐项计划；任务只保存引用、选择、版本与摘要，不复制大块原件或第二份候选全集。
3. 只为领取安全增加必要的单调领取代次/版本；尝试次数不能兼任会被重置的并发版本。最终提交检查当前领取版本；旧 worker 被接管后不得落库。
4. 普通 session 与 ETC session 不强行合表；只统一调用合同和摘要。原批次/行/审计继续作为历史证据，不能为少几张表删除。
5. 任务呈现从 import job 派生。导入类型不再独立更新 background job 执行状态；全局任务接口聚合导入任务及其他原有任务，关闭提醒是独立展示标记，不是执行终态。
6. 只在新增状态、领取查询、版本并发或必要唯一性要求处修改 schema/index/view/grant。已有 migration 不改写；新增迁移编号在实施时按当前最新序列确定，同时更新 migration 测试清单。
7. 预览绑定解析版本、映射/方向、文件选择和源位置；只有这些输入改变才重做解析。确认/执行阶段批量重检相关当前身份及 ETC task 版本，不重复读取整池或重新解析全部 ZIP。
8. 并发先到的完全相同强身份记录可以变为“已由其他任务导入”的合法重复，并解释最终计数；金额/税额/账户/方向/归属冲突或写入范围扩大必须停止本次提交并复核。

### 4.1 去重、请求幂等与计数分开负责

- 文件字节复用只减少存储/解析开销，不决定业务项是否入池。同一次请求因断网重发使用原请求 ID；用户再次主动上传同文件使用新的请求 ID，并重新比较当前事实。
- 发票沿用现有强数电号或合法代码+号码，保留前导零；同身份财务差异不能静默跳过或覆盖。ETC XML/PDF 按同一票身份配套，不计成两张票。
- 流水沿用现有 identity service：账户、官方参考号类别/值、业务指纹，以及已有 bank-v4 账单位置冲突辨识。官方参考号可能复用，同秒同金额可能是两笔真实交易；不替换成简单拼接字段或内容 hash 去重。合法的不同账单位置按现有领域规则区分，不能将它们一律当作冲突或重复；证据不足的弱身份保持疑似复核。
- 逐项基础分类互斥：代表项与当前池比较，其余同次出现项记“本次重复”；一条不能同时累计为“APP 已存在”和“本次重复”。“新增/已有/本次重复/需处理/明确排除”按已定义业务单位对账，错误物理行另带源位置，不能冒充已识别票数。
- “补附件、加入本批次、更新允许的 metadata”是独立动作维度，可以同时发生，不与基础票数相加。例如“已有 10 张，其中 4 张补附件、10 张加入当前批次”仍是 10 张票。前后端直接使用后端摘要，不各自重新推算。
- 确认幂等绑定 owner、同一预览版本与选择。重复确认返回同一任务；同请求 ID 但内容不同明确冲突。预览输入变动产生新版本，并使旧确认无效；已经受理的执行意图不能被编辑。
- 一个工作流任务对应一个可确认的导入草稿，文件上传请求各自有请求 ID，同一草稿的多个文件共用工作流任务 ID。未确认时增减文件/修改映射形成新的预览版本；复用未变化文件的候选，只重算必要决策。进行中的旧准备结果只能按版本写回，不能覆盖更新后的选择。确认时固化选定范围；未选文件保留为未提交证据，不能随任务成功被标为已导入。确认后的任务只读，后续新一轮选择建立新草稿，可显式复用原件引用。

### 4.2 明确状态与竞争规则

下表是拟实施合同，字段/API 名称需要与 W0 的既有 DTO 映射一起更新；不新增独立第二状态表。

| 情况 | 权威状态与允许动作 | 财务写入 |
| --- | --- | --- |
| 原件上传并登记成功 | pending/prepare，返回稳定任务 ID | 无 |
| worker 解析 | processing/prepare；可按下述竞争规则取消 | 无 |
| 计划有待提交动作，或有需处理输入 | awaiting_confirmation/review；查看、修正选择/输入、确认、放弃 | 无 |
| 全部业务动作无变化 | succeeded/prepare，result.outcome=no_changes；显示“检查完成，无需导入” | 仅保存必要计划/检查结果，不排 commit、不新建空业务批次 |
| 用户确认已被持久接收 | pending/commit；重复确认查询原任务 | 无 |
| 执行正式提交 | processing/commit；按当前身份和领取版本提交 | 领域数据、必要审计及任务终态同事务 |
| 确认后发现需重新复核 | 返回 awaiting_confirmation/review 并说明差异；原确认意图失效 | 本次事务零正式写入 |
| 临时依赖故障 | 按既有上限有限重试；达到上限 failed，展示原因与同意图 retry | 未提交的事务回滚 |
| 永久无效输入/缺依赖配置 | 明确错误和可执行动作；不自动循环，不切旧链 | 无假成功 |
| 用户取消与正式提交竞争 | 同一 job 行锁/领取版本决定先后；取消先完成则旧 worker 失去提交资格；正式提交先完成则返回已完成，取消不成功 | 已提交事实不能靠取消删除 |

确认到执行期间，只有“完全同一事实被另一任务先导入”允许减少本次实际新增，并在结果列出预计/实际差异；新增写入范围扩大、目标变更或财务冲突一律回到复核。轮询失败只显示状态暂时不可读，不宣称任务失败或自动发起新导入。

上传对象成功而登记失败时，对象仍是带明确 owner/请求 ID 的暂存工件；同请求可核对复用，最终由精确无引用清理收尾。原件未完成校验/登记不创建可执行 prepare。任务受理响应丢失按原请求 ID 查询/重发，不能依靠文件 hash 猜前一次是否成功。上传、确认和 worker 最终写入均遵守当前 owner/权限，排队期间被撤销权限不得绕过。

## 5. 哪些校验保留，哪些不要增加

| 必要性 | 规则 |
| --- | --- |
| 保留 | 服务端 owner/权限、文件结构与有界资源、必要业务字段、金额/方向、强身份/弱疑似区别、并发版本、唯一性、事务结果 |
| 保留但不扩大 | 原件已有 hash 校验；来源提供控制合计时校验；未提供时如实标注，不拒绝全部银行文件 |
| 仅问题项/文件影响 | 格式错误、缺必需字段、确定财务冲突；不给无关文件、其他月份或其他页面加全局锁 |
| 普通提示 | 名称展示差异、可选信息缺失、来源控制信息未提供；按既有合同保留原值 |
| 不新增 | 每次导入前全库 Audit、全历史数量相等、全部页面 healthy 才允许导入、人工重复确认、全库快照 fingerprint、无限重试 |
| 禁止 | 默认税额 0 掩盖未知、自动猜银行列、弱相似直接去重、坏行 continue 后报告成功、缺对象存储改用本地文件、缺队列改同步执行 |

保留数据库事务、权限、唯一约束和精确修复 CAS 是必要业务正确性，不是额外审批流程。日常导入不进入历史修复工具的审批/清单流程。

## 6. 按顺序执行的工作包

每包包含代码、针对性测试和边界文档；不逐包申请用户确认，不运行 GSD。每包相关检查通过后继续下一包，最终只做一次候选版本的广泛验收。生产操作边界按当时明确授权与仓库正式发布工具执行；本轮已获得实施、提交、推送和部署授权，按下述顺序完成并记录实际验证结果。

### W0：记录基线并将真实缺陷变成回归

**输入**：本报告及现存诊断 JSON、当前 HEAD、当前模块合同。**责任范围**：tests、固定合成数据、窄性能测量脚本。

- 记录当前分支和其他任务改动；实施时重新确认 `b1fddc907` ETC 成员修复及关联台多票补录合同仍在。
- 把已复现的“全局重试仅生成预览”“双租约重启误完成”“任务存在但无事件”“部分行成功却全成功”“同文件部分失败后被阻断”各变成行为回归。
- 为 ETC 加入：已有完整票仍加入当前批次、附件补齐单独计数、无 canonical 匹配不新建票、同一任务重复确认、task 变化拒绝、XML/PDF 数量不冒充票数。
- 采集当前版本的 API 受理、预览/执行、SQL 往返、ZIP 解析/对象读次数、内存和并发页面延迟。使用固定合成数据，不依赖个人真实文件。
- 现有失败测试单独归因；与本次合同相关的旧断言随实现修正，不能删断言掩盖失败，也不能把无关失败伪装成此次新增。

**交付**：能再现问题的测试、基线报告、现有接口字段表。**完成条件**：测试在旧实现确实捕获对应错误，而非只比私有函数调用次数。

### W1：建立单任务直接领取与同意图恢复

**文件**：import_job_queue.py、runtime_worker_handlers.py、runtime_worker_registry.py、worker CLI/runner、拟 import_jobs repository、拟 import_workflow_service；调用方 server.py/routes_etc_import.py/routes_tax.py/routes_settings.py。

- 任务 repository 实现 PostgreSQL `FOR UPDATE SKIP LOCKED` 的有界领取、唯一租约、可执行时间、续租、可重试失败与单调领取版本。
- 准备任务完成后释放租约进入待确认；确认只锁定版本/选择并将同一任务置为待提交；202 在该事务提交后返回。
- 显式 retry 调相同受理命令：原任务成功返回原结果，执行中返回原任务，临时失败续同意图，需复核返回明确计划；不先 acknowledge 再重新预览。
- 同时迁移 tax_certified 与 OA manual 的入队调用，保持其 API/业务合同；不扩展为这两个业务的功能改造。
- 准备阶段不得占用正式财务锁。SIGTERM/崩溃/超时回滚与租约接管有明确结果；单纯领不到任务不能改成成功。
- import worker 的 CLI、registration、heartbeat、pending/failed 统计改读 import job；保留其他三种 worker、通用 outbox 与 matching dirty 队列。
- 领取阶段默认遵循现有有界资源配置，不在正确性尚未证明时贸然提高并发。性能验收确认存在排队瓶颈时，才调整同一实例的有界并发；每个任务必须有独立服务上下文/事务连接，不能共享可变快照。

**交付**：单一正式执行路径及队列/权限/两类共享入口回归。**完成条件**：真实 PG 多 worker 下不重复提交；故障后有明确可恢复任务；同意图只有一个权威任务，代码无同步兜底。

新增的数据自然使相关页面总数/余额变化，属于正确业务影响；“不影响页面”不是要求页面继续显示旧数。修复财务字段时要说明影响，不能为让截图相同而保留错误。

## 9. 性能目标与测量方法

以下是**实施验收目标，不是现有测量结果**。在固定同规格隔离验收环境、固定数据、连接池预热后量测，另报告冷启动、上传传输和远程对象 I/O。若不达标继续分析优化，不通过缩小数据集或只测 mock 宣称达标。

| 场景 | 初始目标 |
| --- | --- |
| 已有预览确认受理 | 服务端 p95 ≤ 500 ms；不做整文件解析/OCR/对象上传 |
| 单任务摘要/进度查询 | 服务端 p95 ≤ 200 ms；不加载逐行 payload 或原件 |
| 无积压时的任务领取等待 | p95 ≤ 500 ms，复用有界 poll 配置 |
| 1000 条合法普通发票或流水 | 规范化/批量查重 p95 ≤ 3 s；最终 DB 提交 p95 ≤ 2 s；分别报告总完成耗时 |
| 120 张合成 ETC XML/PDF | 一次解包/解析/计划 p95 ≤ 5 s；附件传输单列量测；确认与重放不重复 parse |
| 全部业务动作无变化 | 保留必要检查结果；零 canonical 更新、零附件重传、不进入 commit 阶段、不新建空业务批次、零 matching 通知 |
| 同时导入与浏览其他页面 | 记录相同负载前后页面 p50/p95/p99、错误和 pool waiting；出现持续退化必须定位并修，不以恢复缓存/投影掩盖 |

数据集：100/1000 条标准输入、重复混合、错误/冲突混合、当前支持上限附近；ETC 增加 59 ZIP/38 需求形状的合成组合场景。每个基准有足够重复样本和 p99/max，记录文件/附件字节量、CPU/内存、SQL 计数、并发数和硬件条件，不把不同环境数字直接比较。

优先优化次序：删除重复解析/全量加载 → 批量查重与写入 → 索引/EXPLAIN → 对象有限并发与进度节流 → 仅在实测需要时调 worker 并发。不要先加缓存、分片或额外 worker。已有正常流程显著快于目标时也应报告相对变化，目标上限不授权性能退化。

## 11. 备份与恢复工件的完整生命周期

- 代码/队列改造默认使用非破坏性迁移，不为此创建整库复制或恢复主库。既有平台 PITR/日常备份独立管理。
- 数据纠错前按现有修复工具创建本任务精确 before-image/rollback manifest；登记唯一工件名、目标范围、创建者、路径与删除状态。敏感工件不写入 Git 或聊天，不另留一份副本。
- dry-run、事务修复、幂等复查及受影响页面核验未结束前，任务尚未完成，工件继续承担恢复责任。
- 完成上述验证后，通过已有 `import-audit-repair-artifact-delete <task>.json <rollback-manifest-fingerprint>` 精确删除本任务工件。实施时使用当前已部署且支持该正式操作的 helper；不增加缺 helper 就走另一条绕行路径。
- 如确实额外创建本任务数据库备份文件或隔离恢复副本，逐项登记，并在同一收尾包精确移除备份文件/该隔离副本；清理不得使用广泛路径、模糊名称或默认 DSN。
- 删除后确认文件/临时副本不存在，主数据库身份与服务健康保持，正式票/流水/关系可读；只保留不含备份内容的执行结果和合法业务审计。
- 不删除主数据库、现有平台备份、源文件原件、正式附件、不可变业务审计。任务产生的暂存对象仅在明确无引用且本任务拥有时清理。

# 导入明细与复核闭环修复（2026-09-23）

## 目标与边界

银行/发票共享导入工作流：统一 preview audit 与文件逐行分类，展示全部记录和字段冲突，避免已知错误进入确认队列。现有 canonical facts、去重规则、共享任务访问、审计、事务与 worker 租约不变。ETC 只回归公共组件/prepare 合同；无 schema、新依赖、新缓存或新 worker。

直接修改 import service/audit/processing、HTTP review/confirm 映射、两种 store 的 preview completion、typed API 和导入页自有表格。财务字段冲突由正式导入服务判断，repository 只负责已有批量 identity I/O，UI 只展示结果与收集动作。

## 执行顺序与验收

1. 核对现存生产任务与旧 API；确认“需检查 4”实际返回 14 行，漏了 19 个新增。
2. 复用 audit 分组增加互斥逐行分类；file_id 限定分页、橘色优先排序。summary 与当前文件全部行对账。
3. 页内批量读单票 canonical 值，直接复用 financial conflict 规则返回结构化差异；禁止拿关系组金额比较单票金额。
4. 替换旧 tabs/table 为单文件全量明细；金额不截断、公司名称换行、灰/绿/橘色与文字同时呈现，冲突内联展开。
5. API/worker 共用文件可确认校验；prepare 持久化 needs_review；前端收到需复核仍能查看预览；正常提交后才显示成功。
6. 删除旧 kind 分支/状态/tab/CSS/重复文件名/错误测试假设，扫描调用方并同步边界文档。
7. 测试、lint、类型检查、build、浏览器实际排版与性能；提交并推送 main，官方部署，生产只读验证与精确任务重新预览。真实冲突不自动改金额或税号。

## 测试责任

七类均适用：业务分类；service/file 隔离与事务；API 参数和拒绝错误；durable worker 状态及数据库原子提交；UI 明细/颜色/金额/展开/分页；预览→需复核→修正→确认→33条事实闭环；银行/发票/ETC/手工输入/共享任务及下游页面回归。read model/cache 运行时已退役，不新增相关链路。

专用合成用例为 33 行，19 新增、10 已存在、4 金额/税额/税号冲突；错误不产生新事实，修正后得到 33 张正式发票。每页 canonical identity 查询 1 次。生产数据仅核对，不将测试样例通过当成四张真实票已被纠正。

## 数据与性能

不创建生产备份、不修改主数据库结构；独立临时 PostgreSQL `finops_review_test` 只用于验证，结束后停止并删除该临时实例与日志。保留正式文件与任务审计。

部署前同一客户端 20 次读取：任务列表 P95 101ms，任务详情 103ms，旧复核明细 121ms。部署后复测新接口并检查真实 33/19/10/4、完整比较字段、生产 worker/queue、页面链路与 release 一致性。默认核心 GET P95 ≤1000ms、P99 ≤2000ms；小样本仅代表本次观测，不代表无限数据规模。

## 审阅结论

模块与 I/O 明确；复用现有机制、移除旧分支；无新增严格门禁、GSD、兜底或财务自动覆盖。完整闭环指所有系统状态和操作有可验证结果；不能保证来源财务差异无需核实，也不能承诺永不发生任何故障。生产发布证据由正式部署入口保存；本次部署后的文件核对、实测耗时和剩余业务冲突在交付报告中列明。

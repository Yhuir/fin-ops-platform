## 2. 方案取舍

不把修复目标设为“所有 OCR 都必须一次读全”。本次不增加图像放大、多轮 OCR、裁剪重试、其它 OCR 引擎、LLM 或模型依赖。

采用现有证据合同：能够确认完整财务字段时维持原结果；只有票面明确支持强身份、日期及价税合计，但无法确定未税/税额时，输出已知字段，未确认金额保持空，并使用已有 `financial_review_reason`。这是明确的部分识别结果，不得补零、按金额猜票号、按常见税率反算，或把异常伪装成功。

现有 `InvoiceAttachmentRecognitionService.decide` 已先按强身份找已有票，再限制财务不完整候选的新建；`ImportNormalizationService.upsert_oa_attachment_invoice` 已支持使用已有票财务值补来源。因此优先只修正上游产出和同一解析器内的结果选择，不新增关联实现。

“减少门禁”不等于移除强身份、当前子项归属、权限、幂等、事务和防重复报销约束。现有必要约束保持，不新建审批、冻结基线或哈希验证体系。

## 4. 按顺序执行

### A. 先建立失败用例和变更范围

1. 固定本次真实 OCR 的脱敏文本布局，保留漏字、乱序、两位小数、票号长度和第二张聊天截图特征；自动测试不依赖生产文件或生产网络。
2. 在原测试文件生成内存 DOCX/图片替身，覆盖 XML 无文本、媒体包含发票及聊天截图的文件级解析。
3. 完整扫描共享解析入口、调用方、缓存版本消费者、promotion、import normalization、人工识别 API/UI、测试和文档。对结构用 CodeGraph，对状态字符串和字段用全仓文本扫描。
4. 新测试先证明当前返回 `no_evidence`/空列表，再修改；不能通过改测试数据补上“合计”“1%”消除真实失败。

### B. 修改唯一解析入口，明确部分证据合同

1. 保留现有标签化票号识别、日期与正式文档分类。部分结果必须具有既有强身份策略能接受的完整身份及明确价税合计，不扩大残缺号码、裸长数字或非正式票据准入。
2. 调整 `_extract_amount_summary` 的结果语义：明确合计标签或财务标签、现有唯一税率证明可以确认数值时照旧返回完整三元组；明确总额但未税/税额不能可靠归属时，返回空未税、空税额与票面总额。
3. 明确字段互相矛盾、加总不符、金额小数被压平拼接、总额歧义时保持无有效财务结果，不得用“部分识别”绕过原冲突检查。缺字段与矛盾字段必须有独立测试。
4. `_parse_invoice_text` 统一输出既有 evidence；存在空未税/税额时复用 `financial_review_reason`，修改铁路专用措辞为准确的通用原因。不要在 parser 外再做第二次票号提取。
5. 未识别税率保持空。不从 297.03 和 2.97 猜 1%，也不按三个数字的位置认定财务角色。
6. OCR 初始化、推理、下载及文件安全错误沿用现有失败合同，不能转成部分证据或 `no_evidence`。

### C. 保护共享 PDF/重复证据路径

1. 当前 PDF 以“存在正式 evidence”判断是否停止该页 OCR。部分 evidence 出现后，需改为区分财务完整性：完整文本页仍零 OCR；财务不完整页维持原有一次该页 OCR 的机会，不新增多轮识别。
2. 同页文字/OCR和同文件重复表示按既有强身份比较：同身份完整结果优先于部分结果；使用被选结果自己的 region/provenance，不逐字段拼凑另一张票。
3. 替换会丢弃后到完整证据的 `seen_keys -> continue` 行为；保持线性、文件内去重。两份部分结果不拼财务字段，不因金额相同合并不同票；不同身份沿用现有页区冲突合同。
4. OA 继续处理全部页；人工上传仍取首张可识别发票，但该页的文本/OCR选择必须先完成，不能先返回较早的不完整表示而丢失同页完整 OCR。
5. DOCX 同一附件在不同子项的多条 occurrence 仍由 adapter 绑定，不做跨子项全局去重。

### D. 验证复用关联链，不另建修复写入口

1. 从真实 parser 结果出发进入 recognition、promotion、normalization；不能在端到端测试中直接塞入人工构造的“已解析票”跳过失败点。
2. 目标票已存在：唯一票号关联原 invoice ID；canonical 未税/税额/总额、日期和已证实购销方不被 OCR 候选覆盖；来源绑定第三个子项。
3. 保留来源接管原语义：现有合同会调整当前 `manual_invoice_import` 来源/标签；原导入 batch/row/audit 历史必须保留。不能承诺 source_links 原样不变，也不能额外手工删导入历史。
4. 无已有票：即使设置为 create_missing，财务不完整也只保留可解释证据，不能新建财务事实；完整票的原创建能力保持。
5. 多义票号、跨 OA 冲突、OA 已失去准入资格、来源 item 漂移复用原处理；不按申请人/项目/金额自动关联。
6. 重复执行零重复发票/来源/正式关系。校验 persistence 失败不产生半张正式票或半条来源；OA/cache已提交但 promotion 失败时按现有 durable 失败/重试恢复，不能声称整条跨阶段链是单一事务。
7. 证据先到、正式票后导入：复用已有反向来源关联，针对当前 owner 合同验证。进行中/已完成两类 owner 都要覆盖；若现有边界不支持某一路径，先明确缺口和最小调整，不私建第二条数据库回填链。

### E. 人工识别入口的最小隔离

1. `ManualInvoiceEntryService` 继续输出同样字段；部分识别预填票号、日期、明确总额，不把总额放进 net_amount，空税額不转 0。
2. 已发现 `ManualInvoiceBatchEditor.tsx` 只合并非空识别值：更换文件时可能把上一张票的金额保留到新票。对本次共享 parser 新产出的部分结果，必须防止这个混合。
3. 在原 recognize 成功分支按既有 DTO 字段更新当前票的识别字段，包括空值；保留方向/红蓝字等非 OCR 选项。成功识别新文件后原“已保存”状态失效；网络失败不得清空用户草稿。
4. 不做 UI 重设计，不增加待核对页面；沿用现有核对提示和必填校验。测试空字段提交被拒绝、用户补齐后按原预览确认链处理。

### F. 缓存、生效和目标数据闭环

1. 增加 `PARSER_VERSION`，复用 `attachment_invoice_cache_parser_version()`，不改 cache schema。版本切换使旧 `no_evidence` 不再作为当前结果命中。
2. 明确性能边界：版本切换会使其它附件在后续正常同步中按需重解析，不能声称只有目标附件受影响；继续使用现有每轮最多 20 个、达到 45 秒后续跑的准备机制，不新增调度器。
3. 发布后只主动发起该 OA 的既有精确刷新。该接口是 OA row 粒度，可能重解析这一行的全部三个附件，不能声称仅重跑 300 元文件。不发起全历史刷新、不清空 cache 表。
4. 使用 `POST /api/workbench/settings/oa/manual-search/refresh-attachments` 及其 event GET；等待真实 done，并检查 promotion_summary 和逐行 error。事件完成后继续核实 matching 与页面，不以 202 或解析成功作为闭环完成。
5. 若设置当前为 disabled，明确记录既有配置阻止关联，不自动更改全局设置。实施前只读核实；需要改变配置时列明具体范围。

## 6. 性能与验收

- 本次不增加下载次数或每图 OCR 轮数；目标 DOCX 两张图各一次，重复引用同物理附件仍复用当前 cache。
- 完整文字 PDF 零 OCR；原来需要 OCR 的页面仍最多一次；同票结果选择为 O(n) 字典访问，不做两两比较。
- 已有票仍按候选强身份批量查询，禁止每附件额外查库和全库匹配；普通页面 GET 不新增 SQL、OCR 或任务。
- 单独记录下载、OCR、解析、数据库/promotion、排队/matching、页面可见耗时。目标案例报告实际秒数；不预先承诺未经测量的端到端毫秒值。
- 本地用同机相同样本对照，文本解析/去重 100 次记录 p50/p95，完整票与部分票均测；已有 query-count/OCR-count 测试保护零额外 I/O。真实 DOCX一次执行作耗时 smoke，不把单样本伪称 p95。
- 不新增性能硬门禁；若测出额外 OCR 或逐票 SQL，先修正实现再交付，不以宽松阈值掩盖退化。

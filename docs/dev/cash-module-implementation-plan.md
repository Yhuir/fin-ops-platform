## 1. 历史结论：前后端联调后发布现金分支（本轮main交付见§16）

后端主体已先行实现，本轮接入真实App前端并补齐查询展示。使用独立本地测试库验证写入/删除，生产只读验证，不创建试验现金、不创建受限角色。Make仅提供视觉参考，其内存数据、固定金额和模拟保存没有进入生产实现。

- **后端可作为一个完整开发任务交付**，内部按 B01–B10 小步实现和正常 Git 提交；不是一个巨型 service 或一次不可审查的大补丁。
- “次日前端”可以作为用户安排，但**不能保证后端一天完成**。耗时取决于 OA 原始字段核查、现有连接/权限配置和真实 PostgreSQL 并发与回归结果；不能为赶日期省掉这些实际验证。
- 后端完成指可供前端接入的真实 API、存储、业务闭环及服务器侧验证完成，**不等于现金页面可用或整个模块上线**。浏览器交互、导航、设置页权限勾选、现金页端到端和页面耗时由 F 阶段负责。
- 后端阶段不修改现金页面外观、不登记现金导航或权限checkbox、不增加前端临时页面。此前独立部署安排现已暂停；新增API仍必须登录并拥有cash页面权限。005默认管理员可用，其他账号不自动获授cash。
- 业务R1–R7已确认；OA真实字段/阶段编码/字典/分页仍是开发者必须完成的只读技术核查，不能用已有的固定`active`代替。

### 1.1 必须坚持、也必须纠正的绝对化理念

1. **同进程同库不能理论保证零bug、零资源影响。** 按最新要求使用同一数据库账号，靠页面权限、连接预算、明确I/O、旧页回归和同时负载测量降低并验证风险；不宣称数据库账号隔离。
2. **禁止跨池读取，就不能自动跨池查重。** 保证现金不自动复制入普通池、多报表不复制现金；不能暗中查普通金额/hash 判断人为重复。
3. **旧代码按替代关系清理，不是凡旧必删。** 普通页面仍使用的 cash-special、二态项目设置和历史迁移不能因名字相似删除；真正被现金新实现替代的临时/假数据链在同次接线中移除。
4. **禁止兜底不等于禁止明确错误处理。** 权限拒绝、事务回滚、冲突、超时提示和表单草稿保留是正确行为；普通池、假数据、0、上月金额或旧 OA 状态作为替代结果才是禁止的兜底。
5. **不写全局历史不等于撤掉身份/授权。** 现金业务及现金配置均不写全局 requested/completed；005 在平台设置更改页面 ACL 的既有安全审计保留，不包含现金正文。
6. **按需读取 OA 不是瞬时推送。** 保存新项目归属以服务端只读复核时刻为准，OA 与现金库不构成跨系统事务；不新增同步平台或分布式事务。
7. **删除现金不等于撤回真实支付或删除全部关联业务。** 正文物理删除、最少技术身份防旧请求复活；源借款按 R5 明确纠正，其他真实现金/独立非现金事实保留，不能自动造债务。
8. **临时备份清理不能删除主库或唯一恢复资料。** 只清理本任务明确创建且已不再用于恢复的临时 dump/副本；常规备份/PITR、原 Excel 和主数据库不删。
9. **后端交付和页面交付不同。** API 测试不能代替真实浏览器的删除确认、撤权清理、旧响应回填和 receipt→DOM 耗时；F 阶段不能被省略。

### 1.2 保留的最少结构

同一个PostgreSQL、同一App数据库登录账号、cash独立表与有界小池；route → service → repository；OA集成owner的项目只读方法；主键/事务/唯一约束/必要版本检查。持久化为技术设计中的8类核心表，加稳定账单分组cash.bill_labels和最少已删身份cash.deleted_submission_ids，共10表；不为减少表数把稳定身份塞进名称/任意JSON。最新导航目标为左侧四子页、现金流水独立、账目三Tab；仅前端重组，不预建报表平台或专用数据库账号配置。

不新增第二数据库、微服务、RLS 平台、消息总线、worker、页面 read model、Redis 缓存、通用幂等平台、回收站、私有审计、OCR、导入、外部通知或在线说明 CMS。为删除防复活留下技术设计 §4 已说明的最少身份，不保存业务正文，也不扩成通用审计库。

### 2.1 已确认的验收例子，不代表测试已经通过

| 例子 | 正确结果 |
| --- | --- |
| 期初 1000、收入 200、支出 100 | 期末 1100；支出不自动全部成为真实花销 |
| 受管理 A 向受管理 B 互转 300 | A -300、B +300、全池净额 0，池外收入/支出不放大 |
| 一笔现金 100 分配同项目两事项 40/60，另有同额现金 100 | 第一笔仍只 100，两笔共 200；不能一对多 JOIN 放大或按金额去重 |
| 票据来源 100，已使用 40 | 可再用 60、不可用 70；将原使用改为抵债不再占一次票源 |
| 个人票抵 100 后，公司现金回款 100 | 公司应收减少 100、现金增加 100；个人不再减少第二个 100 |
| 11 月实际代付 12 月账单 | 个人矩阵只计实际 11 月一次；账单月单独显示，不重复记提前还 |
| 月目标 100，实际分次 40/60，删除 40 | 有效实际余 60，恢复部分办理；删除前现金只有两笔，删后只有剩余一笔 |
| 月目标未知或点击未还/核对完成 | 未知目标不以 0/上月实际补齐；未还不完成，核对完成不生成现金 |
| 借款来源 1000、真实归还 200，来源改 800 | 来源现金/源事项一致修正，归还 200 保留，未还 600 |
| 原借款根本不存在，已有真实收款 200 | 删除错误来源及仅由其建立的义务，解除错误归还关系，真实收款保留为未分配；不造新债务 |
| 借款改为 100 但已归还 200，或有独立真实非现金后续 | 明确提交受影响分配的纠正方案；不自动截额、删真实事实或假装成功 |
| 独立非现金冲抵 40 改 30 | 原来源占用/目标贡献撤回后按 30 校验保存；现金不变；其他处理保留 |

### 2.3 R7已确认：历史项目结算闭环

用户已接受[历史项目结算规则](../product-specs/cash-module-design.md#102-r7-已确认历史项目结算不是自由新增项目)。自由新增/改选为selection，当前项目必须真实非结束且允许；既有事项真实结算为existing_item，由服务端沿用本地项目ID/名称，不请求OA、不受当前允许集合影响。锚点必须实际参与正额现金分配，事务内校验版本/方向/额度及全部目标同项目；禁止夹带新事项、补本金、混项目或伪造项目。任务new_flow复用同一命令，已有流水认领不改项目或重复分配。

首次使用cash为空时，R3期初旧未结的项目识别须单独落实：仅非现金opening义务可从OA all识别真实历史项目（含结束），不产生flow、不开放普通现金新增。源已消失又无可信本地快照时明确资料缺失，不能猜ID或偷改无项目。R7随后才沿用该真实本地事项。此为已有期初功能的细化，不加新表/模式平台或业务审批轮次。

project_mode只决定首次资格路径，不持久化。重试核对最终项目/现金/原分配等已存业务事实；相同结果零写返回，不同结果409，不能承诺识别未保存的原请求模式。原付款已结清锚点不妨碍返回原未变结果。B05/B06/B07/B09与F03/F05据此实施；当前没有剩余业务选项需要重复确认，但OA/PG真实事实仍须B01核实。

### 2.4 本轮技术复审的具体补齐项

- B04：个人账独立起算存现有settings字段，先设日期再录opening，无首用循环；阶段configured用明确布尔值，个人配置不误标OA设置。
- B05/B06：origin_items仅绑定已真实loan的迟录现金，origin_mode区分新建/补绑定；已有费用走expense_payment，不重复本金或已付额；item_reference_changes同事务纠正子事项引用。
- B06/B08：义务资金与费用两个固定观察口径各自不超flow金额，不横向计成重复现金；累计退款不超实际已付和原费用，原100实付50已退40最多再退10。费用事件不重复往来现金列。
- B07：actual>0不可清空月目标；B08补实际日期、is_opening及无账单组筛选，个人矩阵下钻不误用账单月。
- B09/F05：技术TC21–TC27覆盖上述具体修正；TC28覆盖已确认R7、首次期初历史项目识别与同结果重放。本轮只定义测试，不提前假报通过。无新增表、worker、缓存或通用引擎。

### 3.2 后端交付 B01–B10

每项“完成条件”是正常工作的输出定义，不要求用户逐项审批。先识别该项规则并补适用测试，再实现，再运行对应验证；不让只读检查取代实际代码和测量。

#### B01 只读核实 OA 与现有集成事实

- **依赖**：用户明确授权开始后端实施；若当次只授权 OA 查看，仅做本项的只读部分。

- **输出**：精确 source→DTO 映射、字典 code/label/结束语义、全列表分页/授权范围；开发/测试 DB 及角色配置方式；记录脱敏结构，不保存凭据或真实流水。
- **验证**：覆盖至少一个实际阶段、结束/空/未知状态、同名不同 ID、第一页/后页/总数；确认仅项目资料，未调用 OA create/update/delete。
- **完成条件**：后续 B03 不再使用硬编码 `active` 或估计的五个名称；不能核实的真实字段被明确标出，其他不依赖它的 B02/B04 可继续，不能用假项目宣告 OA 接入完成。

#### B02 同库现金存储、安全入口与旧客户端兼容

#### B06 事项/结算、物理删除与源纠错闭环

- **依赖**：B05；任务在 B07 复用本步事务内方法，不能另造一套结算。
- **责任**：现金事项/结算 service、统一 UoW/SQL、flow 删除命令。
- **输出**：借款、票据来源、公司应收、费用、账单等技术设计明确 type；固定 kind 的结算；事项/来源/目标选择器及有界完整下钻；统一现金删除、独立非现金更正/撤销、R5 来源纠正 API。
- **动作**：票据使用可没有抵债目标，票抵必须有来源和目标；使用改抵债更新原处理，不重复占来源；现金还款只引用唯一 flow。金额/状态与版本传播按技术 §5，稳定顺序锁来源、目标与现金，在一条事务里撤旧贡献、校验并写新贡献，不在单行 CHECK 中伪装跨行 SUM。

- **历史项目**：实现opening旧未结识别真实OA历史项目→本地事项→R7真实现金结算；普通新增仍拒绝结束项目。已有事项在OA断线/源删除/阶段未配置时可结算；资格、金额、版本只查现金事实，不在错误后换selection模式兜底。
- **验证**：票据可用额/并发超额、非现金现金不变、费用只一次/退款不超额、公司回款不二抵个人；现金和独立事项删除与创建/编辑/分配并发、响应丢失重放、同 ID 跨对象类型不混淆、原详情不再返回正文、关联超预览上限、失败全回滚；R5 三类源纠错及独立处理保留。
- **完成条件**：仅 API 即可完成收付→归还/冲抵→纠错/删除全链，不依赖后台修复、前端补偿或人工 SQL；旧请求不能重建删除正文/贡献。

- **开工范围**：沿用codex/cash-ledger和当前已有后端成果；识别工作区已有修改，不重写后端、不清空用户改动。前端新增集中在CashPage、features/cash、components/cash；共享变更限pageRegistry/AppSidebar及现有005权限选项必要接线。后端新增范围限上述3个现金报表展示字段与为真实联调必须修复的具体问题；新字段无需数据库迁移。若发现必须改变既定业务、公共组件API或扩大重构，先说明真实场景，不借移植扩展范围。

- **完成交付**：列实际改动与旧代码清理、七类测试适用性/命令/结果、Make与App可查看画面对照、性能环境/样本/分位数/错误、未测风险及更新文档。不开额外审批平台、不要求每一步用户点头；功能未完成就明确列出，不把一部分可用称全模块完成。

## 6. 性能目标、测量与阶段归属

### 6.1 设计约束

- cash 报表只读 cash.*，OA 请求单独，外部网络不在 SQL 行锁内。
- 服务端 SQL 筛选/分页/集合聚合；列表/合计/总数同一短只读快照，不逐行读 OA/事项，不在 Python/浏览器全量算账。
- 技术 §8.8 的页大小、日期跨度、SQL/锁/连接/OA 超时是测量起点；普通查询默认 50/最大 200、详情预览 20 但可分页查看全部，预览上限不限制真正删除关联。普通期间 366 天的建议不禁止明确父事项/月任务的跨年有界下钻。
- 连接总额不超现有预算；局部 SQL/锁超时不放宽现有更严限制，不改全局 PG 参数。模板补月用集合 SQL/月唯一键，一次短事务，不逐行网络调用。
- 索引先覆盖日期/id、账户日期、任务/月唯一和事项/来源/现金关联；后续依 EXPLAIN，不为每个筛选预建复合索引。
- 不先增缓存、分区、物化视图、报表副本或 worker；减少列/行→SQL/索引→事务/分页→复测。不能为耗时返回旧值/0 或漏所需字段。

蓝色方框不能归因于全局active污染：鼠标选中无outline，键盘切换可复现2px focus-visible。保留可见焦点，常态底线与焦点分开验证。不用删无障碍样式掩盖差异。

# 现金模块实施计划与复审

更新日期：2026-09-07。

工作分支：`codex/cash-ledger`。配套事实源：[现金模块开发设计](../product-specs/cash-module-design.md)。本文写实施顺序、变更范围与验证，不另写一套 UI/记账规则。

状态：**详细待批准计划；本轮仅文档，不实施应用代码、DDL、数据迁移或发布。** OA 原五个估计名称已撤销，以真实阶段为准。本任务不使用 GSD，不创建 goal、冻结 contract、baseline、hash 或新的 gate 平台；现有安全/发布措施保持不变。

## 1. 重新审阅的结论

整体方向可行，需要局部修正，不需要重建 App 或新建数据库。最小形态是：现有 App 内一个懒加载现金页面、一个现金 API family、清晰的 service/repository、同一个 PostgreSQL 的现金表，以及 OA 集成 owner 提供的一条项目资料只读边界。

| 原计划问题 | 本次修正 | 不做什么 |
| --- | --- | --- |
| 现金项目手工维护，与最新 OA 需求冲突 | 取消手工项目表；读取真实项目/阶段，现金只保存可选阶段集合及流水历史名称快照 | 不做 OA 项目编辑、双向同步、手工状态覆盖 |
| 以 `active/completed` 代表 OA 阶段 | 现金使用单独的真实阶段读取结果，旧普通页面语义不变 | 不把 OA 十阶段塞入普通 App 的二态字段 |
| 仅获取已有项目的阶段可能漏选项 | 读取 OA 权威阶段字典 + 项目记录 | 不将当前项目去重结果冒充完整字典 |
| 项目结束可能让历史账不可用 | 候选资格只影响新增/改选；旧账本地显示原 ID/名称 | 不删历史关联、不每行查 OA |
| 用当前任务模板推算所有历史月份 | 生效月份 + 已处理记录必要快照；历史未落库待办不凭空生成，待用户认可 | 不先建通用模板版本系统 |
| 任务完成、现金收付、票抵容易混淆 | 区分现金事实、义务事项、结算分配；核对完成不生成钱 | 不建双重记账引擎，不按报表复制流水 |
| 没有可操作的旧链路清理表 | 第 4 节逐项区分替代、保留和已退役路径 | 不全仓清理、不因名字含 cash 就删除 |
| 性能只有形容词 | 第 6 节给出数据规模、测量指标和改进顺序 | 不用缓存/异步掩盖慢 SQL |
| UI 原型等于可上线代码的风险 | 复用 App 的 FinanceTable/AppDrawer、局部样式和请求方式 | 不覆盖 App 外壳、不整体复制 Make 依赖 |

### 1.1 需要纠正的绝对化要求

1. **同进程、同库不能理论保证零 bug、零资源影响。** 应通过依赖隔离、数据库权限、有界并发、普通页面回归和同时负载测量证明风险受控。不能把设计审阅当成性能/正确性实测。
2. **两个流水池禁止互读，就不能自动跨池查重。** 可保证不自动复制、不为报表重复造流水；人为把同一现实交易录两遍只能先明确业务归属，不能暗中跨池查金额/hash。
3. **旧代码必须按调用与替代关系处理，不能凡旧必删。** 普通页面还在使用的现金特殊标记和项目状态逻辑不属于新现金账旧实现，删除它们会直接违反“不影响旧页面”。
4. **禁止兜底不等于禁止明确错误处理。** 事务回滚、重复提交识别、权限拒绝、超时提示和表单保留属于正确行为；静默使用普通池、假数据、0、上月金额或旧项目状态才是禁止的兜底。
5. **不写全局操作历史不等于取消安全保护。** 身份、页面权限和最少技术诊断仍在；005 在平台设置维护页面 ACL 的现有安全审计不随现金业务一起取消。
6. **OA 按需读取不等于瞬时推送。** 新增项目复核与现金提交不具备跨系统原子性，只承诺以服务端复核时刻判断，不建设分布式事务。
7. **清理备份只能清理本任务明确创建的临时恢复资料。** 不删除主数据库、既有备份或尚在故障恢复中唯一可用的副本；本轮不需要备份。

### 1.2 简化后保留的必要结构

- 同库 `cash` schema 与现金运行角色：不是第二数据库，也不是 guest/editor 角色层级。角色解决普通 SQL 误读现金表的具体场景。
- route → service → repository：对应现有工程职责，不再增加 facade/controller/manager 套层。OA adapter 留在 OA owner，不嵌入现金 SQL。
- 主键、事务、内部外键、唯一约束和必要版本 CAS：解决重复确认、并发编辑、半写入。不加内容 hash 或通用幂等平台。
- 页面 ACL 与现金审计排除：放在现有安全入口，不在每个按钮外再堆审批。
- 3 个一级 Tab + 4 个同级账簿：月份/年份为筛选，未来扩展只是增加局部视图，不预建动态报表框架。

## 2. 设计定案输入（编码前收口，不猜业务）

本表是业务和技术输入，不是一串独立审批 gate。先通过少量实例和表单集中收口，再由用户一次明确确认完整设计/计划。用户未确认前，下面的实现工作项只是待执行清单。

| 编号 | 必须收口的内容 | 建议的最简单方案/核查动作 | 影响工作项 |
| --- | --- | --- | --- |
| D1 | 真实 OA 阶段字段、code/label、字典、ID、项目分页及授权范围 | 开发者只读核查源项目表单和字典，核验各已知阶段及列表完整性；不是让用户提供技术字段 | P2 |
| D2 | 现金账户范围、期初现金/欠款、启用日期、币种、负余额、退款与补录规则 | 不导入 Excel；手工设置经确认的期初和未结事项；起算日前记录如何处理必须明确 | P1、P3、P4 |
| D3 | 现金归还、有票冲抵、无票冲抵、冲账、报账提现、真实花销的金额影响 | 用下表的虚构例子确认“现金/应收应付/真实花销”三列；不能用一套通用减法替代 | P3、P4 |
| D4 | 任务单次或分次、撤销/作废、账单拆分、本月模板修改、历史未处理任务 | 建议先单次确认、有效/作废、只保留已处理历史；需明确拆分是事项用途，还是同一现金跨项目分摊；若跨项目先定义分配金额模型，禁止每项目重复计整笔 | P1、P4、P5 |
| D5 | 页内或关页后提醒、未还后再提醒、29/30/31、跨月、浮动日期 | 建议仅页内到期/提前提醒，不默认外部通知；无对应日期时提示配置，不静默改月末 | P5 |
| D6 | 真实阶段初始允许集合、无项目流水是否可录、历史改选结束项目是否禁止 | 已结束始终不供新增/改选；建议未中标也不选，其余按真实字典勾选；无项目业务不得伪造项目 | P2、P3 |
| D7 | 具体表单字段、必填/选填、金额精度上限、各事项状态、个人账提前还款归属 | 在相关表单设计时逐项确认；批准前把金额和状态机补回开发设计 | P1、P3–P5 |

附件/OCR/导出、私有操作历史、外部提醒不在默认交付范围；保留 UI 扩展位置不等于已承诺这些功能。12 项月任务是初始内容，不是系统任务上限。

### 2.1 用来定案的虚构业务例子

以下用于走通规则，**不是已确定的公司会计口径，也不是测试已通过**。仅执行纸面金额算例，不使用真实业务数据。

| 例子 | 已明确的现金结果 | 待用户确认的事项影响 |
| --- | --- | --- |
| A 账户期初 1000，收款 200，付款 100 | A 期末 1100 | 支出是否构成真实花销取决于用途 |
| A 给受管理 B 账户互转 300 | A -300、B +300、全池净额 0；池外收支 0 | 两端是否均为受管理现金账户 |
| 月任务“未还” | 现金变化 0 | 是否继续提醒及本月状态文案 |
| 月任务确认实际还款 100 | 选定现金账户 -100，一次确认只生成一次现金事实 | 对谁负债、归属账单、是否分次、真实花销 |
| 收回借款现金 80 | 现金 +80 | 哪一项应收减少、可否一笔分配多项 |
| 提供票据/有票直接冲 50 | 没有实际收付时现金变化 0 | 是提供、使用还是抵债事件；何时减少哪个欠款 |
| 无票报销冲抵 40 | 没有实际收付时现金变化 0 | 哪方债务减少，是否构成真实花销 |
| 报账提现/等公司回款 | 只有实际到账才增加现金 | 申请、提供票、抵账、实际回款是否独立，不重复冲减 |

定案产物：更新开发设计中的具体字段/状态/金额规则及对应例子结果。Excel 的错误引用、外部期初链接、颜色和 Make 演示算法均不能代替上述结果。

## 3. 模块边界、文件归属与交付顺序

### 3.1 预期文件范围

表中“新增”是未来拟议名称，不表示文件已存在。无需一次生成所有文件；只在对应业务落地时创建。

| 层/owner | 文件范围 | 最小变化 |
| --- | --- | --- |
| 现金 UI（新增） | `web/src/pages/CashPage.tsx`、`web/src/features/cash/` | `api.ts`/类型、各账簿及任务/设置局部组件；页面状态不进全局业务 store |
| App Shell（现有） | `web/src/app/pageRegistry.tsx`、必要的页面 key 类型与 ACL 选项 | 登记现金 route/lazy chunk；不改 Router/mount 策略、不复制侧栏 |
| 现金 HTTP（新增） | `backend/src/fin_ops_platform/app/routes_cash.py` | 仅请求解析、授权、service 调用与响应映射 |
| 现金业务（新增） | `services/cash_service.py`、必要时 `services/cash_tasks.py` / `cash_settlements.py` | 收付/配置入口与具体任务/结算规则；不先为每张表建一个 service |
| 现金 SQL（新增） | `services/postgres_repositories/cash.py` | 现金 UoW、SQL、分页与组合查询；复杂度确有增长再拆文件 |
| OA 集成（现有 owner） | `services/mongo_oa_adapter.py`，必要时提取同 owner 的小型项目字段 mapper | 复用连接基础、增加明确项目/阶段只读方法，不修改现有普通项目 DTO 或 OA 财务同步 |
| 权限/通用审计（现有） | `app/route_access_policy.py`、`services/access_control_service.py`、page key normalization、`app/server.py` | 注册一个 page key；显式审计排除；不改普通写的审计失败保护 |
| 技术日志（现有） | `app/http_adapter.py`、`services/api_performance_metrics.py`、相关 Nginx/访问日志配置 | 检查是否泄露现金 ID/查询正文；只修真实出口，不新建日志系统 |
| 依赖组装/数据库（现有） | `app/application_factory.py`、`app/server.py`、现有 PostgreSQL pool 基础、`postgres/migrations/` | 注入明确现金依赖、同库受限角色连接；沿用迁移工具，迁移号实施时取下一个可用号 |
| App Health / reset（现有） | `services/page_audit_registry.py`、相关 system audit/query owner、`services/settings_data_reset_service.py` 及其 repository | 现金事实排除；普通覆盖和保护保持；不接入全局 jobs/统计 |
| 验证（新增/更新） | `tests/test_cash_*.py`、`web/src/test/Cash*.test.tsx`、`web/e2e/cash-*.spec.ts` 与受影响旧测试 | 新测试不依赖真实 Excel/OA；真实 PostgreSQL 权限/事务另测 |

后端相对路径均以 `backend/src/fin_ops_platform/` 为前缀。应用构造只组装依赖，不连接 OA 拉项目、不自动初始化现金数据。现金运行依赖缺失时对应现金请求明确 503；不回退普通 DSN、不让无关页面启动依赖现金资料。部署阶段仍须配置好真实现金运行凭据。

- 将 D2–D7 用虚构例子与具体表单收口；明确未分配项目与账单拆分，不制造默认业务。
- 按开发设计第 4 节修改/审阅 UI：3 一级 Tab、4 账簿；补 OA 设置、非现金登记、任务实际确认。Figma 不可编辑时仍可先审阅字段/交互说明，不能谎称已改原型；最终视觉未确认须明说。
- 补全字段和 API，保留“设计建议/已确认”的区别；用户明确批准完整计划后才执行 P1 起的代码工作。

### 3.3 P1：现金存储与安全边界

依赖：P0；先做这一步，避免先让现金请求经过会写全局历史的旧通用路径。

实施动作：

1. 新增现金 schema 与已定案表，先基础六表，需要事项功能时再加事项/分配表；不改普通业务事实表，不导入 Excel。
2. 沿用 migration 工具；不修改已应用历史 SQL。既有迁移 checksum 保留，不添加现金内容 hash 或新的校验框架。
3. 现金运行角色只拥有现金表/序列必要权限；普通 API/worker 无现金表权限。核对 PUBLIC、role membership、owner 和 definer/view 旁路；不动态 SET ROLE。
4. 现金连接按同一数据库配置校验目标，独立受限凭据复用连接池实现；现金 pool 与普通 pool 的总量不增加到超过现有预算。不要假定新开一大池不会影响旧页面。
5. 注册 `cash`（拟议 page key）与 `/cash`（拟议前端 route）、`/api/cash/...`。全部现金接口只接受现金页权限；管理员固定 005；普通账户默认没有新页面权限。
6. 在已登记现金路由上使用一个明确的全局历史排除判断，两处 requested/completed 都使用它；请求仍按真实写操作鉴权/校验。不要通过 read-only POST allowlist 逃避审计。
7. 检查全局状态、System Audit、reset、schema grants 和日志出口；现金不加入全局业务计数/审计证明，不把“跳过现金”伪装成已审计现金。
8. 同步最小模块文档（第 8 节）。

验证：真实测试库内双向权限拒绝；现金成功/失败/配置请求全局 audit 零新增；普通写审计故障仍阻止普通写；cash-only 账号不能访问普通页面/任务；现金连接故障不破坏银行明细的正常请求。

特别注意：当前 `/api/background-jobs` 的页面映射来自 `ASSIGNABLE_PAGE_KEYS`。新增 cash key 时不得顺带授予 cash-only 账号普通后台任务访问；该 route 应继续限定原有普通业务 owner，并保留各 job 自己的授权。相同检查覆盖全局 registries 的“所有页面”集合，不能机械加入现金事实查询。

### 3.4 P2：OA 项目只读与可选阶段设置

依赖：P1 + D1/D6 已定案。与 P3 的局部 UI 外壳可并行，但不能让表单使用假项目完成集成。

实施动作：

1. 在 OA owner 内实现项目基础资料的精确读取及阶段字典解析；请求受限、只读、异常明确；不进入附件/OCR/付款/报销同步。
2. 显式修订 OA 模块边界，允许此“项目资料按需只读”方法；现有“财务事实禁止 HTTP Mongo 直读/inline sync”保护不变。若需要改变更多现有约束，先报告，不能悄悄扩成共享同步重构。
3. `GET /api/cash/projects` 返回开发设计第 8 节的有界 DTO；all/selection 模式分开；分页不遗漏、不伪报总数，阶段选项不来自当前页去重。
4. 配置只写 cash.settings。已结束不能放进允许集合；未知代码拒绝保存，新阶段未选中；项目本身只读。
5. 列表包含已结束与阶段异常项目；候选只包含允许阶段且非结束的项目。普通 App 的手工项目、删除 override、completed IDs 不参与。
6. 新增/改选项目在后端按 OA ID 复核；OA I/O 在现金事务外，事务内再核对允许集合/版本；不受信前端传来的名称、阶段或 selectable。
7. 历史使用现金记录的项目 ID/名称快照；OA 结束/删除/断线不让历史流水消失。仅允许的不改项目编辑不触发候选重验。
8. 历史报表项目筛选从现金历史关联有界读取，与录入 selection 候选分开；结束/源删除项目仍可按 ID 筛选旧账，不需要 OA 在线。

验证：真实阶段映射脱敏样例、未知/空/新增阶段、同名 ID、项目结束、配置并发改变、OA 超时/权限不足/分页失败；全程 OA 写方法零调用、普通财务表零访问。断开项目读取时历史账仍能读，当前候选明确不可用。

### 3.5 P3：手工流水与现金总账闭环

依赖：P1/P2 和 D2/D7。

实施动作：

1. 现金账户/分类的本地配置与启停；期初与业务启用时点明确校验，不把旧 Excel 外链金额自动当期初。
2. 录入收款、付款、现金账户互转，使用一个正金额 + 明确两端账户的简化模型。不把信用卡还款默认做成互转。
3. 保存前检验字段、金额精度/范围、账户有效性、项目资格；服务端生成可信 actor 字段；现金事实在一条短事务内提交。
4. 使用稳定随机提交 ID 防双击/网络不确定重试。相同 ID 与已保存业务内容一致返回原结果，不同内容/已修改对象明确 409；不按金额/备注自动查重，不新增 hash。
5. SQL 完成日期/账户/项目/分类筛选、固定排序、分页、账户余额与筛选合计；列表/汇总/总数用同一短只读快照。账序余额不受金额排序或关键词筛选改变。
6. 新增界面用现有 AppDrawer/FinanceTable 和金额格式；提交中禁重复点击、失败保留草稿、成功后只重读现金当前视图；切页/撤权/退出清空现金局部状态并取消旧请求。
7. 实现已经批准的编辑/作废规则；被任务/事项引用的流水不能绕过所属命令直接改金额或删除。

验证：收/付/互转金额、两端账户约束、空/非法金额、跨年/起算日前日期、启停账户、并发编辑、双击、提交成功但响应丢失、分页余额、空表/报错区分。新增任意现金金额后普通银行/成本/往来/发票页面结果不改变。

### 3.6 P4：往来、有票支付、个人账与结算

依赖：P3；D3/D4/D7 定案。先完成本步事项/结算核心，再在 P5 接入任务确认，避免任务先写不存在的分配表或重复实现事务。此时用手工现金收付验证三本账；任务来源的报表用例在 P5 补齐。

实施动作：

1. 根据已确认的虚构例子确定事项种类、原始义务、结算记录与金额作用方向；分开“原始金额”“已结算”“未结”，不复制现金收付。
2. 现金归还引用已有 flow；非现金冲抵直接登记结算，无 flow。一次实际收付分配到多个事项时，分配金额合计受该笔现金金额约束。
3. 票据提供、使用、抵债和实际回款分开；具体状态由事实推导或由明确命令改变，不让一次状态点击同时制造现金和重复抵债。
4. 冲抵写事务按稳定顺序锁相关事项/flow，计算剩余额；并发超额、重复分配、跨对象冲抵明确拒绝。不用单行 CHECK 假装能验证跨行 SUM。
5. 账户/事项期初、跨年、提前还款按确认定义只承接一次；有票小计不照搬可能漏算的 Excel 公式。
6. 三本账仅为专属查询/视图：往来保留冲账/还款/报账提现/真实花销/票抵；有票支付跟踪提供人/抵账对象/回款；个人账显示月矩阵与三类归还/冲抵明细。
7. 两张卡/不同用途若需要记录拆分，用明确事项/分配表及详情；只读办理说明不建设审批、银行付款或发票 OCR。无用户需求不建信用卡产品系统。
8. 更正/作废结算必须同时更新关联可用余额；不物理删除被历史引用的事实。按批准规则恢复任务/事项，不用后台补偿修半笔账。

验证：现金归还、非现金冲抵、部分/多项分配、超额、重复、并发、作废恢复、票已给未回款、提前还款、跨年欠款、单笔多账展示只有一条 flow。非现金例子的现金余额严格不变。

### 3.7 P5：月任务和页内提醒闭环

依赖：P3/P4，D4/D5；若 D4 确认需要分次，先更新表模型/API，不带着一对一约束实现后再补绕过分支。

实施动作：

1. 配置任务模板，保留 Excel 的 6 收入 + 6 支出方向及其他核对/催办；不由“工资”等文案猜方向。
2. 执行日/提前天数用 Asia/Shanghai 日期计算；提醒列表覆盖当前月与提醒窗口触及的下月任务，归属月份仍是实际任务月份。
3. GET 仅计算列表，不创建 occurrence/job。首次实际处理在事务内创建当月唯一 occurrence；处理记录保存必要模板字段快照。
4. “未收/未付/未还”不生成 flow；核对完成只改处理状态。已收/已付/已还必须确认实际日期、金额、账户及必要关联，不拿 0/上月金额当完成。
5. `template_id + month` 唯一避免两条月度实例；flow 数量和完成条件遵守已批准单次/分次规则。复用 P4 已有的事务内结算方法，occurrence/flow/事项分配由调用方持有的一个现金事务提交，内部方法不另开事务。
6. 同内容重放不重复流水；模板修改/停用不重写已处理历史；修正生成流水通过同一命令同步更新任务和分配，失败全部回滚。

验证：提前提醒、跨月、2 月与 29/30/31、过去/未来月份、模板启停/改日期、重复并发确认、未还后处理、任务确认失败、作废/撤销后报表与任务一致。补齐任务来源在 P4 三本账的展示和金额用例。若最终选择外部提醒，此项需单独补渠道/投递/隐私设计，当前计划不能算已覆盖关页提醒。

## 6. 性能目标与实际测量方法

### 6.1 设计约束

- 报表只查 cash.*，不依赖 OA/全局 jobs；项目查询单独请求，不能挡住历史账主表。
- 单次页大小建议默认 50、最大 200；默认月、支持年；任意跨多年扫描先明确范围与超时。数值为技术建议，UI 定案时调整，不暗改普通页合同。
- 使用 set-based SQL，一次分页和一组聚合，不逐行查项目/事项。索引先覆盖 `(occurred_on,id)`、账户/日期查询、任务/月唯一键、结算 item/flow 外键；是否新增额外索引由执行计划决定。
- 精确 total、汇总和分页来自同一短只读快照。复杂报表不在浏览器拉全量重算；分账户余额和池外收支规则不能为速度改变。
- 查询和连接等待必须有上限；OA 独立总超时，不在 SQL 行锁内等网络。不建立每个请求自动重试多次的链路。
- 不新增 Redis、物化视图、分区、报表副本或 cash worker；先测 SQL/索引/返回字段，确有证据再提独立优化。

### 6.2 测量清单

下列是建议的体验目标和实施期实验，不是新的冻结 baseline/gate，也不是本次结果。既有[正式性能合同](../operations/performance-contract.md)不降低、不删除。

| 场景 | 数据与并发 | 记录/目标 |
| --- | --- | --- |
| 现金月/年总账、筛选、后页、三本事项账 | 10,000 条合成流水作为常用规模；100,000 条作为增长实验；关联事项/任务按实际比例生成 | HTTP/SQL/payload/连接获取分开计时；本地正常目标 p95 ≤ 500ms、p99 ≤ 1000ms；未达到先分析，不假报“极高性能” |
| 普通写与任务确认 | 稳定 ID 重试、2–4 并发确认、真实测试 PG | 无重复/半写；PG 提交目标 p95 ≤ 500ms；含 OA 校验的总耗时另列，不能用纯 DB 耗时代替用户等待 |
| 写成功到页面显示 | 真实 API + 浏览器同一时钟 | 沿用现有 receipt→GET→DOM 测法，目标 p99 ≤ 3000ms；充分样本后才报告分位数 |
| OA 项目列表/阶段字典/提交单项目复核 | 实际授权范围只读采样；设置第一页/后页与候选分别测 | 记录调用数、总数/页数、p50/p95、错误；初期建议请求总超时 2s，按实际源能力确认，不声称零延迟 |
| 与旧页面同时使用 | 测试环境现金 1/4 并发与普通银行、关联台、成本/往来同窗请求 | 比较改动前后延迟/错误/连接等待；旧页保持现有性能合同，无 pool 饱和、现金引起的额外 SQL 或业务数据变化 |
| 页面代码负担 | 生产构建 + 浏览器普通页/现金页 | 现金 chunk 懒加载；普通页不下载业务数据，复用共享组件不加入第二 UI 库 |

每个主要场景至少使用足以支撑分位数的重复样本（建议 100 次有效请求，记录预热与测量各自数量）；错误单独统计，不删除慢样本。记录环境、样本行数、查询参数类别、并发、query count、耗时、响应体大小，不保留真实现金 payload 或凭据。对旧页面的测量比较复用当前工具，不新建长期 baseline 管理平台。

`EXPLAIN (ANALYZE, BUFFERS)`、合成批量写入和压测仅在批准的测试库，不在生产运行。资源问题按“减少读取列/行 → SQL/索引 → 缩短事务/分页 → 复测”的顺序处理；不能为了延迟返回旧值、0 合计或省掉用户要看的字段。

## 7. 安全与操作边界：少检查层，多真实验证

只保留以下必要边界，不新增每工作项的审批状态机：

- **用户实施批准**：用户已明确要求计划完成前不写代码，必须遵守。
- **安全边界**：页面授权、现金 DB 权限、输入/金额/事务约束、敏感日志排除；这些是运行正确性，不是额外管理流程。

- **正式发布边界**：使用既有部署流程；不删除既有 release/audit/migration 保护，也不加一套现金专用 gate。

本轮不新增 hash。数据唯一性靠 ID/唯一约束，业务原子性靠事务，并发编辑靠版本和锁，行为覆盖靠类型和测试，文档历史靠 Git。唯一新增 DB 角色的理由是普通合法 SQL 误读现金隐私表，主键/事务/类型/普通测试无法在运行时拒绝这一授权错误；原生 GRANT 能直接解决。无需再加 RLS、通用策略引擎或新校验凭证。

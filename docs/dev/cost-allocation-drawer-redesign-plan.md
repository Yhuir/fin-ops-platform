# 成本待分配抽屉：紧凑两栏与表格重构计划

日期：2026-09-09。状态：已按用户授权完成 Make V8 设计迭代、App 实施和上线验证，发布验证结果以[实施记录](../modules/cost-statistics/implementation-notes.md)为准。下文保留实施依据，不使用 GSD，不新增门禁。

本计划承接已上线的[银行来源分配](cost-statistics-source-allocation-plan.md)，仅调整待分配抽屉的信息结构和输入方式。现有业务事实仍以[成本边界与 I/O](../modules/cost-statistics/boundary-io.md)为准；当前运行时事实与验证结果维护在模块文档中。

## 1. 目标及边界

- 展开一个关联组后，上方左 OA、右银行流水，下方一张成本分配表。
- 内部 case、OA、流水 ID 不进入可见标题、正文、下拉项、退款区和提示；程序内部继续使用真实 ID 关联、保存和保持行身份。
- 删除常驻的已分/剩余金额、支出减退款公式和输入区重复原额。上方保留一次原始业务金额，发生错误时给出简短、可定位的反馈。
- 表格每行对应一个 OA 成本项到一笔来源支出的金额分配；账户、标签、付款日期同源、只读。
- 每个关联组独立草稿、独立保存；保留来源缺失、零成本、退款、非成本、权限、错误与并发处理能力。
- 优先局限于当前 Cost 前端。复用现有 GET/PUT，不新增表、迁移、worker、read model、缓存、依赖或关联台写链路。
- 本轮不重新设计三个统计视角、银行明细、关联台或公共 Drawer。后续若证据显示必须改变后台合同，应先明确具体缺失字段和最小影响范围，不猜字段或扩大重构。

## 3. 最终信息结构

### 3.1 关联组标题

项目名或项目名集合、待分配/已完成状态、成本项数与流水数；有修改时保留简短“未保存”。内部 ID、原额与净额的重复组合删除。继续一次展开一个关联组，切换保留其草稿。

### 3.2 上方两栏

| OA 栏 | 银行流水栏 |
| --- | --- |
| 项目、申请人、申请类型 | 银行账户名称/尾号、对方 |
| 申请事由或成本项内容 | 付款时间、原始金额 |
| 原始金额，仅在依据区出现一次 | 银行标签，长路径完整可读 |
| 同一 OA 下组织多个成本项 | 支出/付错退款以短标识区分 |

- 两栏展示关联组成员，不按相同行号或连线暗示一一配对，不预选来源。
- 一张 OA 多个成本项时明确显示“X张OA / Y个成本项”，不混用数量。
- 当前 DTO 没有正式业务单号字段，不把 `oaId` 改名冒充业务单号。优先用申请人、项目、内容、金额识别；过长内容可在本项展开阅读全文。
- 来源选择器与上方列表使用一致业务描述；同账户同日流水需要显示足以区分的时间、金额与对方。显示属性仍完全相同时可用局部表格序号辅助定位，不能猜其唯一性或改用项目名作为主键。
- OA 原始费用类型不参与来源分类，也不在输入区重复展示。
- 两栏不各自制造多个嵌套滚动容器。长内容保证可访问，具体折行/展开效果在 Make 浏览器验证后确定。

### 3.3 下方分配表

列顺序：`项目 | OA/成本项 | 来源流水 | 银行标签 | 分配金额 | 操作`。

- 每条来源分配是一行；相同项目/OA的连续行可以采用紧凑分组显示，不能重新变成每项大卡片。
- 项目与 OA 是只读归属；新增行先明确成本项。在该项的新增入口创建时继承归属，避免跨项误加。
- 来源仅可从本关联的支出流水选择；选择器展示账户、日期、原额、对方。选中后紧凑显示，标签只读，不提供独立账户/标签编辑。
- 隐藏余量数字后，禁用选项仍须有简短原因，例如“已用完”；当前行已选来源必须允许重新查看和修改，不能把本行金额重复扣除后锁死自身选项。同一成本项不能重复添加同一来源，来源仍可依法分给其他成本项。
- 金额右对齐、两位小数；标签和金额不得挤到不可操作。输入列有清楚表头和可访问名称。
- 支持新增/删除、Tab连续输入、明确焦点。删除中间行不能使下一行的值或焦点串位；关闭下拉不误关抽屉。
- 没有来源行的成本项仍有新增入口，不能因零行而从表格消失。空行不代表真实零成本。
- 底部保存只作用于当前关联组；长表时确保能方便找到保存和首个错误，不把按钮绑定到其他组。
- 不引入完整 Excel 引擎、公式、拖拽配对或批量粘贴；本次“Excel形式”指清晰行列和高效输入。

### 3.4 状态与特殊情况

- 退款存在时展示紧凑“退款归属”区域；每条退款选择原支出并填金额，退款不能被当作成本来源。未完成的必填退款项不得隐藏到用户无法发现的位置。
- “不计入成本”使用按需展开区域，保留来源、金额和原因。已保存的非成本数据打开后可见，不因默认折叠丢失。
- 常态不显示计算公式与余量。失焦或提交时按行/成本项/来源显示具体错误；保存跳转或聚焦首个错误，不只禁用按钮或显示“校验失败”。
- 银行资料缺失、来源事实变化、保存失败、只读和未保存是必要状态，使用简短业务文字，不能为减少文字而伪报完成。
- 任务摘要读取失败和单条任务详情读取失败分别在所属区域提供重试。详情未加载时不能把空表格显示成真实“无OA/无流水”，加载失败也不能回退演示数据。
- 来源保存后缺标签仍可 pending；回填完整来源行，按真实响应更新列表与计数。
- 保存已明确成功但页面刷新失败，应显示“已保存，刷新失败”并只重试GET，不能再次PUT。请求结果不明确时保留草稿并提示核实保存结果，通过既有详情GET核对version和实际分配内容；版本推进本身不证明本人的提交成功，不伪报失败、成功或自动重复提交，也不新增幂等表/机制。
- 切组/搜索保留草稿；关闭或主动重读脏草稿沿用现有丢弃确认；409保留输入，不自动覆盖并重试提交。
- 任务保存后移出当前页签时，焦点转到下一个任务标题或状态页签；不丢失其他组草稿，不自动保存下一组。可访问名称使用业务字段，不把已删除的内部ID转移到朗读文本中。

## 4. 去掉合计输入后的金额规则

1. `amountsFixed=true`：使用后端任务的固定 OA 原额作为目标，来源行总和必须等于该目标。正目标不能设为零，也不能因用户修改来源行就修改目标。
2. 允许人工确定成本：合法来源行按成本项精确汇总，生成现有 `allocations[{unit_id,amount}]`。这是编辑器构造提交金额，不重建后端成本业务规则。
3. 无来源行默认“未分配”；只有业务允许时可显式设为零成本。使用一个简单的显式零标记，新增来源时取消该标记。已有行需清空时不能无提示丢弃草稿，可要求先删除已有行。
4. 合法的已保存零成本回填零标记；固定零目标沿用后端事实。失效决定不得当作有效零或有效来源继续提交。
5. 历史已知成本金额但来源尚未补齐：保留服务端事实，不在加载时改成0，不反推银行来源；未完成来源前阻止提交。用户在可编辑任务中完成来源后才形成新的拟提交合计。
6. 空值、非法小数、未选来源、重复同一成本项/来源组合明确报错，不能用0代替非法输入并提交。
7. 保留逐OA、逐来源、逐退款及 `成本+非成本=净支出` 的现有校验；金额运算复用现有分/BigInt工具，提交继续为两位小数字符串。
8. 非成本额的既有输入与来源闭合暂不扩大改造；不为统一表面形式引入额外状态机。

合计始终由当前合法草稿派生，不能另存一份可编辑/缓存合计而形成双重事实。行在插入、删除、切组时使用稳定的内部行身份；显示序号、数组位置、项目名称和来源下拉文本都不能充当持久化身份。

## 6. Figma Make到App的执行顺序

### 步骤一：准备一次完整设计输入

提供用户截图、当前真实UI参考、现有Make链接与本计划，配合虚构但结构一致的演示数据。明确截图里的旧字段正是待删除内容，不照抄内部ID。Make只使用演示数据，不接生产身份/API。

桌面先以约1280–1320px宽度设计，最终根据实际可读性确定；宽度不能超过视口。窄屏上方两栏可上下排列，表格仅在自身容器横向滚动，按钮与弹层不能被截断。

### 步骤二：Make生成与浏览器迭代

生成可操作原型，检查：组标题、两栏成员、计数、输入表、来源下拉、新增/删除、特殊区域、错误、保存、长文本、滚动与窄屏。发现问题记录场景/窗口/实际/期望，定点要求Make修正，浏览器复查后再移植。

代表样例：单OA跨月350/250；多OA多流水的未分配初态；同OA多成本项；金额不等；允许零成本；退款；非成本；缺标签；同账户同日多流水；长项目与标签；409/只读。

不只看缩略图或静态截图，不反复无差别整页生成；正常设计迭代不逐轮要求用户批准。无法取得Make实际预览/资源时明确说明缺失，不冒充验证或以自行生成UI替代。

### 步骤三：移植与替换

读取实际Make展示源码/资源，提取必要结构与局部样式，接入当前组件和Cost接口。保留经过验证的宽度、比例、行高、字体、间距、色彩、图标和交互，不把原型的mock状态/假保存带入App。原型遗漏先在Make修正，App局部覆盖错误在App修正。

修改草稿逻辑、表格与两栏后，同步删除旧渲染/重复输入/CSS/无用helper及其旧断言。检查内部ID在标题、正文、下拉、退款和错误文案的所有可见出口。

### 步骤四：App对照、真实接口和性能验证

在同一浏览器、窗口、缩放、字体、演示数据、展开状态下对照Make/App。先修结构与遮挡，再修细节；不使用“95%还原”代替证据，不承诺跨操作系统字体栅格化绝对相同。

使用真实隔离后端执行保存→重读→三视角/月份/导出；浏览器mock只验证展示与交互，不替代持久化验证。完成测试和旧代码清理后记录结果。

### 步骤五：实施完成后的交付

更新模块状态机/测试矩阵/边界中真实变化的前端部分，以及Make交接与实施记录。应用实施后的提交、发布按届时有效授权及现有正式发布入口执行，不在本计划轮触发。发布验证使用实际浏览器和有限API请求；不为视觉或压测编造生产财务决定。保留旧服务端合同允许应用代码回滚，不做数据库回滚或删库。

## 7. 性能计划

- 列表摘要→展开时定向取任务；不为两栏逐OA/逐流水发请求，不提前加载全部任务明细。详情已在当前会话时切换不重复获取。
- 输入金额、选来源、新增/删除仅改本地草稿，不发HTTP。保存一次PUT，按既有成功回调刷新，不叠加重复列表/详情读取。
- 对普通任务和100条合法分配行任务实测输入、来源选择、增删、滚动、保存后刷新；100行样例使用足够的OA/来源组合，不能用重复非法行充数。
- 目标：普通及100行任务输入/增删到下一次可见更新p95不高于100ms；数据到达后的任务内容显示目标150ms内。记录浏览器、数据量、样本数，使用普通性能测量，不建CI性能gate或截图baseline。
- 首屏网络、纯渲染和保存后的后台响应分开测量。出现卡顿后针对分组/汇总重复扫描做局部优化，优先一次遍历和复用本次计算，不默认新增虚拟列表、缓存或重型库。
- 既有生产项目下钻p95约459ms、4并发根查询约1145ms的聚合瓶颈不因本次UI自动消失。本次不承诺解决全部后端容量问题，不顺带重构聚合架构；报告前端是否改善、请求是否增加和剩余接口耗时。

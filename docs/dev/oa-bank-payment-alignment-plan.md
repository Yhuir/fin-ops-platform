# OA 与银行流水逐笔对应及后到补全实施计划

日期：2026-09-20。状态：实现和本地验收完成；本次发布的生产证据另存验证报告。

本计划采用直接实施、现有模块和验证入口，不使用 GSD。实施与验收记录随发布更新；不增加审批流程、匹配平台或通用门禁。

## 1. 已确认问题与验收对象

生产只读查询已确认关系 `CASE-AUTO-0252` 包含两条 OA、两笔银行流水和一张发票。当前接口将整组列为 paired，三栏各合计 16000 元，但 `display_subgroups` 仍把两笔流水全部放在第一条 OA 下，并将该历史子组标为 resolved。

| 对象 | 已核对事实 | 期望对应 |
| --- | --- | --- |
| OA `oa-pay-2440` | 樊祖芳，2026-08-14，8000 元，合同 16000 元、预付 50%，已完成 | 2026-08-14 10:17:33、8000 元、备注“货款”的流水 |
| OA `oa-pay-435cb9a9-a831-11f1-b875-024207e7fd4a` | 杨丽萍，2026-08-24，8000 元，“紫外线设备配件，50%尾款”，进行中 | 2026-08-24 11:25:34、8000 元、备注“货款（50%尾款）”的流水 |
| 发票 `26132000002867042881` | 定州六联环保科技有限公司，16000 元 | 在这两条付款之间共享展示，真实成员及金额只计一次 |

代码与内存复现确认四个缺口：

1. 历史分区只要同时有 OA 和流水，就先被视为 resolved 并占用成员，没有证明逐笔对应。
2. 组内对齐主要处理唯一等额与唯一合计；重复的 8000 元不能利用日期、付款阶段进一步区分。
3. 普通组合证据扩展跳过三种类型已齐全的关系，不能补入本例缺少的第二条 OA。明确来源引用扩展是另一条既有规则，不能笼统说所有扩展均被禁止。
4. 整组金额闭合不能证明组内对应正确。把五条模拟事实全部设为自由成员能够建组，但保留旧组后不会补入第二条 OA；输入到达顺序影响结果。

最初将两笔流水放入旧组的历史操作来源尚未核实，不能据此断言是自动匹配还是人工操作。修复依据是已确认的当前缺陷，不依赖猜测历史来源。

## 2. 业务范围与必要修正

- 本次修复普通付款的 OA—流水对应、同组展示，以及后到 OA/流水补入。继续支持有效的一对一、一对多和多对一，不强制所有付款等额单笔。
- 金额相同不是身份。日期、文字和金额各自都不能独立证明业务归属；候选需要真实收款证据，已知冲突不能忽略。
- OA 审批状态、资金支付、正式关联、逐笔展示、成本资格分别表达。进行中 OA 可以建立正式关联并逐笔同行，但整组必须留在未配对；全部 OA 完成后才按其余条件进入已配对，不提前获得成本确认资格。
- 正式组成员与组内展示分区分开。新的展示推断不写入发票费用归属或成本分配，也不自动成为外部支付系统的逐笔付款证明。
- 历史同组不等于人工逐笔确认。仅保护已经由现有合同证明的明确引用或绑定；不假设数据库已经有“人工逐笔锁定”字段，不新增一套锁定状态来完成本任务。
- 原组已闭合且不存在待解释付款时，不因同收款方有新记录就继续扩展。不自动合并两个已经各有 active owner 的关系。
- 不要求每次操作全库重算。事实和关系变更影响匹配范围，搜索、排序、展开不触发正式关系写入。
- 完整性指支持范围的成功、歧义、失败、重试、撤回和验证闭环，不是承诺自动识别所有自然语言或绝对零 Bug。

## 3. 架构、I/O 与事实所有权

复用现有模块，无新增表、持久化逐笔映射、read model、缓存、worker、LLM、通用规则配置或第三方依赖的需要。

| 边界 | 输入 | 输出及责任 |
| --- | --- | --- |
| `PostgresWorkbenchFormalRelationFactRepository` | 变化月份、相关 typed IDs、现有关系 | 批量 canonical 事实与占用；SQL、原始字段映射由 repository 负责 |
| `workbench_relation_alignment_service.py` | 标准化 OA/银行事实、明确引用、历史证据 | 纯计算返回对应成员、证据种类、未确定成员及原因；统一 OA—银行规则 |
| `WorkbenchFreeMatchingEngine` | 标准化事实、active anchors、撤回记录 | 正式新建/扩展计划；不做 I/O，不写关系 |
| Orchestrator + Command/UoW | 计划、来源及关系版本、actor | 同事务重验并提交关系、history、审计和既有领域事件 |
| `workbench_display_subgroups.py` | 当前完整组、历史解析及统一对齐结果 | 现有 `display_subgroups` DTO；不改变正式成员和金额 |
| Workbench 前端 | 分区 DTO、真实成员、筛选与选择状态 | 同行/共享区域展示；不推断正式关系 |
| Cost | 自身 canonical facts、原有历史证据、已确认成本来源 | 复用修正后的关系展示；来源资格和成本计算仍由 Cost owner 决定 |

内部输入合同明确为：typed ID、整数分金额或 Decimal、币种、收支方向、真实收款主体、已知收款账号、业务日期、明确引用、付款阶段证据。字段映射先核对 canonical source；不从页面文本、同步时间或猜测字段构造证据。

共同纯计算放在现有对齐模块，原 `align_relation` 保留公开调用合同并负责适配。正式 matcher 调用同一纯计算，不把前端字典 DTO 当作正式匹配事实。禁止为了复用产生 engine/service 循环依赖。

金额、日期、阶段只是内部推断输入；现有 `display_subgroups[{oa_row_ids,bank_row_ids,resolved}]` 公共结构保持。诊断和证据优先复用已有内部返回/审计能力，不向无关页面扩散字段。

## 4. 对应规则

按明确顺序计算，不增加可配置权重或无法解释的评分：

1. 固定已有明确引用与合法来源绑定。历史同组记录不自动提升到这一层。
2. 以收款证据、方向、币种、金额缩小候选；已知账号冲突拒绝，账号缺失不是新增硬门槛。
3. 保留无竞争的唯一等额对应，以及现有有界、互不争用的唯一合计对应。
4. 对重复金额，使用明确付款阶段和业务日期消歧。阶段仅识别本笔明确表达的预付款/尾款等语义；同时叙述多个阶段、否定、阶段不明时不强行分类。
5. 同日是辅助证据，不是所有付款必须满足的条件。不同日期不能仅按“最近的一笔”选择。已有精确交易引用不因缺日期失效。
6. 按整个候选集合判断唯一性，不按遍历顺序占用流水。只有证据和金额条件仍成立时才处理剩余成员，不能靠排除顺序将最后一笔强配。
7. 返回确定部分与未确定部分。明确部分可以先形成合法对应；有歧义的成员不得被重复占用，也不得伪装 resolved。

规则需同时验证：本例两条正确对应、同额同日无法区分、多笔尾款、文本冲突、有效拆分/合并付款、输入顺序置换。特殊退款、往来款、ETC、报销明细继续由既有领域规则负责，不套用普通正向付款规则。

## 5. 顺序实施任务与完成标准

### A. 建立缺陷测试与测量基线

- 将第 1 节结构构造成脱敏 fixture，覆盖旧组存在后新增 OA、人工合并，以及全部自由成员三种起点。
- 增加重复金额歧义、有效历史分组、连续合并撤回和成本展示隔离测试。
- 记录代表页面 GET 耗时、查询数、纯对齐耗时和 matching 单批耗时。基线用于比较，不新增冻结文件或硬编码机器耗时门禁。

完成标准：准确复现错误，能区分正式成员正确与组内展示错误；测试不依赖生产文件。

### B. 实现单一付款对应规则

- 扩展现有对齐模块，明确内部类型和证据输出。
- 在 repository 与 page hydration 边界映射相同的 canonical 业务证据；阶段提取只保留一个实现。
- 原纯金额逻辑迁入统一判断，移除调用方自己的竞争处理，不保留新旧双跑。
- 保留显式发票来源归属的现有责任，不能把 OA—银行规则用于票据明细归属。

完成标准：各调用方相同事实得到一致结果；无 SQL/HTTP/外部模型调用；排序不改变对应。

### C. 修正历史展示分区

- `relation_history_partitions` 保持精确历史解析合同，继续服务 Cost 等调用方。
- `apply_display_subgroups` 不再把含 OA 和银行的历史分区直接视为 resolved，也不提前无条件占用全部成员。
- 有效历史分区经过当前事实判断后保留；历史分区与当前明确证据冲突时，交由统一规则重新对齐。
- 金额不闭合需要进一步判断，不能一概判定所有部分付款历史非法；有明确证据的部分付款仍保留其业务含义。
- 真实无法判断的成员进入共享区域；发票仍在组级共享，金额/成员只计算一次。

完成标准：本例第一条 OA 不再占用两笔流水；有效历史一对多/多对一和撤回展示没有退化。

### D. 补齐已有关系内同类型成员

- 用待解释付款与明确差额替代普通付款路径中“三种类型齐全就跳过”的判断。
- 查找与这些付款有证据联系的未占用 OA/银行候选，复用第 4 节规则。
- 本例只有“尾款流水与后到 OA 对应明确，补入后关系闭合”才能扩展，不通过最大栏金额凑平。
- 支持一次将同一 case 的确定变化合成一个计划，保留原 case ID、明确来源与合法 metadata。
- 不抢其他 active owner、不自动跨 case 合并、不重新建立被明确撤回的成员集合；已有来源不可变规则继续有效。
- 通过现有 UoW 重验事实、竞争所依赖的来源版本和唯一占用。并发后证据不成立则明确冲突，不能仅因计划生成时唯一就提交。

完成标准：OA 先到、银行先到、旧组先存在三种支持场景均能闭环；重复任务零重复关系/事件，陈旧计划零写。

### E. 触发、跨月与任务完成

- 扫描 OA sync、银行/发票导入及纠正、关系确认/撤回、成员移除的现有 matching producer。
- 对实际缺少的触发补齐现有 dirty-scope writer；变化月份来自受影响真实成员，不能只取发票月份而遗漏无发票的 OA—银行关系。
- 业务提交与必要任务登记保持现有事务边界。自动 actor 不反向投递自身；处理期间新变化保留为下一轮任务。
- 当前 scope 可以通过已有关系身份批量读取跨月完整成员，不扩大成每次全库配对。
- 人工撤回的目标拓扑和撤回记录继续生效，worker 不立即把刚撤回的完整关系重新建立。
- 逐项核对“导入完成”“匹配完成”“页面读到新结果”三个时点，复用现有任务状态和完成反馈。若现有 UI 完成信号只覆盖导入，先确认其实际合同，再在该入口补闭环，不能假设一次过早 GET 已完成匹配。
- GET 保持只读；不引入页面 read-model 刷新、全页轮询或新的推送基础设施。

完成标准：导入/sync commit → matching → 正式关系提交 → 正常 canonical GET 的全链路可验证；异步失败可见，不显示虚假完成。

### F. 前端、跨页和文档

- 普通多 OA 关系使用后端完整分区；去除该适用范围内重复推断或按顺序兜底的旧前端路径。
- 保留报销明细与明确票据来源等有效专用分段。分区失败显示未确定，不转回旧猜测算法。
- 验证搜索、排序、分页、展开、折叠、选择、确认和撤回；银行折叠不能跨新的付款对应区域合并。
- Cost 详情关系展示复用新结果，但 `source_relation_groups`、已保存分配、成本资格和来源月份沿用自身合同。展示 resolved 不升级成自动成本来源。
- 检查 OA 待付款及既有支付状态事件：正式关系增加 OA 可能按原业务规则改变其支付状态；展示变化本身不应新增外部事件，审批状态不改。
- 更新 Workbench、Relations 的 boundary-io/tests/state-machine；Cost 只更新实际变化的共享展示合同；改变 producer 时同步 runtime worker 合同。同步受影响的产品/API 文档，不重写无关历史。

完成标准：本例视觉正确、跨页合法数据保持、受影响长期文档与实现一致。

### G. 存量收敛与发布验收

- 本例已是完整正式组，优先通过只读展示重算修正，不为排列重写关系。
- 尚未补齐的同类关系先通过相同 matcher 生成可核对计划，再将确定的受影响范围交给现有任务/UoW 收敛。不硬编码生产 case ID，不另写修复 SQL 算法。
- 存量收敛按范围记录创建/扩展/未确定/失败数，重复执行验证幂等；未确定不算修复成功。
- 进入获授权的实施发布阶段后，使用 `./scripts/deploy-oa.sh`；保留已有事务、安全和发布要求，不新增重复发布门禁。
- 生产验证实际样本、读取性能、四个既有 worker 与队列状态。写链验证使用测试自有数据并清理，不撤回真实用户关系制造测试案例。
- 代码回退与已写关系恢复分别记录；不能宣称 git revert 自动恢复数据。恢复关系仍须走已有正式命令和当前版本检查。

完成标准：部署版本可核对，真实案例同行，后到补全链路有验证证据，性能达标，测试数据与本次临时备份完成清理。

- 候选先按收款身份、方向、币种、金额组织，避免全库两两比较；日期窗口沿用已确认业务合同。
- 原始文本每条事实解析一次，历史索引按批构建，标准化付款事实请求/批次内复用。
- canonical rows 和历史集合读取，页大小和成员数增加不能产生逐行 SQL/外部 I/O。
- 不增加现有组合搜索资源预算。达到限制返回明确未确定，不截断事实后声称成功。
- 页面只处理当前页组；存量收敛与 worker 按相关范围执行，不将自动匹配搬入 GET。
- 使用同一环境、数据与查询条件比较变更前后 p50/p95/p99、最大值、SQL 查询数、CPU 纯计算及队列延迟。公开样本数与并发；少量样本不能证明稳定 p99。
- 复用仓库现有生产目标：核心 GET p95 ≤ 1000ms、p99 ≤ 2000ms。采样使用既有有界 probe，包含未筛选页、本例搜索、关系详情和成本详情，核对 2xx 与业务结果，不能只测健康检查。
- 另测导入 commit→matching 完成→GET 可见的端到端延迟。现有 GET SLO 不能冒充后台处理延迟；先记录实测基线和结果，不许未测就承诺“立即”。
- 只有实测证明 SQL 瓶颈时才提出具体索引；不预先加缓存、表或任务。

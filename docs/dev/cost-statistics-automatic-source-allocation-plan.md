# 确定来源自动分配实施计划

日期：2026-09-14。状态：已按用户后续授权实施；本地验证与执行记录见[成本模块实施说明](../modules/cost-statistics/implementation-notes.md#2026-09-14确定来源自动分配)。下文保留实施顺序与设计复审，不使用 GSD。

## 1. 目标与决定

已有正式事实能够确定项目、成本单元、来源流水及金额时，直接生成成本并移出待分配；存在业务选择或资料缺口时才保留待办。用户无需打开抽屉或点击保存才能看到自动成本。

沿用当前 canonical direct-read 架构：自动分配是成本 Policy 对当前事实的计算结果，不新增自动分配数据库记录、自动保存 API、worker、缓存、read model、依赖或迁移。人工修改继续使用原 PUT、版本校验、事务和审计。

## 2. 必须澄清的边界

1. 金额相等、金额组合唯一、界面同行不证明付款归属。现有预填算法限制了候选形态，不能直接作为自动确认算法使用。
2. “不用严格门禁”不等于删除金额守恒、来源归属、审批资格或既有并发保护。这些是业务正确性规则，不增加用户确认步骤。
3. 不承诺其他页面绝对零 Bug；通过只读依赖、局部文件修改、输入不变测试和真实回归证明影响范围。
4. 不承诺尚未测量的绝对耗时；本次优化确定性计算，不顺带重构整个成本查询引擎。
5. 删除被替代或错误的旧路径，保留仍有业务价值的人工预填。不能因为名字带“旧”就删除正常能力。
6. 本方案自动结果随有效事实重算；如未来要求锁定历史会计期间或保存每次自动判定快照，属于另一项需求，本次不加入。

## 3. 自动与人工的判定

先读取完整 active 关系，再依据正式子关系和明确 canonical OA 引用限制来源归属，最后应用成本范围与日期筛选。不能因为范围缩小而新造唯一关系。

| 情况 | 行为 |
| --- | --- |
| 一成本单元、一来源，金额和资格明确 | 沿用并扩展现有自动计算 |
| 一来源对应多个固定目标成本单元，金额闭合 | 自动按各项目标金额分配 |
| 多来源对应一个正成本单元，无未决退款/非成本 | 自动保留各来源金额、月份、账户及标签 |
| 大关系由正式证据分成上述独立子组 | 子组分别计算，不因外层多对多强制人工 |
| 子组仍含多个来源和多个成本单元，只有金额组合线索 | 保留现有详情建议与人工编辑 |
| 同一 OA 下多个费用明细 | 父 OA 引用只限定候选；不能补造逐费用项付款证据 |
| 退款来源或差额用途不明确 | 保留人工；已有单来源退款处理规则不回退 |
| 只有部分独立子组确定 | 确定部分计入成本，余下部分待处理，不标整组完成 |
| OA 未完成、资料缺失 | 沿用现有审批和资料规则，明确待处理原因 |
| 已有有效人工决定 | 优先使用原决定，不自动覆盖或补足其未处理金额 |
| 已有人工决定失效 | 保留现有 stale/重核流程，不自动把旧决定洗成新结果 |

“无正式历史”不是额外拒绝条件：当前完整关系或明确引用已经足够时直接计算。来源引用与历史冲突时，停止受影响部分的自动判断；不能忽略冲突后按金额匹配。结构损坏、重复 owner 等沿用现有明确错误。

本次不新增任意多对多拆分求解器；不能由现有事实和上述简单规则证明的结果，继续人工。无随机、比例、日期接近、名称相似或排序猜测。

## 4. 模块边界与 I/O

| 所属与文件 | 输入 | 输出与责任 |
| --- | --- | --- |
| `cost_statistics_canonical_repository.py` | 当前读取范围、同一数据库事务 | 批量 canonical OA/银行/关系/人工分配及相关正式历史；成本内部 snapshot |
| 已有关系 repository 与 `relation_history_partitions` | typed members、相关 history | 复用原正式历史解析结果；不修改 Workbench 公共匹配或展示语义 |
| `cost_statistics_source_allocation.py` | 成本单元、来源、固定目标、正式归属边界 | 确定的来源行及未解决部分；纯函数、无 I/O |
| `cost_statistics_policy.py` | 完整 snapshot 与来源计算结果 | 唯一成本事件集合、任务及状态；决定资格与人工优先级 |
| `cost_statistics_allocation_scope.py` | 完整决定、标签范围 | 范围内来源与金额投影；保留范围外历史，不重新推理归属 |
| query/manual allocation service | repository、Policy、HTTP 已解析参数 | 原查询/任务 DTO、手动保存及审计；路由仍只负责 HTTP 与权限 |
| 成本专用前端组件/features | 服务端 DTO、用户操作 | 自动结果展示、剩余编辑、保存和重读；不计算自动配对、不自动发 PUT |

依赖方向：关系事实只读 → Cost repository → Cost 纯规则/Policy → Cost API → Cost UI。不得把成本规则放到关系 owner、银行 owner、公共表格或通用 API client。

详情专用的展示对齐继续留在详情；统计热路径只消费正式来源证据，不能执行展示金额对齐或详情预填组合搜索。内部 snapshot 中 `source_relation_groups` 由所有成本读取入口一致提供，空证据显式表达，读取失败直接报错。

保持既有 HTTP 路径、PUT 请求形状、分配持久化形状和权限。现有 `status`、`pending_reasons`、`source_allocations`、`version` 足以表达本次生命周期；不新增状态表或通用规则引擎。自动结果没有人工操作者/保存时间，不伪造这些字段。

## 5. 实施顺序与逐步验收

### 步骤 1：固定输入样例与受影响调用点

- 读取执行时工作区差异与当前模块事实，保留其他工作。
- 通过 CodeGraph 定位来源函数调用者，再扫描相关符号和字符串的全仓引用，登记生产、测试、本地 tooling 入口。
- 核对截图目标关系的完整正式成员、145/204 来源、历史分组及引用。可读取真实记录时只读核对；定位不唯一或不可访问时明确记录，不能把合成样例冒充该记录。
- 编写最小合成反例：145/204 有正式子关系时自动；仅金额对应时仍为建议；重复金额有独立证据时自动；父 OA 多费用项仍有歧义时不猜。
- 不在生产写入测试分配。

验收：明确哪些记录会改变，所有新增自动结果都有实际证据类型；截图记录是否满足条件单独报告。

### 步骤 2：统一批量来源证据读取

- 在 Cost repository 复用 `load_display_history` 与 `relation_history_partitions`，按本次所需 OA/case 批量读取和解析。
- 从 `_attach_relation_display` 中分离供成本判断使用的正式来源分组，详情展示复用同一输入；不复制历史解释算法。
- `load_snapshot`、`load_manual_allocation_task_snapshot`、`load_relation_snapshot` 和事务内保存重读使用同一证据口径。
- 一次请求内组织 OA/case 索引，避免每个关系重扫整份 history；只为需要历史区分的关系读取相关历史。
- `time|bank_tag` 原始流水视角保持提前返回；不增加关系历史读取。保留单个一致性快照。

验收：关系数量增加不会产生逐关系数据库往返；列表、详情、统计和导出证据一致；公共输入不被修改。

### 步骤 3：扩展现有确定性来源计算

- 在现有来源规则文件内扩展 `automatic_source_allocations`，按正式独立子组复用单来源/单正成本单元规则。
- 正式子组与明确 OA 引用取交集；无明确引用不能被解释为任意新配对事实。
- 使用 Decimal/整数分及现有逐来源、逐单元校验；不枚举金额子集，不新增阈值、hash 或启发式算法。
- OA 审批资格按单元判断，未完成单元不生成成本；若与已完成部分共享歧义来源，不把共享金额擅自拆开。
- 保留完整原金额、已确定来源金额和剩余金额的区别。对部分自动结果只确认独立且闭合的子组，未知部分没有正式成本行。
- 现有来源验证若需复用到子组，由调用者提供准确子组输入；不通过吞异常、关闭整组校验或伪造非成本使结果通过。

验收：正反例全部通过，执行时间随已读取成员和证据规模增长，不引入组合爆炸。

### 步骤 4：任务、范围、统计和人工保存闭环

- Policy 统一消费确定结果，三个项目成本视图、详情、预览与导出共用同一成本事件集合。
- 全部确定且资料完整的任务为 allocated，进入现有已完成列表并可重新打开，自动分配无需保存。
- 补齐原来自动完成提前返回时缺少的详情/人工编辑所需现有身份字段；首次人工修改仍用 version 0 与原 CAS 创建记录，不伪造人工历史。
- 部分确定的任务保留 pending：确定来源行进入统计，未解决来源和原因可见。编辑器初始化保留确定行，用户只需补齐剩余；保存发送现有完整范围分配数据并通过原事务校验。
- 普通金额固定任务仍要求最终完整闭合，不为本次新增“任意部分保存”模式；混合审批及已有部分保存继续按原规则处理。
- 不让范围投影把“部分已确定金额”误当作“人为修改 OA 目标”，保留固定目标校验；复用已有 `covered_source_task`/来源范围 helper 的适用部分。
- 保存后整份有效人工决定接管该任务，不与自动结果重复叠加；刷新、撤回、修改金额/标签/范围后下一次读取重算有效结果。
- 人工决定 stale、历史 NULL 来源、范围外人工项、退款、非成本和并发冲突保持既有处理，不借此次改造恢复旧数据猜测路径。

验收：自动 → 已完成/三视图 → 详情 → 人工修改保存 → 重读 → 事实变更/撤回全链一致；部分自动 → 人工补齐 → 保存无丢行、重复金额或目标松动。

### 步骤 5：保持页面交互，删除替代路径

- 复用原抽屉和已完成入口，显示自动结果；沿用 `version=0` 与已有来源结果区分尚无人工记录的分配，不显示虚假的“保存成功”。
- 只读用户能查看自动成本；人工修改仍遵守 `can_save`。
- 详情建议只处理尚未确认的部分，不能重新使用已确定的来源或覆盖自动行/会话草稿；保留现有金额组合建议的独立业务用途。
- 保留请求取消、旧响应丢弃、脏草稿保护、409 重核与未知保存结果核实。关系证据变化通过原刷新边界显示，不自动发送写请求。

必须删除/替换的具体旧路径：

| 旧路径 | 处理 |
| --- | --- |
| 仅在详情 `_attach_relation_display` 附加来源证据 | 统一到 Cost snapshot 的正式证据组装；详情只保留显示投影 |
| 外层多来源、多成本项无条件进入人工的判断 | 用正式独立子组判断替换；真正歧义仍人工 |
| `_cost_entries` 排除无人工记录且已自动完成任务的条件 | 调整为现有已完成入口可查询、详情可打开的一致任务集合 |
| 自动完成提前返回造成身份字段不完整 | 收敛任务构建出口，沿用已有字段，不复制构建器 |
| 对已确定来源再次产生建议或合并重复行 | 删除该调用路径；建议只服务未解决部分 |
| 测试与当前文档中“多来源一律人工”“有正式子组也只能建议”的断言 | 按新业务边界更新，保留金额歧义/错误证据的反例 |

删除后执行全仓符号/文本扫描，检查 import、API client、测试、文档和本地工具引用。仍被业务使用的预填、人工保存及保护措施不得删除。不加入新旧双算法开关、旧结果兜底或异常后取缓存。

性能实测：

- 热路径不调用 `suggest_source_allocations` 的组合枚举，不逐关系请求详情；原始流水视角不增加历史查询。

- 当前规模核心读取沿用既有 p95≤1000ms、p99≤2000ms 合同；本次争取详情/下钻 p95≤300ms，但未实测前不承诺达标。输入、来源选择和增删行复用 2/100 行交互 p95≤100ms 目标，至少 20 样本，区分网络与渲染。
- 不把固定 SQL 次数当成高性能证明：必须检查批量 history 返回量和解析复杂度。先优化本次新增热点；若瓶颈属于原全量聚合，记录实际限制，不擅自扩大成架构重构。
- 不新增性能 baseline 文件、CI gate、hash、缓存、索引或 worker。保留现有正式发布合同。

同步更新成本 README、boundary-io、state-machine、tests 和 implementation-notes，以及 `docs/product-specs/cost-tax.md` 中受影响的自动分配口径。API 语义变化更新对应 API 文档。无新 owner/表/模块，不机械改写全局架构或无关模块文档。

## 6. 数据安全、回滚与交付

本方案不涉及生产数据迁移或历史分配回填，因此不创建数据库备份。实现回滚使用 Git/原发布版本；回滚后新增自动成本可能恢复待分配，这是明确的业务可见效果。期间合法人工保存仍使用原 schema，保留不删除。

若执行中发现必须改 schema/回填，先说明设计变化及必要性，不擅自扩展。本任务若实际创建临时备份，交付前仅按明确路径清理该任务备份和独占测试资源；不匹配删除既有备份，不删除主数据库。

交付包括：修改文件与删除清单、七类测试覆盖和执行结果、截图真实关系核对结果、同口径成本变化与原因、真实性能数据、剩余限制。实施验收与生产发布分开；本计划本身不执行部署。

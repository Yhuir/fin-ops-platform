# ETC 票根无扩展名文本上传修复计划

日期：2026-09-08

状态：2026-09-08 用户已授权执行、commit/push main、部署及生产验证；修复已进入实施验证。下文第 1–9 节保留获准的实施范围与验收依据，涉及“本轮只计划/未实施”的句子属于当时审批上下文，不表示当前执行状态。实际结果持续记录于第 10 节。不使用 GSD。

## 1. 结论与范围

应修复。票根网来源文件不应因缺少 `.txt` 扩展名而被拒绝，但“可读文本”不等于“可用于核对的完整通行明细”。

已确认的实施范围：

1. ETC 票根入口显式接受无扩展名纯文本，其他上传入口默认行为不变。
2. 票根文本按明确记录边界解析，损坏记录不得静默丢弃或与相邻记录拼接。
3. 前端可选择/拖拽该文件，正确显示已上传、解析异常、来源冲突及失败后的实际文件状态。

第二项是上一轮复审补充、用户本轮已同意的真实缺口，不能把只修扩展名称为文本导入完整闭环。它只影响现有票根文本解析器及其 TXT/手工粘贴调用，不修改 PDF/OCR、信用卡解析或对账匹配算法。无需重复确认这一范围；本轮请求仍是完善计划，不能据此开始代码实现或部署。

不做：通用文件转换、任意扩展名放行、UTF-16 等新编码支持、OCR 新链路、历史批次重算、数据库迁移、新表/索引、缓存、worker、新依赖、新 hash、冻结 contract、baseline 文件或新增发布 gate。

## 2. 已核实的根因

### 2.1 无扩展名在读取内容前被拒绝

`untrusted_document_policy.inspect_untrusted_document` 先用 `Path(file_name).suffix` 查询类型。无扩展名直接抛出 `document_format_not_allowed`，尚未执行文本检测。

`EtcReconciliationSourceUploadService._validated_documents` 在来源模式判断和对象存储之前调用此检查。现有文本解码器及 `TicketRootClipboardTextParser` 已具备解析能力。

已用同一份内存合成文本验证：`云A516HJ` 被拒绝，`云A516HJ.txt` 通过；内容可正常解码并符合现有票根特征。

### 2.2 前端选择提示不完整

`EtcTicketManagementPage.tsx` 的票根 input 当前为 `.txt,text/plain`，可能使系统文件选择器隐藏无扩展名文件。拖拽未依赖该 accept。点击选择与拖拽应由同一后端规则判定，不能只修 API。

### 2.3 文本分块依赖前一条已含金额，导致丢行/串行

`_ticket_record_blocks` 用已有合法时间、金额判断新记录；`_ticket_item_from_block` 缺字段返回 None，文本 parser 只追加非空 item。只要存在有效 item，最终可能不返回任何 issue。

本轮纯内存执行结果（未触及数据库）：

| 输入 | 当前输出 | 问题 |
| --- | --- | --- |
| 单条有效记录 | 1 item / 0 issue | 正常 |
| 有效记录后接金额损坏记录 | 1 item / 0 issue | 损坏记录静默消失 |
| 金额损坏记录后接有效记录 | 1 item / 0 issue，前条时间配后条金额 | 产生错误通行记录 |

新记录边界不能依赖前一条金额能否解析，也不能跨记录查找金额补齐。

### 2.4 两项既有失败的正确期望不同

- `test_ticket_root_upload_route_imports_txt_without_extension_with_clipboard_parser`：有效无扩展名文本返回 200，来源和明细正确。
- `test_ticket_root_upload_route_rejects_existing_pdf_ticket_root_source_before_txt_upload`：已有 PDF 来源时返回 409 / `ticket_root_source_mode_conflict`，不能报格式错误，更不能改成上传成功。

## 3. 业务行为与模块 I/O

### 3.1 接受范围

- 票根文本支持现有 `.txt`、`.text` 和无扩展名文件；扩展名大小写按现有规则处理。只补“缺少后缀”，不自动接受 `.bin`、`.exe`、伪装双扩展名等未知后缀。
- 保留原始文件名和 bytes。MIME 为空或 `application/octet-stream` 不单独作为拒绝或接受依据。
- 无扩展名但内容为 PDF/图片/ZIP 的文件不进入文本路径。现有有扩展名的合法 PDF/图片 API 能力保留，不扩大当前 TXT 上传框的业务类型范围。
- 复用 UTF-8（含 BOM）、GB18030/GBK；空白、NUL/异常二进制、解码失败、资源超限明确报错，不以 `errors=ignore/replace` 丢字符。
- 内容必须属于现有支持的票根“按行程查看”格式。普通文字、错误页、缺车牌或缺必要字段不能冒充解析成功；文件名不能代替内容中的车牌。
- 不承诺识别任意格式，也不能证明用户已经复制网站全部行程。能验证的是上传文本中已支持格式的记录未被静默丢失/串行；缺外部总数时不声称已核对外部完整性。

### 3.2 接口和持久化保持原形状

入口仍是 `POST /api/etc/reconciliation-tasks/{taskId}/ticket-root-files`，multipart 保留 `files`、`expectedVersion`；actor 由认证 session 注入。

| 结果 | HTTP 与现有输出 | 写入语义 |
| --- | --- | --- |
| 合法文件、模式与文本 | 200，task/sourceFiles/ticketRootItems/parseIssues | 保存原件和来源，返回最新 version |
| 可保存文本但非票根或有损坏记录 | 200，来源 `hasBlockingIssue`、具体 `parseIssues` | 保留原件；该问题文件不贡献可用于核对的 items，不伪造上传失败 |
| 空文件、类型伪装、解码/资源错误 | 400，`invalid_document_upload` + 明确 message | 当前格式预检阶段不写来源/解析结果 |
| 资料投错入口 | 400，`wrong_reconciliation_source_kind` | 保留现有不落来源的行为 |
| 已有其他来源模式、混合模式上传 | 409，现有来源冲突 error/message | 不删除或替换已有来源 |
| 版本/状态冲突、解析期间来源被删除 | 既有 409 error/message | 不提交过期结果、不恢复已删除来源 |
| 对象存储失败 | 503，现有存储错误 | 失败文件不能有成功元数据；前面已成功的文件按真实状态保留并显示 |

权限、审计、版本、对象存储和 source file 生命周期不变；不写 OA、不改银行或现金事实池。

### 3.3 边界

| 模块 | 输入 → 输出 | 禁止承担的职责 |
| --- | --- | --- |
| ETC 页面 | 用户文件、当前 task/version → multipart、响应展示 | 猜业务字段、自动重传、跨批次覆盖 |
| ETC route | 认证请求 → HTTP 映射 | 业务解析、DB/对象存储直写 |
| 共享文档检查 | 名称/bytes/允许类型/limits/显式许可 → 既有 ValidatedDocument 或文档错误 | 理解票根业务、访问 DB/OA、全局放开类型 |
| 来源上传 service | task/version/actor/uploads → 来源检查、存储/解析编排、最新 task | 新建事实池、绕过版本和来源冲突 |
| 文本 parser | file_id + 文本 → 既有 FileParseResult | 跨记录补字段、I/O、猜格式/OCR |
| task service/repository/file store | 既有命令 → 文件、task/version/audit | 因本次需求增加持久化模型 |

## 4. 可执行实施顺序

### A. 固定复现，先执行目标测试

1. 在现有测试文件保留两项失败的真实期望，新增无扩展名与 `.txt` 等价断言。
2. 增加“好+坏”“坏+好”文本，断言不会静默漏行、不会生成前条时间配后条金额。
3. 增加共享检查默认拒绝、ETC 显式允许、其他入口仍拒绝的测试。
4. 使用自包含合成样例，不依赖桌面业务文件。不新搭测试框架，不以长篇预检代替真实运行。

### B. 最小修复文件识别

文件：`backend/src/fin_ops_platform/services/untrusted_document_policy.py`、`etc_reconciliation_source_upload_service.py`。

1. 给既有检查函数增加一个关键词参数，如 `allow_extensionless_text=False`。它是内部单一许可，不是配置中心/注册框架，不能由客户端控制。
2. 只有后缀为空、许可开启且 allowed kinds 包含 text，才将文件作为待验证文本进入既有内容检查；实际类型仍必须是 text。不得 catch 失败后改按 TXT，也不得伪造 `.txt` 名称绕过校验。
3. 仅 `SourceFileKind.TICKET_ROOT` 调用开启；信用卡 PDF、OA 附件、关联台补充凭证保持默认。
4. ETC service 复用已有严格解码 helper，文本解析阶段复用解码结果与编码；错误槽位识别也使用相同结果，避免 GB18030 被 UTF-8 忽略错误后破坏。
5. 替换已明确文本路径中的 `decode... or ""`、默认猜 `utf-8`；缺结果明确报错。被替换的 wrapper 只有全仓无剩余调用方才能删除。
6. 现有原件完整性 hash 保留，不增加新的内容 hash/扫描；ValidatedDocument、公开 DTO、数据库字段不扩展。
7. 按已知 document error 改进现有 message 映射，区分空文件、格式/编码、资源上限，HTTP/error 字段不变。不为此向 server.py 搬入业务解析。

### C. 修复文本记录边界，不重写通用解析器

文件：`backend/src/fin_ops_platform/services/etc_document_parsers.py` 的 `TicketRootClipboardTextParser` 及文本专用切分逻辑。

1. 对当前支持格式，以明确“交易时间”记录起点及已有格式边界分段；遇新起点即结束前条，不要求前条金额合法。
2. 时间、金额、票数、站点只从同一段读取；明确标签重复、必要字段缺失/不合法形成 issue，不用相邻记录、全文件合计或文件名补齐。
3. 保留合法样例现有站点可选、票数等业务规则，不借机新增字段必填要求。业务口径冲突单独报告，不猜。
4. 明确的记录段解析失败，返回现有 ParseIssue，以文件和记录序号/已有 sourceLine 定位；导航、页头、空行不是坏记录。
5. 该文件只要有这种损坏记录，就返回 issues、不返回可进入核对的 items；保留原件供删除重传，不影响其他合法文件。无需给整个对账流程增加新门禁。
6. 完整合法文件的字段值、金额精度、来源关系和返回顺序保持不变。未支持格式明确报错，不增加泛化猜测。
7. 替换 TXT 的旧分块调用，禁止新失败再走旧 parser。PDF/OCR 仍使用的共享 helper 保留其调用和测试；TXT 不再调用它，不构成旧逻辑污染。
8. 既有手工粘贴和 TXT 继续共用同一文本 parser；来源互斥限制不变，不新加手工粘贴 UI。

### D. 前端闭环与多文件失败可见性

文件：`web/src/pages/EtcTicketManagementPage.tsx`；client/route 仅在测试证明必要时修改，endpoint/DTO 不变。

1. 仅票根 input 去掉会屏蔽无扩展名文件的 accept 限制；信用卡 input 保留 PDF 限制。选择/拖拽处理器只做最小文件名范围提示：现有文本后缀或无后缀可提交，明确 `.pdf/.jpg/.zip` 等在此 TXT 框提示入口不支持、不发 POST，防止移除 accept 后顺便扩大 UI 支持范围。文件名提示不是安全证明，无后缀内容仍由后端验证。
2. 文案：“支持 TXT 或无扩展名的票根网行程文本，可多选或拖拽”。沿用紧凑上传区，不加卡片、按钮或全局 CSS。
3. 点击/拖拽保留原名与 bytes，MIME 为空也能送达；不在前端再读全文或复刻解析规则。
   多选包含明确不支持后缀时，在提交前列出具体文件名，本次不发 POST、不静默过滤后只传剩余文件；用户重新选择即可。此规则只解决已知入口类型，文本是否真实有效仍由后端决定。
4. 复用来源与解析异常列表；有问题显示文件已上传但内容需处理，不能只因 HTTP 200 宣称全部解析成功。
5. 覆盖重复选择、失败重试、删除坏文件再上传、版本冲突、切换批次晚返回。错误不清空旧成功来源。
6. 不把现有逐文件存储改造成跨对象存储事务。第 2 个失败时第 1 个可能已保存：存储异常等可能已有写入的失败后，经现有 task detail GET 精确重读一次，显示实际来源和最新 version，保留原错误；不自动重复 POST。格式/权限等已明确在写入前拒绝的请求不额外重读，版本冲突沿用既有刷新处理。旧 task 的响应不能覆盖新选择。
7. 重读也失败时明确提示当前上传状态尚无法确认，保留原视图及错误，不猜全部失败/成功。这是已知失败处理，不是隐藏 fallback。
8. 请求超时或连接断开也属于写入结果可能未知，按同一上传专用重读处理；不能把“未收到成功响应”当成“服务器没保存”。只按服务端 file_id/来源状态展示，不用相同文件名认定重复；既有通行记录去重规则保持不变。

## 6. 性能：实际测量，不增加常驻设施

- 识别/切分应为有界 O(字节数 + 记录数)，不反复拼接已扫描全文，不通过跨整文件的回溯查找补字段。
- 固定数量的既有编码尝试，service 内复用结果；无新内容 hash、每行 DB/对象请求。纯 TXT 零 PDF 渲染/零 OCR。
- 用 10/100/1000 条合成记录及金额损坏对照运行，记录字节数、行数、检查/parser/service/API 分段耗时和峰值内存；正常与错误都测。
- 同内容分别命名 `.txt` 和无扩展名，对比同一处理链耗时。若差异超出重复测量噪声先定位，不用等待/缓存掩盖。
- 受控测试环境 1/4 并发、每档至少 20 请求，记录 p50/p95/p99、错误数与重复来源；小样本只作诊断，不声称容量认证。
- 并发性能样例使用相同规模但独立的测试任务/当前版本，避免多个写请求竞争同一 expectedVersion。另以同一任务单独测版本冲突正确性，不能把 409 快速拒绝当作成功吞吐量。纯 parser 测量与含对象存储/DB 的 API 测量分开，原文件字节和预期记录数明确可复现。
- 继承项目已定义且适用于该接口的性能目标；未定义时报告实测，不临时发明一组硬 gate。现有 64 MiB 文档上限是拒绝边界，不代表这么大的文本也应瞬间解析。
- 不提前承诺任意网络/文件均小于某毫秒。若实际瓶颈在对象存储/既有任务重算，单独给出证据，不借小修复扩大架构重构。

# 现金账分类与录入简化实施计划

日期：2026-09-20。状态：**计划已编写并自审，尚未实施、测试或发布。**

最终复审：保留既定范围，补明确经办人不等于借款对象、候选精确读取的请求隔离、备份清理和验证边界；不新增实施阶段或审批节点。

本计划以本轮用户确认优先：保留“内容说明（必填）”“备注（选填）”；费用类型按收入、支出、往来分组；删除重复办理入口；借款、还款、补录能力保持闭环。不使用 GSD，不增加审批流程、规则引擎或新门禁。

模块事实入口：[现金边界](../modules/cash/boundary-io.md)、[现金业务设计](../product-specs/cash-module-design.md)、[UI 设计](../product-specs/cash-module-ui-spec.md)、[技术合同](cash-module-technical-design.md)、[测试入口](../modules/cash/tests.md)。本文是待实施增量；与旧文档中的“必须选择本次办理用途”等界面描述冲突时，以本轮确认及本文为准，不把待实施方案写成现状。

## 1. 范围与完成定义

本次交付仅包含：

1. 基础设置的费用类型按三个固定大类管理，每类可新增、编辑、启停、搜索和分页。
2. 现金模块现有费用类型录入下拉单列分组；账户、账单、项目等下拉保持原有行为。
3. 新增、编辑、详情、流水列中的现金 `content` 统一称“内容说明”；`remark` 仍为“备注（选填）”，不合并数据。
4. 移除“本次办理用途”下拉及其重复状态，普通收付直接保存；需要借款、费用或结算时，只使用一套显式操作。
5. “补记借款现金来源”从通用录入移到符合条件的借款详情；复用原现金命令和来源绑定，不重建债务。
6. 完成任务录入、个人代付、历史结算、编辑/删除、权限撤销和其它页面的相关回归。

以下问题不纳入：双账户逐笔余额重排、有票支付重做、个人矩阵月份口径、账户 cash/savings 枚举、OA 项目资格放宽、Excel 导入、共享备注/报销组、其它页面重构。往来大类不意味着按分类自动生成借款。

完成标准：新界面路径真实写入后，现金、往来/个人/费用账与任务关联正确；错误和取消不产生半笔账；被替代代码实际删除；相关测试、浏览器检查和耗时测量完成并记录。计划自审不代表实现验收通过。

## 2. 确定的交互设计

### 2.1 三大类管理与分页

- 固定顺序：收入 `receipt`、支出 `payment`、往来（收付均可）`turnover`。不新增父分类表、多级目录、拖动排序或自定义第四类。
- 一个页面展示三个纵向分区，每区有标题、该组查询结果总数、“新增费用类型”按钮和同结构列表；每区默认每页 50 条，分别分页，内容随页面自然滚动，不增加三个嵌套滚动框。
- 共享一个关键词查询/重置/刷新入口和状态筛选。关键词提交后同时应用三组、各自回第一页；翻页仅请求该组。删除旧“适用范围”筛选、列表范围列及通用新增按钮，因为分区已明确范围。
- 使用现有 GET `/settings/categories?group=...` 分组读取，三个有界请求同时发出、各自显示成功/加载/失败，不等待最慢组再展示全部。不串行获取，也不全量下载所有页。
- 每组新增自动携带该组 `group`，新增抽屉显示只读归属；编辑归属沿用旧业务限制，不因分组界面放开已引用分类的换组。保存仍走原 POST/PUT、原版本校验。
- 页面内恢复已应用关键词/状态/排序和三个页码；离开现金模块或撤权后按原规则销毁。每组空态、失败态分别表达，不能把读取失败显示为“暂无类型”。
- 权衡：首次由一个分类列表请求变为三个固定请求，用现成分页合同换取清晰完整的组内管理。不为减少两个轻量请求新增聚合 API；实测再评价耗时。

### 2.2 单列分组下拉与原值

- 一次展开，一个纵向列表，大类标题不可选，具体类型可选。复用当前 HeroUI ListBox.Section，不手写定位/键盘/焦点系统，不增加左右两级菜单。
- 收入录入显示收入和往来；支出录入显示支出和往来；内部转账继续无分类。事项费用、票据、无票调整等调用方保留自己的既有允许分组，不扩大可用范围。
- 保留有界搜索和每页 100 条的候选分页，分组只整理该页结果，并明确页码/总数；绝不把首 100 条当成全部候选。搜索应用短防抖并取消旧请求，快速切换方向/关键词不能串入旧响应。
- 数据行保留真实 `group`；显示已选项时，不能因为它不在当前候选页就丢掉名称或归属。编辑引用优先使用已有 DTO 的 `id/name/group`；本次选中的候选保留于组件生命周期内。
- 月任务默认分类目前可能只有 ID，且位于另一页或已停用。为此只给现有 GET `/settings/categories` 增加可选 `category_id` 精确 UUID 筛选；通过既有 UUID 归一化、SQL 参数和主键查询取回真实元数据。响应仍为 `rows/pagination`，其它配置列表不接受该参数。精确查询可与已有过滤条件相交，不改变默认列表合同。
- 只有缺少原值元数据时才发一个精确查询；不逐页遍历、不按名称匹配、不默认归入“往来”。不存在/加载失败明确显示；用户可按原规则重选或重读。
- 精确读取与候选列表使用独立查询状态，不能覆盖彼此的 rows。切换收付方向、选中 ID 或关闭表单时取消过期请求；返回结果只用于它对应的当前 ID，防止旧默认分类回填到新草稿。复用现有取消机制，不新增请求调度层。
- 已有流水的停用原分类按旧规则显示和保留，新建流水不能把停用默认值当成有效新选择。普通账户/账单候选和历史表头筛选不改为此分类录入规则。

### 2.3 内容说明与唯一办理入口

- `content` 保持必填且去除首尾空格后不能为空；`remark` 保持选填，允许清空。只改标签和必要提示，不改字段名、长度、历史值或数据库。
- 删除“本次办理用途”下拉、`purpose/purposePartId` 状态及只服务该下拉的分支。不要误删后端列表查询里名为 `purpose` 的合法筛选参数。
- 下方标题改为“借款、费用与还款（按需登记）”。保留“新增借款 / 代付”，支出保留“登记实际费用”；原“关联已有事项”改为“登记还款 / 回款 / 费用结算”，内部选项按方向使用“收回借款、归还借款、公司回款、费用付款、费用退款”等具体名称。
- 没有选择办理项时，一次保存仅创建现金流水；费用类型和备注不触发推断或自动挂账。
- 创建第一条新增借款/费用办理项时，一次性带入已填写的金额、内容说明；用户可更正。流水“人员 / 经办对象”不自动映射为往来对象，两者可能不是同一人；一般借款的往来对象由用户明确填写，个人专账归属使用已配置人员。后加的办理项金额不自动复制整笔金额，避免多条全部占用整笔。既有事项结算仍需显式选择目标和本次金额，不能自行填满债务余额。
- 一次性预填之后不使用 effect 持续覆盖用户编辑；最终沿用原金额分配校验。不将“事项说明未填”默默替换为“其它”，也不从备注猜往来对象。
- 个人代付在借款项选择“个人专账”后，才读取专账归属配置并明确展示归属人；该归属使用配置，不从人员输入或信用卡分类名称猜。配置依赖由现金表单 owner 管理，组合组件接收状态/结果。失败只阻止含个人代付项的保存，普通收付仍可办理。
- 个人专账、借款方向、账单标识/月份和费用关联借款能力保留。删除 `personalEntry` 的位置/首行特判，改为按每项真实类别呈现和校验，多个办理项也不能错用个人归属。
- 每月任务继续复用同一表单、同一次原子命令；任务标题不隐式确定代付。任务已录流水认领入口继续只关联，不重新生成借款或流水。

### 2.4 补记原始收付的迁移闭环

- 通用新增流水移除“补记借款现金来源”按钮和从任意来源选择借款的 `origin` 行分支。
- 仅在 `type=loan && !is_opening && origin_flow_id===null` 的借款详情显示“补记这笔借款的原始收付”；已有来源显示原有“来源流水 / 纠错”。条件来自现有后端规则，不增加新的确认门禁。
- 借款详情通过 `onOriginFlow(item)` 回调交给当前 owner 打开原 CashFlowDrawer；CashItems 不反向 import CashFlowDrawer，避免现有 Drawer→Items 依赖形成循环。
- 明确区分补来源与归还：借出/代付的原始现金为支出，借入的原始现金为收入；原始日期、项目取借款本身并展示只读，金额预填原额但仍按原预算规则校验，账户和分类由用户指定。
- 表单使用明确的来源上下文，与普通新增、已有事项结算、编辑上下文互斥。提交仍是 POST `/flows`，`project_mode=selection`，`origin_items=[{item_id,expected_item_version}]`，不发送新借款或还款 allocation。不得冒用 `project_mode=existing_item` 绕过原来源约束。
- 原来源绑定仍可能受当前 OA 新增资格约束；本次不放宽，也不能遇到已结束项目就静默改“无项目”。历史事项还款仍沿用原 `existing_item` 路径，不受此补录限制变化影响。
- 成功后现金账户只增加一次原始收付，旧借款本金不再次增加、余额不被当成归还减少；详情重读后补录入口消失、显示来源链接。关闭新表单回到原详情；失败保留草稿、取消无写入。
- CashBooks 和 CashFlowDetailDrawer 两类现有详情 owner 均接入回调；关联详情切换借款时使用当前借款，不能携带上一条借款的上下文。删除补录流水仍执行原 `linked` 语义，保留真实旧借款并解除来源绑定。

## 6. 性能与必要校验

### 6.1 有界性能方案

- 分类管理初次最多三个组查询，每组 50 行；单组翻页只查该组。分类候选最多 100 行/次，搜索取消旧请求；缺少选中引用最多一次精确查找，不拉全部页。
- 分组为当前候选 O(n) 处理，组名/顺序为现有枚举；不每行查详情、不新增报表 N+1。仅明确个人代付项读取个人配置，不让普通收付等待它。
- 保存仍一次 POST/PUT、原事务；成功使用现有 cash revision 重读，不先写现金再串行写借款；读取失败不重发已经成功的写入。
- 用合成的 30 类与 1,500 类（每大类 500）验证分组/搜索/跨页原值，三组各 50、候选 100 的上限保持固定。相同机器、浏览器和本地独立数据库下记录查询数、响应体大小、p50/p95，每种关键动作至少 20 次。
- 本地工程目标：已有数据时菜单展开/分组响应 p95 ≤100ms；分类管理三组全部就绪 p95 ≤500ms；精确分类读取 p95 ≤100ms。分别记录冷启动和重复操作；这些是测量目标，不新建 CI 硬时间门禁，不承诺公网延迟或所有业务均能达到。
- 先解决本轮引入的重复请求、串行等待或渲染阻塞；不以本次优化名义改数据库连接池、加缓存或重做无关慢查询。不能只报告“感觉变快”。

### 6.2 应保留与不新增的控制

保留：正数/小数精度、内容非空、收付方向/账户/分类有效性、分配额度与欠款不能超额、个人归属、版本冲突、权限、原子事务、重复提交保护、已有放弃草稿/删除/切换方向丢失办理项的确认。

不新增：选择分类审批、借款录入二次审批、哈希快照、任务前置清单、所有资料补齐才可记普通现金、用户重复确认保存、自动回滚到旧界面。必要校验是避免错账的边界，不属于可随意删除的耗时门禁。

“不影响其它页面”是回归目标，不能在未验证时保证零缺陷；通过限制改动到 cash、共享组件实现不变和实际回归降低风险。“禁止兜底”指不伪造数据、不吞错、不降级旧链；明确错误反馈、取消旧请求和按真实 ID 查询并非兜底。

关键算例与断言：

1. 三组各至少 51 条：第二页可找到，切一组页码不动其它组；搜索/新增/停用后组总数和结果正确；某组请求失败不伪装空组。
2. 候选超过 100 条：分页/搜索可选择后页类型；已有已选类型在别页仍正确显示；任务仅有默认 ID 时精确读取、停用/不存在反馈准确。
3. 普通支出 100：一条 flow，related_items/origin_items/allocations 都为空；内容空白不能保存，备注空可保存。
4. 借入 10,000：现金 +10,000、我方欠款 10,000；归还 3,000 后现金 -3,000、旧债剩 7,000，无第二笔本金。借出方向相反。
5. 任务中个人代付 2,480.52：现金减少一次、个人应归还增加一次、任务累计一次；配置失败不猜人员；普通录入不受个人配置故障阻断。
6. 已登记非期初借款 1,000 漏来源：详情补现金后本金仍 1,000；再次补绑定被既有版本/来源约束拒绝；删除补录流水后借款保留、来源解除。期初/已绑定借款无补录入口。
7. 来源补录项目不适用时明确错误且零写入；已结束历史事项的真实还款在 OA 不可用时仍走原合法路径，无新增项目限制污染。
8. 费用付款/退款及有票、无票冲抵既有路径不丢；现金写入失败整体回滚，成功后重读失败不重复 POST；未授权无现金正文。
9. 内部转账只登记一笔、不建立债务、不显示分类/办理项；改方向丢弃办理项仍按既有确认，不引入新连环确认。
10. 经办人与实际借款对象不同：借款对象不从经办人推断；分类精确读取较慢时切换方向/ID，旧响应不能覆盖新选择或重新挂入旧分组。

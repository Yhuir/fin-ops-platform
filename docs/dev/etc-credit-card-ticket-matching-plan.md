# ETC 信用卡账单与票根文本匹配实施计划

日期：2026-09-14。

状态：2026-09-14 已按用户授权实施并进入发布验证。以下保留设计与验收口径；实际实现差异和验证记录见末节。未使用 GSD，不新增审批工作流。

## 1. 结论与必须纠正的认识

实施方向合理，但不能把“尽量分配”理解成无条件追求更高配对率。系统应在合理候选中自动择优，明确输出已匹配/未找到；解析失败、非通行交易是不同问题，不能被包装成匹配结果。

以下要求不能按字面无限扩大：

- 金额相近不是金额相等；23.00元不能自动当成23.50元。日期延迟可以有业务规则，明确身份或币种冲突不能被评分抵消。
- “不设过多门禁”不表示删除权限、已有来源校验、任务版本、已确认状态保护和事务。它们是当前操作的数据正确性，不另做预审批系统。
- “禁止兜底”不表示删除扫描PDF的OCR。文字PDF提取、扫描页OCR是明确的格式处理分支；禁止的是吞错、无依据补值、无限日期同金额搜索、失败后切旧算法。
- “高性能”不能用候选截断或提前放弃完整配对换取。首次OCR与普通刷新分别测量，刷新不得重新OCR。
- “彻底杜绝Bug”不能承诺任意未来未知格式零错误。可验收的目标是已支持格式不静默漏行/串行、已知反例受测试保护、异常可定位、无合理候选明确未找到。

## 2. 已有证据和本次验收结果

六笔商户OCR将“贵州黔通智联”识别为“贵州通智联”。解析器设置 `is_etc_candidate=False`，matcher在金额/日期计算前跳过；页面又把未进入候选统一显示成缺票。仅在临时内存放开这六笔，算法不变，即30对、1,711.33元。

本批最终应为：30笔已匹配、2笔支出未找到（47.51元和23.00元）、1笔还款不参与。两笔未找到合计70.51元；32笔支出合计1,781.84元。剩余31笔票根1,949.25元不因提高配对率而强配。

已有测试：后端 `test_etc_reconciliation_service.py` 108 passed；前端页面/API 123 passed。它们尚未覆盖本次商户OCR缺字与若干状态反例，不能把旧测试全绿当成修复完成。

## 4. 单一匹配规则

### 4.1 输入、分类与金额

1. 所有合法支出行先保留，不以精确商户关键词决定是否保留。还款/退款/零金额、明确人工排除及明确非通行消费不进入自动通行分配。
2. 商户识别做空格/分隔符规范化和有来源证据的名称识别。本次“贵州通智联”作为已复现商户写法处理，但未知商户不因缺少关键词一票否决：同日或摘要明确通行日、精确金额、无身份冲突的票根可以形成候选，证据权重低于明确ETC商户。它仍是系统分配判断，不能宣称银行订单唯一证明。
3. 不使用大范围字符串相似度、LLM判断或不断增大的黑白名单。明确餐饮/加油等已有可识别非通行类别保留排除；不能从“财付通”三个字推断全部是ETC。
4. 金额以整数分比较，解析入口使用Decimal；人民币票根只匹配已明确为人民币的结算金额。保留/读取结算币种，不能丢弃第二币种。已支持单币种表头可以提供该列币种；既无列值又无表头依据时报告缺失，不猜CNY。
5. 有明确车牌、通行日期或方向性站点证据时应用相应约束；没有字段只是证据少，不等于冲突。站名存在前缀/简称时先规范化，无法证明矛盾的名称只用于排序，不新增所有站点必填要求。

### 4.2 日期规则和建议默认值

本轮固定以下建议作为实施起点，属于产品选择，不宣称覆盖所有银行的实际结算周期：

- 摘要与“通行费”等业务上下文明确关联的通行日期存在时，使用该日；不把任意8位订单号当日期，不再由第二轮金额搜索突破该日期。
- 无明确通行日期的已识别ETC扣款：行程范围为交易日前7天至交易日；另保留至多次日、且不晚于记账日的日期窗口，兼容现有交易日/记账日差异。这是一次候选生成，不是匹配失败后的兜底。
- 未识别商户仅用交易同日或摘要明确通行日的精确金额证据；不对弱身份开放跨周搜索。
- 同日优先，其次越接近越优先；等距离优先扣款前的行程。跨月、跨年按日期差计算，不按月份截断。通行日期不因账单自然月份而被排除。
- 缺失、非法日期在parser形成问题；不使用 `date.max/datetime.max` 把坏输入送进正常匹配。
- 超过日期范围的正常记录输出未找到，可人工明确关联或提供扣款依据。以后出现可复现的更长延迟实例，再修改这一个规则及测试；不加页面配置面板，也不无限扩大窗口。

7天是“尽量分配”和“不跨整月乱配”的建议折中；若将它收窄为现有1天，会减少误配也增加缺配。计划清楚保留这一取舍，不能把它包装成客观必然正确。

### 4.3 分配算法与占用

1. 先保留明确人工指定；排除removed来源、人工拒绝边、已占用行程和字段冲突边。
2. 按金额分组，日期排序/区间检索生成候选；不用每笔卡全扫所有票根，不截取前N个候选。
3. 在每个连通分组内统一求最大数量、最小代价的一对一分配。使用矩形 Hungarian 最大数量、最小代价分配，在现有matcher内以标准库实现必要函数；不增加求解器依赖、不建设通用图框架。代价依次体现证据强弱、日期距离、方向；等价结果使用稳定来源行顺序。整数权重按实际组大小推导，不能让任意魔法常数破坏优先级。
4. 分组方法和直接取唯一边是同一目标的化简，不是失败后的备用算法。不保留“≤16指数搜索、>16换算法”的分支；不以超时返回半份已完成结果。
5. 完全等价候选直接分配。重复运行同一任务结果稳定；上传顺序改变后归一化业务配对和金额等价，不承诺无订单号的两笔完全相同交易具有可证明的物理先后身份。
6. 一笔卡自动对应一笔行程，行程只能消耗一次。多张发票仍属于一笔行程。本轮不增加任意一对多/多对一求和；没有合并扣款来源事实，不写组合金额搜索。

数量优先的取舍必须明确：若A可配X/Y、B只能配X，系统选择A→Y、B→X，即使A单独看更接近X。这符合本轮尽量分配的目标；不能同时承诺每笔独立最近和全局最多。没有共同订单号的等价候选，只能保证规则确定的分配，不能宣称已证明原始支付归属。

### 4.4 对用户显示

- 有效通行支出仅显示“已匹配 / 未找到”。保留可展开的简短匹配依据，不显示待确认的“高度可信”。
- 还款等显示“不参与核对”；未知消费未找到时显示“未找到”，不武断断言它一定不是ETC。
- 匹配未完成、请求失败和来源解析问题使用既有操作/错误区域，不能借二态要求把失败显示成已完成的未找到。
- 历史 `recommendation_status` 可保留给旧已确认记录的读取，但新匹配不再产生 `needs_review` 作为处理分支。页面以有效链接为配对事实，不按“suggested”字样猜链接。

## 5. 解析、重复输入与已有数据

### 5.1 PDF

- 以页为单位读取；文字页按交易表解析，扫描/不可提取的交易页走既有OCR，纯说明页不触发无意义的交易失败。每页位图用完释放，同一文档不重复初始化OCR引擎。
- 保持一份行归一化逻辑；两个路径都生成相同模型，明确sourcePage/sourceLine。保留OCR原始摘要，商户规范化用于计算，不篡改原文证据。
- 对疑似交易行逐行记录成功或issue，覆盖金额断裂、换行、负号、币种、非法日期；不能匹配不到正则就悄悄continue。无法恢复的字段不猜。
- 利用账单已提供的支出合计/还款/余额做对应口径核平；缺少总额不自动失败，差额明确提示，不用总额反推或填造缺失行。信用卡正常行可展示和核对，坏行明确不可参与；不新增阻断所有文件的全局门禁。
- 已有TXT“坏记录使该文件零可核对items”的安全规则继续保留，不为了少报错删除。

### 5.2 TXT与去重

- UTF-8/BOM/GB18030/GBK复用现有严格解码；按明确车牌段和交易时间段解析，页眉切换不得污染上一条记录。
- 保留现有跨文件自然行程去重，但增加来源归属处理：重复来源删除一份不应丢掉仍有来源的行程；同一自然行程的移除/人工决定不能因另一个副本成为代表而消失。
- 同一文件内真实同日同金额双笔必须保留；不要按日期+金额集合去重。
- 信用卡确切重复来源复用已有文件识别；同账单身份（银行、可确认账户、账单日期/期间）下逐行比较及出现次数核对文档重复。完整相同内容不累计。部分重叠不做泛化“智能合并”：明确提示该账单来源需替换，相关重复来源不能同时贡献自动匹配，其他账单继续工作。账户身份不足时不自行合并两个文件。
- 不新建OCR全文缓存、内容hash或全局交易指纹。保留现有原件hash、ID和导入确认hash。

### 5.3 最小数据增量

仅在既有task JSON及行模型中补充现有字段无法表达的必要信息：结算币种/解析定位、匹配依据、每笔卡明确拒绝的票根ID集合。具体字段名在实现时与DTO逐项对应，不新增关系表、配置表或算法版本hash。

旧已确认task继续可读。缺失的新字段只能按其明确历史含义读取：拒绝集合为空表示历史没有记录拒绝，不能补猜币种或关系。新解析、旧数据刷新、确认前检查必须使用同一matcher；不保留旧匹配代码作兼容分支。

本次旧批次已有准确日期、金额和61笔行程，其六笔分类漏配可通过刷新从保存行重新分类修复，不能继续把旧 `is_etc_candidate=False` 当事实。不过，新规则若需要旧模型未保存的结算币种证据，不能以旧交易币种代填：该来源执行一次下述显式重新解析，补齐后再按统一规则刷新。普通刷新始终不做OCR；不能同时承诺“不补猜新字段”与“所有历史批次绝不需要重新解析”。

确有历史解析缺行时，提供当前来源的显式“重新解析”：复用上传解析service和原件读取，锁外解析、同一任务版本提交。只针对选择的来源，不全库重算。来源ID/原行身份未变的人工决定保留；发生行拆并且不能确定对应关系时明确列出需重新操作的具体行，禁止猜迁移人工决定。

来源代表切换或重新解析导致ID变化时，人工拒绝边与人工指定同样纳入身份映射：只有原行与新行存在明确一一对应时迁移；不能悄悄丢掉拒绝集合。无法对应的决定明确列出，不把旧拒绝误施加给同金额的另一笔。

## 6. 当前任务写入与人工操作闭环

### 6.1 必须移除全量任务回写

`save_etc_reconciliation_state` 当前遍历已加载的所有task并upsert，`get_task`还会全量重载。这与高性能和批次隔离目标冲突。本轮增加的是现有repository的窄方法，不是新的持久化架构。

- 复用已有 `get_etc_reconciliation_task_record(task_id)` 读取当前任务，并补足当前任务来源文件的正式行读取。列表/显式维护的全量读不冒充热路径。
- 以 `save_etc_reconciliation_task(..., expected_version=...)` 为拟定窄写端口：当前task/version/audit与该task文件元数据在同一数据库事务中提交，UPDATE带预期version；冲突明确返回409。
- source file表只处理该task的新增/删除/变化，不能回写其他任务文件。refresh若来源未变不重复逐文件upsert。
- 迁移所有仍会回写任务的调用方：来源提交/删除、refresh、人工处理、confirm/reopen、导入状态、OA task同步、任务删除/显式恢复。不能只把刷新改成窄写，却保留旧入口下一次覆盖回来。
- repository负责SQL和事务，service只提交期望版本与payload。创建保留既有ID前缀，后缀改用标准库 UUID4（避免多进程计数器重复分配及对象路径覆盖）；旧ID继续可读，插入主键冲突明确失败，不用upsert覆盖另一任务；不建设全局ID服务。
- 无变化refresh不落库、不递增version、不追加重复audit；有变化时只递增一次。任务关闭或已确认后不允许普通refresh改关系，复用既有reopen流程。
- OCR/文件读取在锁外，提交前校验当前任务版本与来源是否仍有效。解析期间用户删除了来源，不能恢复它。
- PostgreSQL以已有version和事务为跨进程保证；进程锁不能宣称是跨worker保护。不设全站锁、不锁住OCR过程。持久化失败丢弃计算副本并重读当前task，不能返回成功或自动重放写请求。
- 本地测试adapter继续作为显式测试运行方式，不作为生产DB失败后的fallback；同步调整其窄写/原子保存语义，避免测试假后端保留旧漏洞。

### 6.2 人工关系操作

- `link_ticket`：释放该卡旧票根及目标票根旧自动占用，再提交新的唯一关系；另一笔已有明确人工指定时返回具体冲突，不偷偷覆盖。不能只修改一个方向。
- `unlink_ticket`：记录“此卡拒绝此票根”，随后可以自动分配其他合格候选，不能立即接回刚拒绝的那一条。
- 提供一个明确的“恢复自动分配”操作，清除该卡人工拒绝/指定后重新分配；不引入规则管理页面。手工明确指定某条时清除此边的旧拒绝。
- `remove_ticket`：从有效占用中移除，页面与后端忽略旧链接；restore后参加同一匹配器。
- 当前自动配对不等于自动勾选报销。普通刷新保留有效卡项选择；关系变化后展示新依据，确认提交使用新version。

每一步产物是可运行代码及针对性验证。直接顺序执行，不使用GSD、不拆成审批轮次；实施、推送 main 和部署已获用户明确授权。

| 步骤 | 修改范围 | 工作与删除动作 | 完成证据 |
| --- | --- | --- | --- |

## 9. 性能方案与目标

这些是同一硬件上的测量目标，不新增CI时间gate或baseline文件；未达标应定位并改进，不通过截断候选或压低输入上限掩盖。

| 场景 | 本轮目标/验证方式 |
| --- | --- |
| 本批33卡/61行程纯匹配 | p95 <50ms，100次计时，结果每次一致 |
| 1000卡/2000行程，正常多金额/多日期分布 | 纯计算p95 <1s；记录候选边数、最大组和实际内存 |
| 16/17同金额全连接 | 均<100ms且择优目标一致，取消旧6s级突变 |
| 200卡/200行程密集组 | 目标<2s；记录实际值，不用少匹配换性能 |
| refresh接口（不含OCR） | 本批目标p95 <500ms；拆分DB、计算、序列化耗时，跨环境结果分别报告 |
| 首次扫描PDF | 同等输出准确性下不劣于本机约8s的现状；单独记录冷/热OCR，不能用纯matcher时间冒充上传时间 |
| 数据库 | 当前任务点读点写；无变化refresh零UPDATE；SQL数量与其他批次数无关，无逐行commit |
| 多文件来源 | 原件存储/逐文件结果恢复语义保留；同一上传请求尽可能只在可见提交边界重算一次，失败时前序已保存来源能正确重读，不能为批量提速把提交结果藏在内存 |
| UI | 建立一次Map索引，不逐卡扫描全部ticket；复用现有表格能力，先测DOM/渲染再决定是否需要额外优化 |

不增加外部OCR服务、模型下载链路、自动备用引擎、后台轮询或缓存。单一算法若密集组未达目标，先优化同目标的图规模/数据结构并复测，不退回旧大组算法。

## 14. 实施结果与边界说明（2026-09-14）

- 已删除旧金额兜底、指数搜索/16笔切换、过期候选布尔准入和 service 全任务回写。保留的 `save_etc_reconciliation_state` 仅供显式测试/维护播种，委托同一个窄写方法；运行时仅调用当前任务 CAS。无变化刷新不保存或递增版本，导入状态使用版本+状态 CAS 并保持既有 preview 版本语义。

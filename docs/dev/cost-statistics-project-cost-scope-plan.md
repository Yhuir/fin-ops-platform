# 项目成本标签范围与内部往来标签修复实施计划

日期：2026-09-11

状态：计划待执行。本轮只新增实施计划，没有修改业务代码、配置、数据库或生产服务。采用现有模块与普通测试，不使用 GSD。

## 1. 目标及已核实事实

目标：修复内部往来标签在成本链路中缺少名称的问题；增加统一的项目成本标签范围，控制按项目、按流水标签、按银行账户三个成本视角及其明细、合计、导出。

上一轮生产只读查询确认：

- `CASE-AUTO-0100` / OA `oa-pay-2148`：150 万还款申请关联建行 8106 的支出 `txn_imported_0039` 和平安 0093 的收入 `txn_imported_0463`，银行明细的有效分类均为 `internal_transfer` / 内部往来款。
- 成本接口已取得 `internal_transfer` 代码，但主标签、子标签和标签路径为空；任务版本 0，自动确定来源，因 `bank_tag_missing` 待分配，金额仍已进入成本。
- 银行列表通过系统分类语义构造名称，成本使用的批量有效分类投影没有相同的系统标签语义。这是输出边界缺陷。
- 现有成本准入没有排除内部往来；只将明确的付错退款收入冲减来源支出。
- 全部期间成本 12,232,622.50 元；2026 年成本 10,748,266.90 元。全部期间包含来源未确定的 53 行、1,484,355.60 元；该部分不进入指定年份/月。
- 标签待完善共 3 行、1,501,400.00 元，其中 150 万是上述名称缺失，其余 200 元和 1,200 元在成本接口没有有效标签代码。
- 现有标签接口有 50 条启用规则，另有系统内部往来标签及 3 条归档规则。无 OA 项目配置当前为空。
- `tests/test_cost_statistics_bank_tags.py` 上一轮执行为 1 通过、1 失败：内部往来用例仍向当前标准化 helper 输入旧的 `effective_category_*` 字段，不能保护真实批量查询链路。

以上是调查时点证据，不是冻结金额。执行和发布时重新读取同范围事实，使用差额明细解释变化，不为匹配历史金额修改业务规则。

## 2. 本计划采用的业务规则

### 2.1 成本准入

1. 继续保留 OA 已完成、有效关联、正确金额、来源与退款归属等现有规则。审批完成时间依旧允许为空，不恢复该门槛。
2. 正式项目成本必须存在已确定的来源支出，并且该来源的有效标签已被选中。系统原有无歧义自动来源可以直接采用，不一律要求人工保存。
3. 未确定来源的成本继续留在待分配，不进入任何正式成本视角的合计和导出。未保存的建议/草稿仍不作为事实。
4. 已有来源但缺付款日期，不补日期，沿用现有无日期处理：允许的金额只在全部期间展示，指定年月排除并单列无日期金额。不得把移除未知来源扩大成新增付款日期非空门槛。
5. 标签选择是准入必要条件，不会自动让进行中 OA、普通收入或缺少合法项目归属的流水成为成本。
6. 全部取消选择表示零项目成本。设置缺失或读取失败必须明确报错，不能解释成全部允许或读取旧设置。

### 2.2 标签清单与默认值

- 清单来自银行标签 owner 的完整字典和系统标签语义，不取当前搜索、年份、分页或当前有成本的标签子集。
- 按主标签组织，展示现有主/子层级；单层标签正常显示。同名但不同标识的标签不合并；多条匹配条件产生同一标签时不重复提供开关。
- 每项保留 checkbox。支出及内部往来标签可选；普通收入标签完整展示但 checkbox 不承担成本来源准入，保持禁用。付错退款作为原支出冲减项显示为系统处理，不做可关闭的冲减开关。
- “未标记”使用现有未分类标识作为独立可选项，首次不选。用户显式选中后，真实来源已确定的未标记支出可按其余规则计入未标记分组；资料待完善仍是任务状态，不能宣称标签已经完善。
- 首次持久化现有支出标签的选择集合，排除内部往来和未标记；仍可识别的历史支出标签纳入初始化考虑，不因为归档就悄悄丢掉历史成本。归档标签在清单中标识，允许控制其历史成本范围，不恢复其银行分类规则。
- 之后新增标签不自动加入选择集合。改名沿用原标识的选择，删除或不可识别的历史代码明确处理，不按名称猜新标签。
- 所有标签由其现有稳定代码识别。若三级路径只是同一代码的业务维度，本次开关作用于整个标签代码，不能在 UI 上伪装成彼此独立的三级开关。

### 2.3 分配、退款与无 OA

- 保留完整 OA、支出、付错退款、来源分配和非成本事实，先按现有规则完成对账，再决定各已确认来源行是否进入项目成本。
- 不把“被范围排除”写成用户的 `non_cost_amount`，不改 OA 原额、不把取消标签后的流水删除再重新配平。
- 一张 OA 拆到多笔来源时，只计入允许来源对应的金额；一笔来源支持多张 OA 时，对该来源的所有分配一致应用范围。
- 不增加部分草稿持久化。只有现有自动来源或现有有效保存决定才是来源事实。
- 支出 1000 元、明确退款 200 元，允许的来源成本为 800 元；取消该来源标签后为 0。不得因收入标签未选使成本反增为 1000。
- 全部来源不在范围的关系从项目成本待处理列表及数量中移出；混合关系保留完整对账资料。未知标签未获准入与未知来源分别处理，不能混为一种状态。
- 保存的分配记录保留；重新勾选后按当前事实重新计算。范围改变不应使原分配事实过期，不把范围版本加入现有来源 fingerprint。
- 无 OA 成本必须同时满足全局标签范围、现有虚拟项目映射和无 active OA 关系保护。新范围不自动创建项目，不改写原映射。

### 2.4 作用范围

同一全局设置作用于历史和当前三个项目成本视角、根合计、下钻、成本详情、预览、XLSX 和待分配数量。银行明细、关联台、账户余额，以及成本页面内的两个原始银行流水视角保留全部真实收支。

范围设置的校验只进入项目成本读取/写入所需链路。两个原始流水 view 保持原有提前返回路径，不因新范围配置缺失、读取错误或空选择而不可用。

这里的后端短文件名均位于 `backend/src/fin_ops_platform/services/`。不新增通用策略引擎、分类器、缓存、队列、worker 或 read model；不把银行页面 HTTP payload 当成成本输入。

拟新增接口，名称属于本次设计而非现有 API：

- `GET /api/cost-statistics/project-cost-scope`：返回 `version`、`selected_tag_codes`、`available_tags`、`can_save`。标签项含既有稳定 code、展示 path、状态和是否可选；不传银行流水明细。
- `PUT /api/cost-statistics/project-cost-scope`：仅接受 `expected_version` 和完整 `selected_tag_codes`；返回保存后的配置及 `changed`。复用成本规则既有读写权限。非法代码/字段/类型为 400，权限不足为 403，版本冲突为 409。
- Settings family 拟用 `cost_statistics_project_cost_scope`，只持久化版本和选择；展示标签来自当次字典，避免复制一份名称事实。
- 查询响应在请求级提供范围版本；复用既有成本 cursor 校验绑定该版本，不新增 hash 或签名。范围改变后的旧 cursor 明确失效，前端重置分页后重读。
- 分配详情如需新增范围状态，由后端返回来源/任务是否在项目成本范围内；前端不自行按标签再实现准入。完整分配金额与正式成本金额不可混用。

## 4. 按顺序执行的实施步骤

### 步骤一：先修有效标签输出

- 复现系统内部往来代码存在、主标签缺失的批量投影；补充真实 PostgreSQL 场景。
- 在银行分类 owner 中统一系统标签语义输出，保留现有人工覆盖优先级，不把系统自动结果盖过有效人工分类。
- 单层标签允许空子标签；Cost 分组按现有无子标签规则表达，不复制主标签填子标签。
- 更新失效的旧字段单测；补齐“银行明细输出与成本批量输出语义一致”的回归。
- 验收：150 万来源应输出内部往来；主标签不再待完善；真正未标记仍保持未标记。

### 步骤二：建立独立、窄写入的设置

- 复用已有 versioned family 持久化原语；新写命令只合并本 family，校验当前版本、代码合法性，并用同一 PostgreSQL transaction 写 durable audit。
- 不照搬现有某些方法整份 snapshot 保存后单独记 audit 的写法；也不借本次任务广泛重构其他设置 writer。
- 对完整相同的选择返回 `changed=false`，不增加版本或重复审计。
- 迁移仅在设置缺失时一次性初始化；新安装走显式初始配置入口。初始化、读取和每次保存职责分离，GET 不写入，runtime 不生成“缺失时全选”。
- 区分“配置键不存在”和“已保存的选择为空”。空数组是有效的零成本范围；重复部署、重启、标签字典暂时为空和重复保存均不得重新全选。初始化本身不依赖先存在普通标签才能完成。
- 保持设置正式 payload 与现有 raw normalized mirror 一致。检查现有 normalizer、普通设置保存和标签变更路径不会删除新 family 或自动扩选。
- 验收：并发两个保存只有合法版本生效；数据库或审计失败整体回滚；其他 settings family 不被覆盖。

### 步骤三：统一正式成本集合

- 在现有 Policy 中实现一处纯函数范围判断，选择集合每个请求构造一次。
- 保留来源构建与完整闭合校验，去掉未定来源向正式成本集合插入占位成本行的旧分支。未知来源任务仍保留，不伪造日期/标签。
- 对有效来源成本行和无 OA 行应用同一准入；不能在页面、路由或导出各写一遍过滤。
- 全部期间、年、月、搜索、根合计与下钻都消费过滤后的同一集合；未定来源金额仍可作为明确的待处理质量信息，不能再加进正式总额。
- 分别测试内部往来、未标记显式选择、混合标签、退款、真实有来源但缺日期、O=N 与 O!=N。

### 步骤四：打通人工分配与详情

- 任务列表和计数使用同一范围判断。全排除关系不占成本待处理数；混合关系不能因为有一个排除来源而消失。
- 尚未确定来源的任务根据关联组完整支出来源的准入情况判断是否仍需处理，不能根据已过滤的成本行或占位行空标签判断。组内仍有允许来源时保留任务；组内所有来源都不允许时才从该范围移出。
- 任务内部保留完整来源事实。来源选择、OA 目标、退款、非成本的闭合条件不因标签取消而改变。
- 已打开任务期间其他人修改范围，保存仍只保存合法来源分配，不冻结旧准入；返回/重读按当前范围显示，不把“已保存但不在当前成本范围”伪装成保存失败。
- 检查现有详情通过可见任务集合查找的实现：不能因为任务已被范围筛出，就错误阻断有效记录回查或误报数据库保存失败。分配事实定位与列表可见性在同一实现中明确分开。
- 被排除的成本下钻链接按正常不可用处理，原银行来源仍通过原始流水入口查询。
- 如混合关系需要状态文字，只使用来源行的短状态“范围外”等，不重新加入长篇解释性文案；绿色金额一致提示仍说明完整分配闭合，不表示所有金额都进入项目成本。

### 步骤五：实现右侧抽屉和刷新闭环

- 复用 AppDrawer、HeroUI Checkbox/Button 和现有加载/错误样式。新增一个专用展示组件；页面容器拥有 GET/PUT 和草稿，组件通过 props/callback 交互。
- 三个项目成本视角右上角显示“项目成本范围”；使用标签分组及搜索，清单项前有 checkbox。普通收入保留可见的禁用 checkbox。首版不加规则表达式、动态预览接口或新的配置页。
- 首次打开抽屉才读取清单；勾选只修改会话草稿，不请求网络；点击保存才提交。保存前页面金额保持已生效设置对应的数值。
- 成功后取消过期读取，重置成本 cursor/失效下钻路径，更新当前成本视角；任务列表仅在已打开时重读，关闭的任务详情下次打开取新值。不刷新整个浏览器，不触发其它页面请求。
- 本窗口保存后使三个成本视角的旧请求结果和任何会话缓存失效；保留用户的年份/月份与搜索，仅重置失效分页/下钻。其他窗口下次正常读取使用最新配置，既有版本冲突保护覆盖旧表单；不为实时同步新增轮询或推送。
- 保存失败保留草稿；无权限可读不可写；并发冲突提供重读。网络超时不自动重发 PUT，使用现有明确保存结果核实方式读取版本和选择内容。
- 浏览器视觉验收覆盖宽屏、较窄窗口、长标签、滚动、禁用状态、键盘焦点和保存错误；真实查看截图，检查颜色对比、布局和按钮位置。

### 步骤六：删除旧逻辑并同步文档

删除/替换范围：

- 未定来源继续生成正式成本占位行的执行分支，以及与该旧口径绑定的失效断言。
- 用全部任务数代表本次成本范围任务数的旧统计位置。
- 本次发现的有效标签语义不一致分支；改为同一明确规则，不保留新旧选择开关。
- 仍使用旧 `effective_category_*` 入参测试当前标准化 Cost helper 的测试输入与旧重复子标签预期；把有效断言迁到现有边界。
- 如更新 DTO，删除原调用点被替代的 mapper/字段读取及无调用方代码，不追加旧字段兼容。

保留范围：已有完整金额校验、事务、权限、审计、来源 fingerprint、正式发布保护；历史 migration 与验证旧接口拒绝的测试。退役的 `cost_statistics_time_tag_selection` / `time-tag-rules` 不恢复。

执行 whole-repo symbol/text scan 追踪被修改公共 helper、删除符号、旧标签设置的调用方；不因文件名字旧就删除仍有效的业务代码。

更新 `docs/business-flows/cost-statistics.md`、`docs/modules/cost-statistics/{README,boundary-io,state-machine,tests}.md`、银行标签输出与 Settings 对应边界。测试文件范围、HTTP 合同和持久化责任变化时同步开发/模块文档。本计划只记录执行设计，实施后更新为实际验收记录。

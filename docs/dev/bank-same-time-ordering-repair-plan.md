# 银行同时间流水顺序与账户余额修复计划

日期：2026-09-08。状态：已获执行修复、提交/推送 main、部署与生产验证授权。实现及本地验证见 §12；前面的计划与设计阶段记录不代表发布结果。

## 1. 目标、事实与范围

目标：同一账户多笔交易时间相同时，不再以随机记录 ID 或未经证实的银行流水号决定真实记账先后；银行明细、导出、账户余额使用同一判定结果，原始银行时间、金额、余额保持不变。

上一轮已完成的生产只读核对：2026 年建设银行 8106 的 accounts 与 transactions 均返回 665 笔；列表先显示支出 1.00 / 余额 94512.82，再显示支出 54000.00 / 余额 40512.82；前后两次 accounts 均返回最新余额 94512.82。这是已确认的查询取值错误，不仅是浏览器旧数据。截图中的 662/665 差异未在该次核对中复现，不直接归因于缓存。

已验证的正确衔接：

- 2026-09-08 15:36:50：94513.82 → 支出 1.00 → 94512.82 → 支出 54000.00 → 40512.82。
- 2026-09-03 17:16:44：60672.45 → 支出 1.00 → 60671.45 → 支出 300.00 → 60371.45。

当前根因：

1. `bank_details_canonical_query.py` 的 page keys 与最终 rows 均按 `trade_time_sort DESC, row_id DESC` 排序；公开导入 ID 为随机 UUID。
2. `bank_account_balance_canonical_rows.py` 的 latest balance 按时间、`bank_serial_no`、ID 倒序取最新非空余额，与列表规则不同；没有余额连续性判定。
3. accounts 与 transactions 是独立只读快照和独立前端状态；已共用页面 refresh token，但没有跨请求的数据库同一时点保证。
4. 现有主要测试覆盖普通时间排序、最新非空余额、SQL 查询次数，不能替代同时间真实 PostgreSQL 业务用例。

本轮只涉及 `bank-details`、`bank-account-balance` 的查询、DTO、页面状态和 XLSX 导出。导入 owner 是只读证据来源和回归对象；不改导入判重、流水身份、批次归属、分类、配对、核销、现金池或全局权限。

不新增数据库、账号、表、持久化顺序列、worker、缓存、read model、消息、依赖或通用图算法框架。不使用 GSD。本计划不授权执行、提交、推送或部署。

## 2. 业务规则及必要限制

### 2.1 判定证据

- 使用 canonical `trade_time` 的实际精度比较，不先格式化到秒而丢掉原有精度；无时区的来源时间沿用现有导入时区规则，不改变生产 session 时区。
- 银行流水号、账户明细编号和源文件行号只作为原始证据保留。没有明确顺序含义的证据前，不参与先后判定；不新增“按银行配置排序规则”的设置界面。
- 第一实施步可通过既有导入 provenance 核对截图对应原文件。文件不在本机时，不因此阻塞余额衔接方案；不猜字段、不补造顺序号。若发现可直接解决问题的银行权威序号，先评估是否能删减下述推导工作，不保留两套并行排序。
- 导入时间、批次先后、UUID、金额大小、余额大小本身都不是记账顺序。
- “当前余额”在本 App 中只能指截至最新已导入交易的可确认余额，不保证等于此刻银行系统实时余额，也不证明银行文件在 App 外部的完整性。

### 2.2 组与金额

- 按现有真实账户身份、标准化币种、同一实际交易时间组成处理组；不按账号尾号合并，不跨账户或币种拼接。
- 原始金额与余额使用 PostgreSQL numeric；测试使用 Decimal。`before_balance = balance - signed_amount`。同时验证方向、正金额与 signed amount 一致；缺失或冲突不自动补 0 或猜方向。
- 每一条 canonical 流水都是独立成员。同金额、同余额但 ID 不同的记录不能在查询阶段合并；导入判重仍归原 owner。
- 时间精度必须来自已存在的事实：保留 `trade_time` 与 `txn_date` 的区别，不能把 `coalesce(trade_time, txn_date::timestamptz)` 的展示排序键当作真实时间证据；不假设数据库已有一个名为“时间精度”的字段。若导入已经丢失精度且原始来源不能证明，不能从格式化后的时间反推精度。
- 只有日期没有时间的记录不伪装为真实午夜交易。同账户、同币种、同日若有多笔且至少一笔缺具体时间，该日整体相对先后标记未确认；其中有完整时间的行仍可按已知时间稳定展示，但不能据此认定它晚于缺时间的行。若这是最新交易日，账户末余额为 `unresolved`，不使用午夜补值挑末笔。若当天仅一笔，日期足以区分它与其它日期，余额照常独立判断，界面只显示来源实际提供的日期。历史缺时间日不自动否定更晚、证据完整的交易日余额。
- 币种先沿用现有归一口径：RMB/人民币等归一为 CNY，空币种当前也按 CNY；本次不另设默认币种或更改这一既有规则。如果原始文件证明既有空币种口径不成立，应单独说明业务影响，不能借排序修复静默改写历史币种。
- 账户身份或余额币种不明确时，不跨未知账户/币种推导。现有账户 key 保持不变；发现同一账户存在多币种时不得选最后一行的币种去代表全部余额，本轮该账户返回待核实，不扩张成多币种账户 UI 重构。

### 2.3 顺序与末余额分别判断

1. 单笔且具备时间信息：沿用时间顺序；是否有可用余额独立判断。
2. 同时间组有完整、有效的金额及逐笔账后余额：构造每笔的“交易前余额 → 交易后余额”关系，验证整组可以每笔恰好使用一次地衔接。不能只找到一对就宣布整组正确。
3. 可以证明整组唯一顺序时，生成请求内 `order_in_group`，1 为最早；列表倒序显示最大序号在前。
4. 不能证明完整顺序时，返回“同时间顺序待核实”，而不是声称“一定有多个真实顺序”。稳定 ID 只用于未确认组的稳定展示，不能据此挑最新余额。
5. 完整顺序未确认但整组末余额可证明唯一时，仍返回该末余额；无法证明末笔 ID 时 `latest_balance_transaction_id=null`。不能为了填 ID 任取一笔。
6. 缺字段、关系断开、证据冲突或末余额不唯一时，明确返回未确认，不修改原始数据、不用上一笔伪装为当前余额。

### 2.4 有界判定方法

只实现本业务需要的关系检查，放在一份共享 SQL 片段中；不枚举 n! 排列、不引入第三方图依赖。

- 对完整同时间组按余额值聚合进入/离开次数，并验证忽略方向后整组连通。连通遍历使用 `(group_key, balance)` 去重；不能把不断变化的深度或整条路径放进连通去重键，使循环无法停止。
- 整组可衔接的开放路径要求：恰好一个起点离开比进入多 1、一个终点进入比离开多 1，其它点相等；若所有点相等，则为闭合情形。必须同时满足连通性，不能仅凭净金额或度数判定。
- 开放情形的终点余额可确定；即使某些中间段有分支，也不必求出所有排列来确定这个终点。它必须对应原始账后余额，不从不完整历史累计出一个新余额。
- 逐笔顺序采用保守的充分条件：已知起点、每个余额节点最多一条出边，且最终恰好覆盖全部成员时才输出完整序号。对有分支的组不做排列搜索，返回未确认，即使逐步排除已使用边或更复杂算法可能最终证明唯一。此限制必须在测试及用户提示中保持诚实。
- 闭合情形只有存在可验证的起点证据时才采用该起点。本轮只使用紧邻前一时点的单笔、非空同币种余额作为有界校验输入；前组也是复杂未解组、历史缺口或证据冲突时，不递归追溯整个账户历史来猜起点。
- 顺序遍历最多使用本组成员数 n 步，并检查成员不重复及覆盖数恰为 n；不得依赖数据库恰好按某种递归输出顺序返回，最终显式按序号排序。
- 开放路径的组内顺序和终点依据本组完整成员判断，不要求更早导入历史连续。若紧邻前一时点的余额与本组起点不衔接，可能是跨时点缺流水；不能因此把已经证明的组内顺序或银行原始终点余额降为未确认，也不能自动补流水。这个跨时点问题由既有来源核对处理，本次不新增“历史连续性”字段、全账户对账模块或递归修复。闭合组不同：它需要外部起点证据，起点证据不足时不能确认。这些判断均只针对已导入事实，不声称证明银行明细在系统外没有漏项。

数学依据参考 [有向逐边路径的连通与进入/离开条件](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.euler.has_eulerian_path.html)；这里只借用判定条件，不安装 NetworkX。SQL 生命周期、显式排序及循环终止参考 [PostgreSQL 16 WITH/递归查询](https://www.postgresql.org/docs/16/queries-with.html)。规则证明不等于 SQL 性能证明，后者必须实测。

## 4. 查询与数据库细节

### 4.1 列表与导出

顺序为：选定账户/日期范围的候选组 → 从 canonical 补齐这些组的全部成员 → 共享顺序判定 → 与现有分类结果按 canonical identity 连接 → 最终 keyword/category filter → ORDER BY → LIMIT/OFFSET → 现有本页关系批量查询。

实现时先从命中行按时间/账户取 `page * page_size` 前缀并使用 `WITH TIES`，边界处保留完整时间/账户组；再从既有 classifier base 补齐候选日期全部成员，检测日期精度并仅计算目标组。最终仍按共享组内顺序分页，不会先截断同时间成员。复用已有 account_key；完整历史输入只在闭合组需要历史锚点时执行，不让普通列表额外扫描并计算全历史账户 identity。

特别注意当前金额 keyword 已下推：保留其对昂贵分类工作的减量，但它不能成为顺序 CTE 的唯一事实输入。可以由命中行定位组，再补齐完整组；不能只剩 54000 那一笔时，把同组手续费从顺序上下文丢掉。

缺具体时间的同日歧义检测也必须先于分页和内容筛选，从候选行所属账户/币种/日期的完整事实检测，不能因缺时间的那笔被搜索条件隐藏就变成“已确认”。这只扩大必要的证据读取范围，不让非命中行混入返回列表。

同一时间、不同账户/币种没有可比较的真实先后：展示排序使用时间倒序、稳定账户/币种组键、已确认组序号倒序、ID 稳定键。只有同组已确认序号具有额外记账顺序含义。`page_keys` 与最终 SELECT 必须使用完全相同的键；导出复用这条路径。

原 page size 1..500、导出上限 20000 + 1 检测、行计数、facets、标签和关系不变。连接必须一笔事实最多一条顺序结果，不放大金额/统计，不因未确认而删行。序号仅属于本次快照，不写回流水、不对外当作跨导入永久 ID。

### 4.2 账户余额

- 账户数量、范围内笔数与最新余额继续分开：日期只影响笔数；余额不受页面搜索/分类/分页影响。
- 优先检查账户最新时点完整组，正常单笔不进入复杂遍历。
- 最新组末余额已确认：返回该值。末余额确定但末笔身份未确认：返回值和时间，ID 为 null。
- 最新组全部缺余额时，保留“历史最新非空余额”能力，但对这个历史组也必须使用同一顺序判定；只有历史组末余额可靠才返回 `last_known`。不会为了得到数字持续越过一个个冲突组向历史搜索。
- 最新组部分有余额却无法确定末余额：`unresolved`，不从该组任挑有值行，也不将更早余额充当当前余额。
- 全账户无非空余额：`missing`；账户仍显示，不补 0。
- 保留账户名称/尾号 metadata 一致性选择逻辑，不把它误当成余额先后逻辑一起删除。
- 同一账户多币种且现有账户 UI 无法表达时，保留账户 key 和笔数，`balance_status=unresolved`，该行展示币种为 null，不能挑最后一行币种代表整个账户；所有涉及币种的总额均标记不完整，依据底层币种集合而非这一行展示币种判断。本轮不引入新的账户身份或币种子账户模型。

### 4.3 数据库与查询次数

默认零正式 migration、零数据修复、零备份：全部派生结果在现有只读快照内产生，旧数据下次 GET 自动使用新规则。

目标保持现有固定读查询数：accounts 为 settings + balance aggregate + 范围 count；transactions 为 settings + 页面/summary/facets + bounded relation；账户导出沿用现有单快照追加账户 aggregate/count。新增算法嵌入同一 SQL，不逐组发 SQL。

查询数只是防止 N+1 的检查项，不是性能结论；即使保持三次查询，若单条 SQL 出现重复全表扫描或尾延迟超标也不能通过性能验收。不为保持一个数字而叠加不可维护的查询技巧。

复用既有账户/日期/identity 索引，先看执行计划再决定是否需要一个明确有收益的索引；不预先增加索引、hash、物化视图、持久顺序列或缓存。若实测说明需要变更 schema，应说明实际慢查询、最小索引和发布影响后另行确认，不偷偷扩张本计划。

## 5. API、前端与导出

以下是目标变更，不代表当前生产已经拥有这些字段。

| 字段 | 设计 |
| --- | --- |
| `rows[*].same_time_order_status`（新增） | `time`：没有需要推导的同时间歧义；`balance_chain`：整组顺序已确认；`unresolved`：同时间顺序未确认。必须由 API 明确提供，前端缺字段不默认为确认。 |
| `accounts[*].balance_status`（新增） | `confirmed`：最新已导入组末余额可靠；`last_known`：仅历史已知余额；`unresolved`：存在数据但当前末余额无法确认；`missing`：完全没有可用余额。 |
| `latest_balance` | 既有 nullable 金额字符串；confirmed/last_known 返回可靠来源值，unresolved/missing 为 null。不是重新计算的流水余额。 |
| `latest_balance_at` / `latest_balance_transaction_id` | 只表达该值的实际来源；无法确认单条末笔时 ID 为 null，不用随机 ID 补齐。 |
| `has_balance` | confirmed/last_known 且有可用数字为 true；其它 false，不单独当成“当前余额完整”标志。 |
| `total_balance` | CNY 范围内所有应计账户均 confirmed 才返回完整合计；有 last_known/unresolved/missing 时为 null。真实合计 0 返回零值字符串，不是 null。 |
| `total_balances_by_currency` | 只包含能形成完整合计的币种；缺失币种不是 0。前端结合 accounts 状态显示未完整，不混加币种。 |
| 既有余额数量字段 | 继续按是否有可显示来源值统计；总余额是否完整由 balance_status 判定，不把两个概念混用。 |

不新增 CRUD、人工拖动排序、手工修改余额或“确认推断结果”按钮。未确认行只在时间旁使用现有 HeroUI 小型提示/Tooltip，说明“同时间顺序待核实”；正常行不堆叠标记或增加大卡片。`last_known` 必须展示“最后已知余额”和来源日期；unresolved/missing 显示对应文字或破折号，不显示假 0。

未确认的处理闭环：通过既有导入来源记录核对原银行明细；确有漏项时走正式预览/确认补导，确有错误时走既有受控纠错或符合条件的批次撤回/重导，下一次 GET 重新判定。不能在排序修复中静默更正金额或删除所谓重复项；原始资料仍不足时继续明确未确认，不新增猜测式人工排序入口。

总余额不完整时显示“暂无法确定完整总余额”，附简短账户数量提示；不在本次增加另一套“估算余额/推测总额”。这是对当前“部分已知金额也叫总余额”的口径纠正，必须同步 API 文档及测试，不能仅改文案掩盖返回值。

导出保留所有现有列名称、相对顺序、金额值和 sheet 分组，在末尾追加“同时间顺序说明”列；正常留空，未确认明确说明，已确认可写“按账后余额衔接”。不在文件内重新排序或为未确认组补造组内序号。已有导出权限与下载审计保留。

新增状态字段、nullable 总额、导出末列属于明确的输出变化，必须同步类型、映射、现有消费方和断言；尤其排查把 null 转成 0、把空币种替成某个展示币种、严格依赖导出列数的调用。这里只修受影响的消费点，不重写全局金额格式化。前后端按既有同一 release 配套发布，不新增双版本适配或轮询；旧浏览器在版本切换后若遇到新旧接口不匹配，应明确要求刷新，不能把缺失状态当成 confirmed。该行为须复用/核对现有发布与请求错误处理，不新增版本服务。

## 6. 刷新链路：先复现，再最小修复

现有页面 refresh token 已同时驱动 accounts、rules、transactions，不添加第二个刷新入口或跨页通知。

实施时先用组件测试模拟：accounts 慢、transactions 快；一个失败；旧请求晚返回；导入完成后重新激活；快速切换账户/日期。核对同一日期/账户统计，不拿全历史 count 与年度 count 比较。

- 确认旧请求可回写时，使用现有 AbortController 加结果提交前检查，确保过期请求不能覆盖当前状态；不要新增全局版本服务。
- 确认局部失败被另一个成功请求清掉时，局部记录失败并显示“账户未更新”或“流水未更新”，不让旧结果冒充本次成功结果。
- 如果现有流程已满足测试，只增加回归保护，不为猜测的缓存问题重写状态管理。
- Promise.all 或相同请求编号只能协调前端显示，不能制造两个 HTTP 请求共享数据库快照。本轮不承诺并发写入期间两端绝对同一时点；需要这种更强产品保证时再评估合并读取入口，不能静默引入快照票据、轮询或重试。
- 生产 GET 不触发 import job、余额重建、现金读取、OA 写回。导出虽为 GET，但现有实现会追加下载审计；生产验证导出须按既有权限/审计执行，不能称其为“零写入纯只读”。

## 12. 实际实施与发布前验证（2026-09-08）

### 12.1 已实现与删除项

- 一个银行域共享 SQL 片段负责请求内顺序和末余额证明；账户/列表/导出使用同一规则。没有正式 migration、新表、顺序持久化、缓存、worker 或新依赖；保留原始银行事实。
- 分支只确认可以证明的末余额，不枚举路径；闭合组必须有紧邻前组的单笔、有时间且非空的锚点。日期精度不足、断链、缺余额及多币种按明确状态显示。
- 账户/行新增状态及 nullable 完整总额；银行公共 DTO 单独附加状态，分类公共 mapper、Workbench 等下游不接收排序 I/O。XLSX 原 18 列不变，只追加第 19 列顺序说明。
- 全仓扫描确认旧账户读取仅有废弃测试使用后，删除 `BankDetailsService.list_accounts/_latest_balance_transaction`、core `list_bank_transaction_accounts`、state-store wrapper 与独占 fake。有效 metadata、缺余额、日期范围、账户合计等断言迁入真实 PostgreSQL 测试；不删 metadata 一致性选择、事实保护、审计或历史 migration。
- 前端通过测试复现并修复三个竞态：旧账户流水晚返回、账户失败被流水成功清掉、旧页面刷新覆盖规则重新读取。复用页面内 AbortController，账户/流水/标签统计/规则各自保留错误；不加全局状态框架或轮询。

### 12.2 本地验证

- 独占 Docker PostgreSQL 16 测试库 `fin_ops_cash_test_bank_order`，只绑定本机端口；所有准备和 truncate 均走现有测试库校验，未使用生产 DSN。
- 新增 `tests/test_bank_same_time_ordering_postgres.py` 29 项，加现有真实 PG 集成 1 项，最终优化后 **30 项通过，25.643 秒**。覆盖截图两组、跨页/筛选/导出、混合收支、分支/闭合/断链、缺余额、日期精度、币种及账户隔离。
- 导入链验证使用正式 normalization/core import fact owner → 重读 → 补导/重复导入 → export snapshot → 正式 withdrawal service/repository → 幂等撤回 → 重读。这是真实 PG 服务闭环，不冒充 HTTP 上传→durable worker 全路径。
- 银行 query/service/routes/export/metadata/Workbench API 局部 **89 项通过，3.352 秒**；新增导出测试确认未确认组仍保留原顺序、零/缺失余额和末列说明。
- 完整前端 **96 文件 / 1249 项通过**；最后一项竞态加入后，银行专项 **75 项**、生产构建、相关 **6 项浏览器用例**再次通过。累计 28 个不同 Chromium 用例已通过，覆盖银行初始态、导出/权限、分页筛选、大表格、分类、规则及导入；这些浏览器用例使用明确 mock，不代替真实后端与生产验证。
- 最终真实 PG16 全量后端 **4121 项，4119 通过、2 failure、0 error、0 skip，499.114 秒**；两个失败仍是独立的 ETC 无扩展名上传，不属于银行排序变更。没有新增失败，不跳过、不放宽断言；不宣称全量全绿。
- 首次重跑遇到本地 Docker 退出，连接被管理员终止；恢复环境后完整重跑通过。该环境失败未改成 skip，没有影响生产。

### 12.3 性能实测与限制

以下为同一隔离 PG16、同一合成数据的旧 HEAD 与新查询，每项 3 次的中位数（毫秒），包含 repository/service，不是 HTTP p95。没有创建 baseline 文件。

| 规模 | 账户：旧→新 | 无筛选首页：旧→新 | 金额搜索：旧→新 |
| --- | ---: | ---: | ---: |
| 1 千笔 | 25.55→23.31 | 41.39→51.15 | 47.21→50.30 |
| 1 万笔 | 150.85→99.78 | 309.55→316.84 | 280.47→286.53 |
| 10 万笔 | 1035.42→800.59 | 3177.89→3226.61 | 3185.78→3336.68 |

规模为库内总笔数；合成起点 `2026-01-01 +08` 在测试库 UTC 的 txn_date 下有479笔落在上一日，因此年度列表分别命中521/9521/99521笔，旧新读取相同范围。导出另外测量真实 snapshot→XLSX 序列化：521行中位数566.72→513.61ms；9521行13729.49→16258.94ms，后者增加约2.53秒，不能称大导出高性能已达标。两组均核对导出行数与 snapshot total 相等；上限拒绝路径由原导出回归覆盖，未对超过2万行生成绕过限制的文件。

同时间链 2/10/100/1000 笔均实际执行；1000 笔新账户/列表/搜索中位数为 107.81/135.71/192.88 ms。查询不枚举排列，但不据此保证任意数据分布的尾延迟。

第一版对整个候选区间编号导致 10 万笔列表约 5.5 秒，已通过收窄目标组和复用 classifier base 移除这项无效开销；没有加缓存掩盖。最终 1 万笔 `EXPLAIN (ANALYZE, BUFFERS)` 显示账户只判定 6 个最新组、列表只判定 50 个组；列表历史账户 CTE 的 Actual Loops=0，普通路径不额外全历史扫描/hash。账户 SQL 80.765 ms、列表 SQL 346.499 ms、搜索 SQL 315.300 ms；列表存在既有分类中间结果临时块，不能宣称已经消除大规模分类成本。

发布前生产只读重测：建设银行年度账户/列表均 665 笔，错误余额仍为 94512.82，两组均手续费在前。每端点/并发档 20 个 HTTP 样本，全部成功：

因此修复前就存在 4 并发列表 p95 超过 1000ms 的问题。10 万笔无筛选列表也仍在约 3.2 秒，不宣布全场景高性能达标，不借本次正确性修复擅自重写分类架构。发布后按相同样本重测，并由现有 root-owned release checkpoint 保存生产证据；正式发布检查不绕过。
